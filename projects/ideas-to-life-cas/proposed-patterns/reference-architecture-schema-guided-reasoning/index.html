    Reference Architecture: Schema-Guided Reasoning Contract

    Purpose & when to use this

    The Schema-Guided Reasoning Contract pattern solves the inherent unpredictability and non-deterministic nature of Large Language Model (LLM) outputs in autonomous and semi-autonomous systems. While LLMs excel at probabilistic reasoning, synthesis, and creative generation, programmatic execution pipelines, state machines, and persistence backends require deterministic, strictly typed data structures.

    Without an enforced schema contract, LLM responses suffer from structural drift, hallucinated attributes, missing mandatory fields, and unpredictable primitive types (such as string literals where numbers or booleans are expected), causing unhandled runtime exceptions and corrupting downstream knowledge layers.

    When to use this

    • Multi-Step Agentic Pipelines: In sequential or DAG-based agent workflows where the output of step N serves as the structured input to step N+1.
    • Architectural Knowledge Substrates: When reasoning processes generate persistent architectural artifacts (such as Architecture Decision Records, Architecture Evolution Maps, Alignment Reports, System Context models) that must be indexed, validated, and queried programmatically.
    • Hybrid AI/Deterministic Systems: Where an AI agent interfaces directly with strongly typed backend systems (Python Pydantic, TypeScript, Go) and databases (SQL, document stores).
    • Enterprise Governance & Compliance: In environments requiring auditable verification that an agent's reasoning artifact adheres to organizational policies and data contracts before ingestion.

    When NOT to use this

    • Open-Ended Conversational UI: When the user expects natural, fluid, interactive dialogue without programmatic parsing downstream.
    • Exploratory Idea Generation: Early-stage divergent brainstorming where enforcing rigid schema constraints suppresses generative variety and causes unnecessary rejection of creative thoughts.
    • Pure Text Summarization for Humans: Single-shot document summarization intended solely for human reading, where minor format variance does not affect downstream systems.
    • Extreme Low-Latency / Resource-Constrained Scenarios: Environments where the token overhead of transmitting complex JSON schemas and running parsing/validation loops adds unacceptable latency.

    Components

    • FlowRunner (src/cas_runner/runner.py): The top-level pipeline orchestrator. Manages the execution lifecycle of reasoning flows, coordinates sequential steps, passes prepared context inputs, and maintains the shared blackboard.
    • ReasoningExecutionContract (src/cas_runner/orchestration/reasoning.py): The central enforcement gateway. Couples prompt retrieval, runtime context injection, provider execution, and response validation into a unified fail-fast transaction. Ensures that invalid reasoning outputs never escape to downstream components.
    • PromptRepository (src/cas_runner/orchestration/prompts.py): The catalog and resolution engine for versioned prompt templates (src/prompts/). Resolves prompt content and extracts metadata (such as schema associations and semantic contract versions) from prompt frontmatter.
    • Schema Store (src/cas_runner/schemas/*.json): The authoritative repository of domain JSON Schema specifications (Draft 7 / Draft 2020-12). Defines immutable structure, required properties, field types, and validation rules for each reasoning step (e.g., rule_context_schema.json, aem_schema.json, aid_schema.json, architecture_decision_record_schema.json).
    • LLM Provider Abstraction (src/cas_runner/llm/): The unified boundary between CAS and upstream AI models (LiteLLM, Google Gemini, OpenAI, Anthropic). Formats schema constraints into model-native parameters (response_schema or response_format) to guide generation at the token sampling level.
    • Schema Validator (jsonschema engine): The post-generation verification engine. Performs deterministic validation against the target JSON Schema, catching malformed outputs, schema mismatches, and data type violations before data enters application state.
    • Context Blackboard (FlowRunner.context & src/cas_runner/io.py): The ephemeral runtime state and persistent knowledge store. Only accepts validated, schema-compliant dictionaries from the contract, ensuring downstream consumers operate with full type certainty.
    • Telemetry Span Collector (src/cas_runner/orchestration/telemetry.py): Observability component that records execution spans for every reasoning invocation, capturing token usage, latency, cost estimation, and explicit schema_validation_success or schema_validation_failure telemetry events.

    Technology choices

    • JSON Schema (Draft 7 / Draft 2020-12) via jsonschema: Selected as the primary contract standard because it is programming language agnostic, human-readable, widely standardized across enterprise ecosystems, and can be maintained independently of application code. Alternatives considered and set aside: Regex extraction (too brittle), raw YAML without schemas (lacks formal type contracts), and proprietary parser formats.
    • Pydantic v2 for Schema Generation & Model Serialization: Used within Python code to define strongly typed models (BaseModel) that can export JSON schemas directly, bridging the gap between Python type hints and JSON Schema definitions. Alternatives considered and set aside: Python dataclasses (lack built-in validation rules and runtime schema serialization).
    • Model-Native Structured Output (Constrained Decoding): Leverages vendor-provided structured output modes (e.g., Gemini structured output, OpenAI JSON Schema mode) during generation to guide token logit sampling, reducing generation failures. Alternatives considered and set aside: Free-form text prompting with secondary re-prompting (higher latency, token waste, and lower reliability).
    • Fail-Fast Step Interception: When validation fails, the contract immediately logs errors, emits an error span, and halts or gracefully falls back rather than attempting unsafe field coercions.

    Variants

    • Native Constrained Decoding (Strict Mode): Used when the LLM provider natively supports strict JSON schema enforcement at the API level (e.g., Gemini SDK response_schema or OpenAI strict: true). The schema is passed directly in the API request, ensuring 100% syntactically valid JSON output from the model.
    • Prompt-Embedded Schema with Post-Validation (Fallback Mode): Used when running against local or open-weights models (or legacy endpoints) that lack native constrained decoding. The JSON Schema or its TypeScript representation is serialized into the prompt system instructions, followed by strict jsonschema.validate() in the application runtime.
    • Self-Healing / Reflection Loop Variant: An optional extension where a jsonschema.ValidationError triggers an automatic, single-turn reflection prompt containing the original prompt, the failed output, and the specific validation error message, allowing the model to repair the schema mismatch.

    Non-functional characteristics

    • Reliability (High): Replaces unpredictable probabilistic text with deterministic, schema-validated contracts. Downstream code never receives unexpected keys, missing attributes, or invalid data types.
    • Quality & Consistency (High): Structuring output into defined properties forces the model to organize its thoughts systematically, improving reasoning completeness.
    • Performance & Latency (Moderate): Local jsonschema validation takes sub-millisecond time. Passing schemas to LLM APIs can marginally increase initial token processing, but eliminates latency overhead from multistep parsing errors or retry loops.
    • Cost & Token Efficiency (Predictable): Reduces token waste by preventing garbage completions and hallucinations that would otherwise require multiple conversational turns or workflow reruns to correct.
    • Operability & Observability (High): Telemetry hooks track exact schema pass/fail rates, making architectural drift and model degradation immediately visible in telemetry dashboards.

    Anti-patterns & known pitfalls

    • The "God Schema": Creating massive, deeply nested schemas (>500 lines) for a single reasoning step. Over-complex schemas degrade LLM attention, leading to truncated outputs or timeouts. Remedy: Decompose into smaller, focused sequential reasoning steps.
    • Untracked Schema Drift: Updating internal Python models or prompt instructions without updating the corresponding JSON Schema in src/cas_runner/schemas/. Remedy: Enforce CI/CD linting and automated schema validation tests.
    • Instruction-Only Schemas (No Runtime Validation): Prompting the model with "Please respond with JSON matching this format..." but failing to execute a validation check in code before using the response.
    • Over-Constraining Dynamic Fields: Imposing rigid regex patterns on fields that inherently require human language variability, resulting in false-positive validation rejections.
    • Conflating Syntactic Validation with Semantic Correctness: Assuming that passing schema validation means the architectural decision or reasoning is logically sound. Schema validation guarantees data shape, not cognitive accuracy.

    Adoption guidance

    Sensible Starting Point

    1. Identify the Reasoning Step: Choose a specific reasoning step that currently outputs free-form text or unstructured dictionaries.
    2. Define the JSON Schema: Author a concise JSON Schema in src/cas_runner/schemas/<step_name>_schema.json defining mandatory attributes and field types.
    3. Register the Schema: Add the mapping to ReasoningExecutionContract._load_schema_for_step() or specify it in the prompt's YAML frontmatter.
    4. Enforce Validation: Ensure the reasoning step wraps output consumption with jsonschema.validate(instance=output, schema=step_schema).

    Migration Path

    1. Shadow Mode: Introduce schemas into existing prompts, but set validation errors to log as warnings rather than raising exceptions.
    2. Baseline Collection: Run existing test suites and historical runs to identify schema edge cases.
    3. Strict Enforcement: Promote validation warnings to blocking exceptions in CI/CD and production runs once stability is established.
