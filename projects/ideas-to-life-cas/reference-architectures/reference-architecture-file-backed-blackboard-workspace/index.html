    Reference Architecture: File-Backed Blackboard Workspace

    Purpose & when to use this

    The File-Backed Blackboard Workspace pattern establishes a version-controlled filesystem hierarchy as a shared, persistent, and auditable knowledge store for multi-agent and multi-process systems. It enables independent agents, scripts, and CI/CD workflows to cooperate by reading and writing structured artifacts (templates, runtime context, governance rules) without introducing an external database or service dependency.

    When to use this

    • When multiple independent processes or agents need to share state, configuration, or knowledge across invocations.
    • When a complete audit trail of all writes and changes is mandatory (e.g., governance, compliance, or reproducibility reasons).
    • When operations require the ability to rollback to a previous state or inspect historical revisions.
    • When infrastructure simplicity is preferred and an external state store is considered overkill or operationally disruptive.
    • When the system already uses Git or version control for its deliverables and the blackboard can naturally coexist with the repository.
    • When the expected write throughput is moderate and the data volumes remain manageable (a few hundred to tens of thousands of small text files).

    When NOT to use this

    • For high-throughput transactional workloads that require low-latency reads and writes (e.g., a real-time trading system).
    • When complex relational queries or joins are frequent – files are not a substitute for a query engine.
    • When the system must handle massive binary blobs (large images, multimedia) efficiently; Git and filesystems are not optimised for that.
    • When concurrent writers need fine-grained locking or atomic multi-object transactions – file-level operations require explicit coordination.
    • When the deployment environment does not provide a persistent filesystem or when the system runs on ephemeral compute with no shared volume.
    • When you anticipate a high number of concurrent updates from many agents; Git commits become a bottleneck and race conditions become common.

    Overview

    The pattern is centred around a Git repository that acts as the single source of truth for all collaborative state. A bootstrap script initialises the required directory structure and merges governance blocks, after which agent processes read and write files to the workspace. The filesystem is the medium that decouples agents, allowing them to run asynchronously and on different hosts as long as they can access the same repository (through a shared volume or a Git remote).     Components

    Component Path (example) Responsibility
    Workspace Root workspace/ The top‑level directory that contains all blackboard artifacts. It is the single shared source of truth for agents and processes. It includes subdirectories for templates, runtime context, and governance blocks.
    Bootstrap Script src/cas_runner/bootstrap.py Initializes the workspace hierarchy, merges governance blocks (e.g., policy definitions), and sets up baseline configuration. It is the only component allowed to create or modify the global structure during initial setup.
    Governance Blocks workspace/governance/*.yaml Versioned, human-readable definitions of rules, policies, and constraints that agents must respect. They are written once and referenced by all steps to ensure consistent behaviour.
    Runtime Context Files workspace/runtime/execution-profile.yaml Dynamic, machine‑readable files that capture the current execution state, step results, and intermediate data. Agents update these files after each step to enable chaining and stateful workflows.
    Agent Step Scripts src/agents/**/step.py Independent execution units that read from and write to the workspace. They are stateless in memory but rely on the filesystem as their durable state. The scripts are the primary consumers and producers of blackboard content.

    Technology choices

    Recommended: - Version Control: Git (any distribution) – provides versioning, branching, merging, and distributed sync with minimal tooling overhead. - File Formats: YAML for configuration and runtime context, Markdown for documentation and templates. These are human‑readable, diffable, and supported by all major languages. - Bootstrap Language: Python – because the existing bootstrap.py uses it, and the surrounding ecosystem (e.g., pyyaml, click) enables quick customisation. - Filesystem: POSIX‑compliant filesystem (local disk, NFS, or a mounted volume). Git repositories work well across these.

    Alternatives considered and set aside: - Redis / Memcached: In‑memory key/value stores – provide low‑latency but require a separate service, have no inherent versioning, and are not suitable for audit trails. - PostgreSQL: Full‑featured relational DB – offers strong querying and locking, but adds infrastructure, schema maintenance, and operational complexity that is unjustified for document‑centric blackboards. - Object storage (S3, GCS): Good for binary blobs but poor for fine‑grained updates and auditability; also requires network I/O and credentials. - NoSQL document store (MongoDB): Flexible schema but still an external service with its own consistency model and no native Git integration.

    Variants

    1. Single‑Repository Blackboard: All blackboard files live in one Git repository (the pattern’s default). Simple and portable, but can cause merge conflicts if many agents write simultaneously.
    2. Submodule‑Based Blackboard: The blackboard is a separate Git repository that is included as a submodule. This isolates the blackboard from the main codebase and allows independent versioning and access control.
    3. Loose vs. Strict Schema: The blackboard can impose a strict folder structure and file naming (easier to validate) or allow arbitrary files (more flexible but harder to enforce consistency). The pattern favours a moderate, schema‑light approach.
    4. Synchronous vs. Asynchronous Write: Agents can write files synchronously (commit immediately) or asynchronously (stage and commit in batches). Asynchronous reduces commit frequency but complicates rollback and conflict resolution.
    5. File‑Based Locking: To avoid concurrent modification issues, agents may acquire a lock file before writing. This adds coordination overhead but ensures atomicity when multiple writers are active.
    6. Hybrid with Small Database: Some teams augment the file blackboard with a small database (e.g., SQLite) for indexed runtime context while keeping the canonical blackboard in Git. This is acceptable if the file tree remains the audit source.

    Non-functional characteristics

    Reliability: - Git history provides a complete recovery mechanism; any file can be restored to a previous version. - File corruption is unlikely if atomic writes (write temp + rename) are used; Git also hashes content and detects integrity issues. - The pattern supports graceful degradation: agents can continue reading stale files even if the workspace is temporarily inconsistent, as long as they validate content.

    Performance & Latency: - Reads are fast – typical filesystem lookups are milliseconds. - Writes are slower due to Git commit overhead, especially in large repositories. For a small number of files (< 1000) commits are acceptable, but latency grows with repository size. - Concurrency is limited by Git’s merge complexity; heavy simultaneous writes can cause conflicts and require retries. - No external network calls, so latency is deterministic and largely bounded by disk I/O speed.

    Cost & Efficiency: - Zero infrastructure cost – no separate database service or dedicated storage buckets. - Low operational overhead – only a Git repository and a filesystem are needed. - Storage is cheap, but disk usage grows with every update (Git keeps full history). For long‑lived projects, periodic garbage collection or history squashing may be required. - Human effort to maintain structure and resolve conflicts is the primary “cost” in terms of team time.

    Operability: - The blackboard is transparent – any developer can inspect it with standard tools (git log, grep, less). - Monitoring is simple: check file existence, modification times, and commit history. - No external service to scale, patch, or back up – backups are automatically provided by Git remotes. - Requires careful documentation and disciplined commit practices; otherwise, files can become inconsistent.

    Anti-patterns & known pitfalls

    1. Overstructuring and Schema Rigidity: Imposing a rigid, complex directory tree and mandatory metadata for every file creates overhead and discourages agile use. Remedy: Start with a minimal set of directories and only add structure when needed; keep schemas optional and tolerant.
    2. Storing Large Binaries: Committing large binary files (e.g., videos, ML models) bloats the repository and makes every operation slow. Remedy: Use Git LFS or keep binaries outside the blackboard and store only pointers/URLs in files.
    3. Lack of Atomic Writes: If agents write files directly, a crash mid‑write can corrupt state. Remedy: Always write to a temporary file and rename atomically; or use Git staging and commit as a single operation.
    4. Uncontrolled Concurrent Writes: Multiple agents updating the same file without coordination leads to lost updates and merge conflicts. Remedy: Introduce file‑level locking, partition responsibility per agent (each owns a directory), or use a central coordinator.
    5. Ignoring Governance Blocks: Agents that bypass policy definitions may violate rules. Remedy: Enforce validation at bootstrap and at each step; make governance blocks immutable after initial merge.
    6. Using the Blackboard as a Log: Writing every transient event to the blackboard creates a monotonically growing file and pollutes the knowledge store. Remedy: Separate runtime context files from a dedicated log area, and periodically clean or rotate them.
    7. Not Using Git Remotes: Keeping the blackboard only on a local disk defeats the purpose of auditability and distribution. Remedy: Always push to a remote repository and pull before starting new work.

    Adoption guidance

    Starting points: - Begin by defining a minimal workspace layout (e.g., templates/, governance/, runtime/). - Reuse the existing bootstrap.py from src/cas_runner – extend it to merge any new governance blocks. - Identify the first agent that will persist state to the blackboard; convert it from an in‑memory or ad‑hoc JSON file to the structured workspace.

    Migration path: - If you currently use a database (e.g., PostgreSQL) for state, export the data into YAML/JSON files in a new runtime/ directory, then update the agents to read/write the files instead of issuing SQL queries. - Gradually shift more components (CI jobs, other scripts) to consume the same workspace files. - Use a feature flag to keep the old database alive until the new blackboard is fully validated in production.

    Governance ownership: - Assign a “Workspace Steward” who owns the directory structure, governance block versioning, and conflict resolution policies. - The steward should be an architect or a senior engineer familiar with the full system. - Governance metadata should be documented in the governance/ folder and linked to ADRs (architecture decision records) for traceability. - All changes to the workspace structure must go through a lightweight review process, similar to code changes.

    Stakeholders to involve: - System architects (to approve structural changes) - DevOps/CI engineers (to ensure pipeline integration) - All agent developers (to align on read/write contracts)
