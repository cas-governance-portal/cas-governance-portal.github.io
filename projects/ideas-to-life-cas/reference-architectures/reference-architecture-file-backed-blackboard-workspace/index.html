    Reference Architecture: File-Backed Blackboard Workspace

    Purpose & when to use this

    The File-Backed Blackboard Workspace pattern coordinates multi-agent and pipeline execution state by organizing structured, human-readable, and version-controlled filesystem directories as an immutable and branchable shared blackboard.

    When to use this

    • Multi-agent or step-based workflows requiring shared context, prompt templates, and execution state across discrete invocation boundaries.
    • Systems where full execution auditability, reproducibility, and git-commit-level time-travel debugging are essential.
    • Deployments in local-first, air-gapped, or containerized CI/CD environments where provisioning external databases (e.g., Redis, PostgreSQL) introduces excessive operational friction.
    • Workflows requiring human-in-the-loop review, direct file editing, and standard git diffing of intermediate agent artifacts.

    When NOT to use this

    • High-frequency, sub-second concurrent write workloads spanning multiple distributed nodes requiring transactional ACID locking.
    • Storage of large binary assets, embeddings, or multi-gigabyte vector payloads that degrade filesystem performance and bloat git repositories.
    • Highly distributed agent swarms requiring millisecond pub/sub signaling rather than state-file polling or step-phase synchronization.

    Components

    • Bootstrap Orchestrator (src/cas_runner/bootstrap.py): Responsible for scaffolding the standardized directory hierarchy, creating initial runtime profiles, and merging governance configuration blocks into the target workspace.
    • Knowledge Provider IO Layer (src/cas_runner/io.py): Defines the abstracted IO protocol (LocalKnowledgeProvider) for reading, writing, and parsing structured artifacts (YAML, JSON, Markdown) across workspace directories.
    • Workspace Blackboard Store (cas-knowledge/): Functions as the centralized, file-backed shared state holding runtime execution profiles, governance contracts, intermediate agent memory, and generated output artifacts.
    • Agent Execution Workers (src/cas_runner/): Execute discrete architectural or code synthesis tasks, reading input prompts and configurations from the blackboard and writing back state updates and validation signals.

    Technology choices

    • Structured Serialization (YAML / JSON): Delivers human-readable, schema-validatable configurations and profiles easily inspected and diffed in source control.
    • Filesystem & Abstracted IO (Python pathlib & KnowledgeProvider Protocol): Decouples pipeline steps from raw filesystem paths, facilitating in-memory or alternative storage mockups during testing.
    • Git Version Control: Functions as the authoritative distributed log and audit trail, capturing agent state transitions across commits.

    Alternatives Considered & Set Aside

    • Relational / Document DBs (PostgreSQL / MongoDB): Set aside due to unnecessary operational deployment complexity, loss of direct git branching alignment, and friction in local CLI execution.
    • In-Memory Cache (Redis): Set aside because volatile memory lacks out-of-the-box post-execution reproducibility and git revision association.
    • Embedded SQLite: Set aside in favor of flat structured files to preserve transparent human inspection, manual editing, and visual git diff capability.

    Variants

    • Transient Execution Scratchpad: An ephemeral variant where a local temporary directory is scaffolded for the duration of a single execution run and discarded or zipped into an archive upon step completion.
    • Git-Committed Persistent Blackboard: A strict governance variant where every phase transition or agent milestone triggers an automated git commit, capturing an immutable chronological history of state mutations.
    • Hybrid Local-Remote Mirror: A distributed variant where the local blackboard synchronizes to an object storage bucket (e.g., S3 or OCI Object Storage) at the conclusion of each pipeline milestone for team visibility.

    Non-functional characteristics

    • Reliability: High data durability guaranteed through local filesystem journaling and Git revision tracking. Failure recovery is achieved by resetting the git working directory to the last known valid commit.
    • Performance & Latency: Local NVMe/SSD read/write operations yield microsecond latency for file access. Scalability is bounded by directory file counts and parse times of serialized artifacts.
    • Cost & Efficiency: Zero continuous infrastructure or database licensing costs; runs natively on local workstations and commodity CI/CD compute instances.
    • Operability: Unmatched debuggability: developers can inspect, tail, and modify workspace files directly using standard command-line tools without database clients.

    Anti-patterns & known pitfalls

    • The Monolithic Single-File Blackboard: Storing all agent memory, history, and outputs in a single state.json file leads to write contention and frequent git merge conflicts. Remedy: Partition the blackboard into modular domain folders (e.g., runtime/, governance/, artifacts/, memory/) with individual files per concern.
    • Unbounded Log and Binary Accumulation: Writing massive log streams or large binary artifacts directly into the blackboard clogs git history and degrades cloning performance. Remedy: Store large binary artifacts in object storage or git LFS, keeping only content hashes and structured references in the blackboard workspace.
    • Direct Hardcoded Path Access: Pipeline components referencing direct absolute or relative filesystem paths instead of routing through the IO abstraction layer. Remedy: Enforce all disk access through the KnowledgeProvider protocol to allow transparent redirection and test mocking.

    Adoption guidance

    • Starting Points: Define a standard workspace schema outlining mandatory directories (e.g., cas-knowledge/runtime, cas-knowledge/templates). Integrate bootstrap.py initialization logic into developer setup scripts and CI step entrypoints.
    • Migration Path: For projects currently using scattered environment variables or local JSON dumps, consolidate into the structured blackboard folder structure and apply validation schemas to runtime profile files.
    • Governance Context: Maintained under the Intelligence domain in ideas-to-life-cas with Established maturity status.
