    Reference Architecture: Schema-Enforced Domain Contracts

    Purpose & when to use this

    The Schema-Enforced Domain Contracts pattern mandates formal, machine-validated contracts (e.g., Pydantic models, JSON Schema) for all data exchanged between system components, especially those originating from generative AI or LLM outputs. It ensures that every payload entering a critical domain boundary is structurally verifiable, type-safe, and semantically correct before any side effects occur.

    When to use this

    • LLM or generative AI agents produce structured data that will be persisted, transmitted, or used to trigger business actions.
    • Multiple consumers depend on a consistent, well-defined data shape (e.g., health calculators, dashboards, state mutation).
    • Data integrity is paramount, and silent corruption or incomplete records can cause cascading failures or erroneous decisions.
    • You need to enforce an explicit, evolvable contract across teams or services, and want runtime validation rather than trusting implicit assumptions.
    • There is a need for clear, actionable error messages when data is malformed, enabling automated retries or escalation.

    When NOT to use this

    • The data is ephemeral, low-stakes, and does not affect persistent state or downstream logic.
    • Schema evolves extremely rapidly and strict validation would create expensive churn or constant redeployment.
    • Performance is critical and the overhead of validation on every message is unacceptable, though usually negligible for moderate payloads.
    • The system already relies on a dynamically typed data flow where flexibility is more valuable than guarantees.
    • You are working with unstructured free-form text that must remain untouched and unconstrained.

    Overview

    This pattern introduces a validation gateway between data producers (particularly LLM agents) and the internal domain logic. The flow is simple but powerful:

    Key Flow: The LLM agent emits raw output. The validator (e.g., Pydantic model) checks it against the schema from the registry. If valid, the output is promoted to a typed contract that downstream consumers can trust. If invalid, the error is captured and routed to an error handler that can trigger retry, fallback, or human intervention.

    Components

    Component Repository Path Responsibility
    Governance Models src/cas_runner/governance/models.py Defines the authoritative Pydantic models for governance entities (GovernanceInventory, ComplianceFinding, GovernanceHealth, etc.). These models serve as the single source of truth for data structure, types, and validation rules.
    ComplianceEngine src/cas_runner/governance/compliance.py (inferred) Executes the validation pipeline. It receives raw agent output, instantiates the appropriate Pydantic model, and returns either a valid contract or a detailed validation error. It also orchestrates fallback strategies when invalid data is encountered.
    LLM Agent / Output Producer any agentic component Generates raw JSON or similar output, often from an LLM. This is the source of potentially malformed or incomplete data that needs to be governed.
    Schema Registry / Definitions src/cas_runner/governance/schemas/ (inferred) Stores JSON Schema representations or versioned Pydantic model definitions. It provides a retrievable reference for validation, documentation, and cross-service contract consistency.
    Downstream Consumers visualization, health calculators, state mutation modules Consume the validated domain contracts to perform actions such as emitting metrics, updating repository state, or generating reports. They rely on the contract's type guarantee and can safely process without defensive validation.
    Error Handler & Retry Mechanism internal utility Catches validation failures, logs structured error details, and optionally triggers corrective actions such as requesting the LLM to regenerate output with guidance, or escalating to a human reviewer.

    Technology choices

    Recommended technology stack: - Pydantic v2 as the primary validation and serialization framework (Python) – provides declarative model definitions, automatic JSON Schema generation, and rigorous type checking. - JSON Schema as the neutral interchange format – enables cross-language validation (e.g., TypeScript, Java) and serves as the canonical schema for external APIs. - Mypy or Pyright for static type checking, ensuring that schema definitions are type-safe at compile time. - FastAPI or similar frameworks that integrate Pydantic natively for API request/response validation.

    Alternatives considered and set aside: - Dataclasses – lacked integrated validation and error handling, requiring manual __post_init__ checks. - Marshmallow – powerful but heavier, with a less seamless integration into modern async Python. - JSON Schema manual validation – error-prone and redundant; Pydantic abstracts the complexity. - Protocol Buffers / gRPC – overkill for internal validation, adds serialization overhead without direct benefit for Python-centric systems.

    Variants

    1. Strict Mode: Validation is fail-fast. Any invalid payload is rejected, logged, and a retry is triggered. Used when data corruption is unacceptable and regeneration cost is low.
    2. Lenient Mode: Unknown fields are stripped, and coercions are applied (e.g., string to int) when safe. Useful when upstream models age faster than schemas.
    3. Fallback Chain: When a primary validation fails, a secondary LLM call is made with the original output and the validation errors as context to generate a corrected version. This is a common pattern in agentic systems.
    4. Versioned Contracts: Schemas are versioned and the validation engine can accept multiple versions simultaneously, allowing gradual migration of consumers.
    5. Schema-as-Code: Pydantic models are the source of truth, with JSON Schema generated and exported for use by external services or front-end type generation (e.g., openapi-typescript).
    6. Streaming Validation: For very large payloads, validation can be performed on a chunk basis (if supported) to keep memory bounded.

    Non-functional characteristics

    Reliability: - Dramatically reduces the incidence of malformed data reaching business logic, preventing silent failures and data corruption. - Enables deterministic error handling and recovery, as validation failures are predictable and actionable. - Increases confidence in cross-team and cross-service data exchanges.

    Performance & Latency: - Validation overhead is typically in the range of microseconds to milliseconds per object, acceptable for most workloads. - For high-throughput scenarios, Pydantic v2's Rust core gives negligible performance impact (~2-3x slower than raw dict access, but often not the bottleneck). - Retry loops (if used) can add latency, so should be bounded and only triggered when appropriate.

    Cost & Efficiency: - Minimal direct cost; validation is CPU-bound and small. - Reduces rework cost by catching errors early, avoiding wasteful downstream processing on invalid data. - If LLM regeneration is used as fallback, it introduces token costs; thus, fallback should be conditional.

    Operability: - Clear, structured validation errors that integrate with logging and monitoring (e.g., structured JSON logs). - Schema changes can be versioned and rolled out gradually without breaking consumers. - Model definitions act as living documentation, reducing onboarding friction for new developers. - Requires discipline in updating schemas when domain rules change; otherwise, drift occurs.

    Anti-patterns & known pitfalls

    1. Overly Complex Models: Creating deeply nested, highly abstract models that are hard to maintain and lead to performance penalties. Remedy: Keep models flat and aligned with actual use cases; use BaseModel composition instead of heavy inheritance.
    2. Silent Failure: Catching validation errors and returning generic error messages without proper logging or retry. Remedy: Always log the specific field errors and the raw payload (sanitized) for debugging.
    3. Schema Drift: Models are updated but JSON Schema exports are not regenerated, causing inconsistencies between internal and external contracts. Remedy: Automate schema generation in CI, and enforce schema compatibility tests.
    4. Ignoring Validation Errors: Treating validation as a suggestion and proceeding with partial data. This defeats the entire purpose. Remedy: Fail fast in production; use fallbacks only in specific, controlled paths.
    5. Using Generic Dicts Instead of Typed Models: This bypasses schema enforcement and reintroduces the very risks the pattern aims to eliminate. Remedy: Enforce model usage via code reviews and linting rules.
    6. Validation at the Wrong Boundary: Validating only at the API boundary but not inside the system before state mutation. Remedy: Apply validation at every trust boundary, including from LLM agent to orchestrator and from orchestrator to storage.
    7. Not Versioning Schemas: When schemas change, old consumers break. Remedy: Implement versioned contracts and support multiple schema versions concurrently.

    Adoption guidance

    Starting Point: - Identify the highest-risk data flows: those that persist, trigger actions, or feed critical dashboards. - Define Pydantic models for the top 3-5 entities in those flows, and integrate validation into the consumption path. - Start with a strict-mode policy for those flows, and make validation errors visible (e.g., alerting hook).

    Migration Path: 1. Phase 1: Core Governance Models (as seen in governance/models.py): Enforce validation for all governance-related outputs. 2. Phase 2: Agentic Output – Apply the same pattern to all LLM-generated structured data (skills, steering, etc.). 3. Phase 3: Cross-Cutting Adoption – Extend to all internal APIs and data stores, using JSON Schema generation for external contracts. 4. Phase 4: Continuous Improvement – Automate schema generation and compatibility testing in CI, and treat validation failures as quality gates.

    Governance Ownership: - Domain: ideas-to-life-cas - Initiative: schema-enforcement (proposed) - Owner: Architecture Guild / Data Governance Team (contact: architecture@ideas-to-life-cas.io) - Review cadence: Quarterly schema review with stakeholders to handle version evolution.
