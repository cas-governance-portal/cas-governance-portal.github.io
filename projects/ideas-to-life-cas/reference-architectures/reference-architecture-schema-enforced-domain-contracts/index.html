    Reference Architecture: Schema-Enforced Domain Contracts

    Purpose & when to use this

    The Schema-Enforced Domain Contracts pattern establishes explicit, strongly typed boundary contracts for all domain entities, state mutations, and intelligence payloads exchanged between autonomous agents and core application services.

    When to use this

    • When integrating Large Language Models (LLMs) or autonomous agent routines whose outputs are non-deterministic, partially structured, or prone to hallucinated attributes.
    • At subsystem and module boundaries where state persistence, compliance evaluation, or visualization requires guaranteed type safety and structural integrity.
    • In distributed multi-agent workflows where structured action payloads (e.g., governance remediation actions, compliance findings) trigger state modifications.
    • When automated validation feedback is required to guide agent self-correction loops on schema mismatches.

    When NOT to use this

    • For simple, free-form conversational interfaces or streaming text responses where structured downstream processing is not performed.
    • In early exploratory prototyping where domain data structures change on every invocation and contract overhead slows proof-of-concept discovery.
    • For homogeneous internal helper functions within a single tightly coupled module where standard Python type hints suffice.

    Components

    • Contract Validator (src/cas_runner/governance/models.py, src/cas_runner/skills/models.py): Executes declarative runtime schema validation, type coercion, field constraints, and structural invariant checks on incoming agent payloads.
    • Agent Runner (src/cas_runner/skills/models.py): Orchestrates prompt execution with external LLM providers and channels raw JSON completion output to the validator before executing side-effects.
    • Compliance Engine (src/cas_runner/governance/): Consumes verified domain models (e.g., GovernanceInventory, ComplianceFinding) to calculate governance health scores and risk profiles without defensive parsing.
    • Domain State Store (data/ or persistent storage): Persists serialized validated models to filesystem or database storage, ensuring state history contains only valid schema instances.

    Technology choices

    Recommended Technologies

    • Pydantic v2: Selected as the core contract engine due to its compiled Rust-based validation core (pydantic-core), high throughput, native support for JSON Schema generation, and ergonomic dataclass-like syntax.
    • JSON Schema Draft 2020-12 / Draft-07: Used for provider-agnostic function calling and tool definition schemas sent directly to LLM prompt APIs.

    Alternatives Considered and Set Aside

    • Marshmallow: Set aside due to slower Python-based validation overhead, lack of native typing integration, and more verbose schema declarations.
    • Raw Python Dataclasses with jsonschema: Set aside due to fragmented serialization/deserialization logic and boilerplate parsing code.
    • Protocol Buffers / gRPC: Set aside because the agent orchestration stack is Python-centric, text/JSON-driven at the LLM boundary, and does not require binary transport serialization.

    Variants

    • Strict Reject (Fail-Fast): The pipeline immediately halts execution upon validation failure, logging schema errors and discarding the agent payload. Used for deterministic batch processing and automated gatekeeping.
    • Agentic Self-Correction Loop: When validation fails, the Pydantic error details (loc, msg, type) are formatted into a remedial prompt and sent back to the LLM provider for a localized retry (up to N attempts) before failure.
    • Versioned Schema Pipeline: Dual-model architecture supporting legacy and current domain schemas (e.g., v1.ComplianceFinding and v2.ComplianceFinding) with migration adapters for rolling state upgrades.

    Non-functional characteristics

    • Reliability: Guarantees complete domain isolation from malformed payloads, preventing catastrophic failure or unhandled exceptions deep in business logic.
    • Performance & Latency: Validation overhead is negligible (< 1ms) utilizing Pydantic v2's Rust implementation, representing < 0.1% of the round-trip latency of typical LLM calls.
    • Cost & Efficiency: Early rejection of invalid structures halts invalid downstream execution cascades, saving inference tokens, database I/O, and unnecessary compute.
    • Operability: Generates explicit, structured error trajectories detailing the exact JSON path and constraint violation, simplifying root-cause debugging.

    Anti-patterns & known pitfalls

    • Permissive Dictionary Escapes: Declaring critical payload fields as Dict[str, Any] or typing.Any to bypass schema rigidity. Remedy: Model all domain fields explicitly, using discriminated unions or generic parameterized models where polymorphism is required.
    • Post-Persistence Validation: Storing raw agent output in a database and validating it when read by downstream consumers. Remedy: Enforce validation at the gateway ingestion point prior to state commitment or side-effect execution.
    • Unversioned Schema Drift: Modifying field names or constraints in consumer models without updating upstream prompt schemas, causing systematic validation failures. Remedy: Generate prompt schema definitions dynamically from the source-of-truth Pydantic models using model_json_schema().

    Adoption guidance

    Migration Path

    1. Identify unstructured boundary dictionaries in existing agent runtimes (src/cas_runner/skills/ and src/cas_runner/governance/).
    2. Define strict Pydantic v2 models representing the domain entities with concrete validations and field constraints.
    3. Integrate model_validate_json() or model_validate() calls at the extraction layer immediately after LLM execution.
    4. Refactor downstream components to accept strongly typed instances instead of generic dicts.
