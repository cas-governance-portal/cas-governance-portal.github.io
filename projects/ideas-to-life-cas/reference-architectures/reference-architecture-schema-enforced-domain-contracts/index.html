    Reference Architecture: Schema-Enforced Domain Contracts

    Purpose & when to use this

    Purpose

    Schema-Enforced Domain Contracts establishes rigid, typed validation boundaries for all structured inputs and outputs across automated and agentic execution pipelines. By inserting deterministic schema validation gates directly before domain ingestion and persistence layers, this pattern guarantees that non-deterministic artifacts (such as LLM generation payloads or dynamic external events) strictly conform to domain invariants before modifying repository or system state.

    When to use this

    • When integrating Large Language Models (LLMs) or autonomous agents whose outputs must update persistent domain models, audit ledgers, or operational state machines.
    • In distributed or multi-stage pipelines where downstream consumers require strong typing guarantees without defensive parsing logic.
    • When automated compliance engines (such as ComplianceEngine) evaluate heterogeneous project structures and require standardized entity structures (e.g., GovernanceInventory, ComplianceFinding).
    • When API boundaries between decoupled services require self-describing, versioned schema contracts that can fail fast at execution boundaries.

    When NOT to use this

    • In simple pass-through proxies or streaming byte-pipe architectures where payload introspection introduces unacceptable latency.
    • For exploratory, schema-free prototyping where entity shapes mutate continuously and runtime enforcement creates unnecessary friction.
    • When consuming strictly immutable binary streams or primitive scalar event buses where low-level wire formats (e.g., raw Protobuf without validation logic) suffice.

    Components

    • Governance Models Specification (src/cas_runner/governance/models.py): Defines rigid typed domain contracts (such as GovernanceInventory, ComplianceFinding, GovernanceHealth, GovernanceRisks, and GovernanceAction) using strict Pydantic definitions and JSON Schema serialization.
    • Steering & Orchestration Models (src/cas_runner/steering/models.py): Establishes schema definitions for workflow steering, routing parameters, and execution state tokens exchanged between flow orchestrators.
    • ComplianceEngine & Validation Gate (src/cas_runner/governance/engine.py): Executes programmatic evaluation against the domain models, enforcing schema validation before allowing entity persistence or state mutation.
    • FlowRunner Agent Orchestrator (src/cas_runner/runner/flow.py): Coordinates execution steps across LLM agents and invokes validation filters to intercept malformed, truncated, or hallucinated payloads.

    Technology choices

    Recommended Technologies

    • Pydantic v2: Chosen as the primary domain modeling and validation engine due to its compiled Rust core, high-throughput validation performance, and native generation of JSON Schema Draft 2020-12 specifications.
    • JSON Schema: Adopted for cross-language contract serialization, enabling documentation generation and tool-calling validation directly at agent runtime.
    • Python Typing (typing / dataclasses): Standardized throughout core interfaces for static type checking via Mypy and Pyright.

    Alternatives Considered and Set Aside

    • Marshmallow / Cerberus: Evaluated for data validation but rejected due to lack of seamless IDE static analysis support, slower execution speeds, and legacy schema composition paradigms.
    • Raw Protobuf / gRPC: Considered for schema enforcement across boundaries, but set aside for domain-level agent interaction due to JSON's ubiquity in generative tool calling and human-readable audit persistence requirements.
    • Handcrafted Defensive Parsers: Rejected because ad-hoc verification leads to code duplication, regression gaps, and brittle error recovery paths across orchestrators.

    Variants

    1. Strict Fail-Fast Validation

    Any validation failure immediately halts execution, aborts transaction commits, and emits a structured ValidationError event containing precise field-level diagnostics. This is the default mode for persistent state modifications and compliance evaluations.

    2. Validated Schema with Agent Self-Correction Loop

    When an LLM agent produces a payload violating the schema contract, the validation error details (including missing fields and constraint failures) are reflected back to the agent context as a prompt correction token. The agent re-attempts generation within a bounded retry loop (typically max 3 iterations) before escalating to an operator.

    3. Graceful Coercion and Partial Extraction

    For non-critical analytics ingestion, inputs that deviate slightly (e.g., string representations of integers or ISO timestamp variations) are coerced safely into standard domain models using tolerant parsing modes, quarantining only irreconcilable attributes.

    Non-functional characteristics

    Reliability

    • Prevents silent schema drift and invalid database updates by enforcing deterministic boundaries.
    • Protects state stores against corrupted structures produced during agent hallucinations or network truncations.

    Performance & Latency

    • Pydantic v2 execution provides sub-millisecond serialization and validation for typical payloads (<50KB).
    • Zero-copy validation paths prevent overhead in in-memory pipeline orchestration.

    Cost & Efficiency

    • Early rejection of invalid outputs reduces downstream compute consumption by aborting subsequent pipeline stages immediately.
    • Bounded retry loops with specific error feedback reduce token consumption compared to naive full re-prompting.

    Operability

    • Schema mismatches produce standardized, machine-readable diagnostic payloads (field path, error reason, provided value) facilitating rapid debugging.
    • Seamless export of JSON Schema definitions simplifies documentation synchronization and API catalog indexing.

    Anti-patterns & known pitfalls

    1. Silent Pass-Through Fallback

    • Description: Catching validation errors and falling back to unstructured dict representations to keep the pipeline alive.
    • Remedy: Never bypass the schema gate. If partial execution is permitted, define explicit optional fields or a distinct fallback contract rather than bypassing typed domain boundaries.

    2. Leaky Database Entity Coupling

    • Description: Reusing database ORM models directly as the external agent or API contract model.
    • Remedy: Decouple domain contracts (e.g., Pydantic transfer objects) from storage layer entities (e.g., SQLAlchemy/Tortoise models) to enable independent lifecycle and migration strategies.

    3. Kitchen-Sink Polymorphic Models

    • Description: Creating overly permissive schemas with broad Any types or weakly constrained union types to avoid schema failures.
    • Remedy: Use discriminated unions with strict type tags to preserve structural enforcement across diverse polymorphic payloads.

    Adoption guidance

    Starting Point

    1. Define canonical models in dedicated contract modules (src/cas_runner/governance/models.py) using immutable Pydantic BaseModel classes with extra = 'forbid'.
    2. Wrap agent output decoders with explicit validation invocations prior to passing objects to downstream domain handlers.
    3. Integrate contract regression tests verifying that synthetic invalid inputs are systematically trapped with appropriate error signatures.

    Migration Strategy

    • Phase 1 (Shadow Validation): Deploy schemas alongside existing untyped flows in passive mode; log contract violations without halting execution.
    • Phase 2 (Enforcement Gate): Activate strict rejection on core mutations and compliance scoring engines.
    • Phase 3 (Self-Healing Pipelines): Integrate validation error reflection into agentic retry prompts for autonomous payload correction.
