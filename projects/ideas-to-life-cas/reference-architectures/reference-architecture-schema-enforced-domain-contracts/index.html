    Reference Architecture: Schema-Enforced Domain Contracts

    Purpose & when to use this

    When to use this

    Use this pattern when LLM-driven agents produce structured outputs (e.g., governance decisions, compliance findings, action payloads) that must be consumed by downstream systems with strict expectations. It is essential when malformed, incomplete, or hallucinated data can cause cascading failures in repository state modification, visualization, or health calculations. It is also applicable when multiple agents or services need to exchange domain objects and you require a canonical, versioned contract enforced at runtime.

    When NOT to use this

    Do not apply this pattern when outputs are only human-facing or free-form (e.g., chat summaries) and validation overhead is not justified. Avoid it when the domain is extremely volatile and contracts change faster than validation logic can be updated, or when performance constraints make runtime validation unacceptable (though static typing may be preferable). If the system relies on untyped data stores (e.g., document DBs) and flexible schemas, enforcing rigid contracts may reduce agility without clear benefit.

    Components

    Domain Models (Pydantic)

    • Path: src/cas_runner/governance/models.py
    • Responsibility: Defines rigid, strongly-typed contracts for all governance entities (GovernanceInventory, ComplianceFinding, GovernanceHealth, GovernanceRisks, GovernanceAction). Enforces attribute types, required fields, and business rules on instantiation.

    ComplianceEngine

    • Path: src/cas_runner/governance/compliance_engine.py (inferred)
    • Responsibility: Receives raw outputs from agents, validates them against the domain models, and either returns conformant objects or rejects the payload. Acts as the guardrail ensuring only schema-compliant data enters the repository.

    Agent Output Streams

    • Path: src/cas_runner/agents/*
    • Responsibility: LLM-powered agents that generate governance decision payloads, compliance findings, and action proposals. These outputs are expected to conform to the domain contracts, but may be incomplete or malformed.

    Repository State Store

    • Path: src/cas_runner/repository/*
    • Responsibility: Persists the validated domain objects. Accepts updates only after compliance validation, ensuring consistency and integrity of stored governance state.

    Visualization & Health Calculators

    • Path: src/cas_runner/monitoring/*
    • Responsibility: Consumes governed domain models to render dashboards, compute health scores, and generate insights. Benefits from strongly-typed inputs, reducing error-handling complexity.

    Technology choices

    Recommended Stack - Pydantic v2 for runtime data validation and serialization. Leverages Python type hints, JSON schema generation, and custom validators. - JSON Schema (via Pydantic's model_json_schema()) for cross-language interoperability and API contracts. - mypy/pyright for static type checking to catch contract violations at development time. - Pytest for contract tests ensuring models reject invalid payloads.

    Alternatives Considered & Set Aside - Marshmallow: Simpler but less integrated with type hints and modern Python; dropped for Pydantic's ecosystem. - attrs + manual validation: More boilerplate, no built-in JSON Schema generation. - Pure JSON Schema validation with jsonschema library: Lacks object-oriented benefits and IDE support. - Protocols/TypedDicts: Provide static contracts but no runtime enforcement.

    Variants

    1. Strict Rejection (default): Invalid payloads are rejected immediately with detailed error messages; the agent must regenerate.
    2. Coercion/Defaulting: Use Pydantic's coerce_numbers_to_str, default, and validation_alias to accept loosely-typed inputs and normalize them.
    3. Fallback to Generic Model: When domain evolves rapidly, fallback to a permissive dict model while logging warnings, then transition to rigid models incrementally.
    4. Multi-stage Validation: Separate structural validation (schema) from business-rule validation (pydantic validators) to allow partial processing.
    5. Async Validation: Use pydantic.TypeAdapter in concurrent contexts to validate large batches of payloads without blocking the event loop.

    Non-functional characteristics

    Reliability - Eliminates malformed data entering the repository, preventing silent corruption. - Clear error propagation from validation failures allows retries or alerts. - Strong contracts increase confidence in downstream computations.

    Performance & Latency - Validation overhead is minimal for small payloads (microseconds per object). - Pydantic v2 is optimized with Rust core, reducing CPU cost. - If validation becomes a bottleneck, use batch validation and caching strategies.

    Cost & Efficiency - Reduces debugging and rework costs caused by bad data. - Slight increase in runtime CPU for validation but negligible compared to LLM inference. - Development cost of maintaining models is offset by reduced downstream error handling.

    Operability - JSON Schema export enables contract sharing with non-Python services. - Versioning of contracts via semantic release ensures safe evolution. - Logging of validation failures aids in monitoring agent quality.

    Anti-patterns & known pitfalls

    • Over-strict contracts: Rejecting any deviation from schema may cause excessive agent retries. Mitigate with reasonable defaults and clear error messages.
    • Ignoring validation results: Silently skipping validation defeats the purpose. Always handle ValidationError and log or act.
    • Contract drift: Changing models without updating all consumers leads to runtime surprises. Enforce versioning and use automated dependency checks.
    • Fat models: Bundling too many concerns in one entity makes validation complex. Split into focused, cohesive models.
    • Skipping static typing: Relying solely on runtime validation misses errors early. Integrate mypy in CI.
    • No test coverage for validators: Pydantic validators must be tested for edge cases. Use property-based testing with Hypothesis.

    Adoption guidance

    Starting Point - Begin by identifying the most critical agent-produced payloads that already affect repository state. - Extract existing dataclasses or dicts into Pydantic models, preserving current behavior. - Add validation in the compliance engine and write targeted contract tests.

    Migration Path 1. Phase 1: Introduce Pydantic models for new governance entities (e.g., ComplianceFinding). 2. Phase 2: Migrate existing code to use these models, replacing manual checks. 3. Phase 3: Enable JSON Schema export and share contracts with frontend or external services. 4. Phase 4: Add static type checking and enforce in CI.
