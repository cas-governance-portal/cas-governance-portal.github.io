    Reference Architecture: Pure Functional Health Evaluation

    Purpose & when to use this

    The Pure Functional Health Evaluation pattern decouples diagnostic assessment and score calculations from telemetry ingestion, persistence, and presentation layers. By formulating health assessment as a side-effect-free, mathematical mapping from immutable metrics to status states and explanatory diagnostic tokens, systems achieve complete determinism, instant unit-testability, and zero I/O flakiness across CI/CD gates and operational dashboards.

    When to use this

    • Evaluating governance, quality, or architectural health in CI/CD release pipelines where gate decisions must be strictly reproducible and explainable.
    • Synthetic status calculation in real-time dashboards requiring verifiable outputs given the same snapshot of metrics.
    • Complex domain scoring logic where testing currently suffers from mocking databases, external APIs, or file system states.
    • Situations requiring transparent, human-readable diagnostic reasoning (e.g. audit logs, compliance evidence) paired directly with every status transition.

    When NOT to use this

    • Real-time sliding-window stream processing where state accumulation cannot be externalized or partitioned cleanly from evaluation logic.
    • Simple single-metric threshold checks (e.g., standard HTTP liveness probes) where introducing dedicated data-transfer objects and evaluation functions adds unnecessary structural overhead.
    • Environments where telemetry fetching must be dynamically interleaved with evaluation queries via iterative round-trips without pre-materialized metric snapshots.

    Components

    • Pure Health Evaluator (src/cas_runner/dashboard/health_model.py): Houses side-effect-free functions (e.g., calculate_health, get_health_reasons) that consume immutable metric snapshots and yield deterministic status enums and structured diagnostic reasons.
    • Telemetry Snapshot Ingestion (src/cas_runner/telemetry/collector.py): Gathers disparate system observations, architectural signals, and repository metrics, normalizing them into immutable Data Transfer Objects (DTOs) before passing them to the evaluator.
    • Dashboard & Reporting Presenter (src/cas_runner/dashboard/views.py): Translates the evaluator's deterministic HealthStatus outputs and explanation tokens into visual indicators, summary widgets, and remediation checklists.

    Technology choices

    Recommended Technologies

    • Immutable Data Structures: Python @dataclass(frozen=True) or Pydantic V2 models (frozen=True) to enforce boundary immutability across the input snapshot.
    • Type-Safe Enumerations: Standard library Enum (e.g. HealthStatus.GREEN, YELLOW, RED) to prevent invalid state representations.
    • Pure Function Paradigms: Stateless Python functions free of global state, network calls, or clock queries.

    Alternatives Considered & Set Aside

    • Stateful OOP Evaluators with Injected Repositories: Rejected due to tight coupling with database schemas and the requirement to mock I/O during unit testing.
    • External Rules Engines (e.g., Cel, Drools): Rejected due to unnecessary runtime complexity, lack of static type checking, and poor developer ergonomics for Python-native codebases.

    Variants

    Variant 1: Strict Gating Mode

    Optimized for CI/CD gates. The evaluation short-circuits on critical failures, immediately returning a terminal error code and high-severity diagnostic messages to minimize execution time.

    Variant 2: Exhaustive Diagnostic Accumulator

    Optimized for audit dashboards and architecture portals. Evaluates all criteria independently regardless of failures, producing a comprehensive health breakdown with every diagnostic issue categorized by severity.

    Variant 3: Parameterized Ruleset Evaluator

    Accepts dynamic weighting and threshold configurations as a pure argument alongside telemetry metrics, allowing organization-level policy adjustments without modifying algorithmic code.

    Non-functional characteristics

    Reliability

    • Absolute determinism: identical inputs guaranteed to produce identical outputs.
    • Zero flakiness in automated testing since network outages, disk permissions, and database locks cannot affect scoring.

    Performance & Latency

    • In-memory execution delivers sub-millisecond evaluation latencies (< 5ms for standard rule suites).
    • Zero allocation overhead beyond lightweight primitive structures, enabling high-frequency batch executions.

    Cost & Efficiency

    • Extremely low CPU and memory footprints. Can execute locally in Git hooks or serverless evaluation workers without dedicated infrastructure provisioning.

    Operability

    • Reproducing reported production or pipeline anomalies requires only capturing the input snapshot payload and passing it to a local test fixture.

    Anti-patterns & known pitfalls

    Anti-Pattern 1: Hidden I/O Leakage

    • Symptom: Calling external APIs, database drivers, or filesystem checks inside calculate_health.
    • Remedy: Enforce strict architectural boundary checks (e.g., import linters) preventing I/O libraries within evaluator modules. Fetch all inputs beforehand.

    Anti-Pattern 2: Ambient Context Dependence

    • Symptom: Reading datetime.now() or os.environ directly within the evaluation algorithm.
    • Remedy: Pass timestamp snapshots and configuration dictionaries explicitly as functional arguments.

    Anti-Pattern 3: Opaque Status Results

    • Symptom: Returning a naked status code or score without accompanying explanation strings.
    • Remedy: Always return a composite tuple or object containing both the discrete status and an ordered list of machine-readable and human-readable diagnostic reasons.

    Adoption guidance

    Migration Path

    1. Separate Data Fetching from Decision Logic: Audit existing health checks to decouple metric collection queries from threshold evaluations.
    2. Formalize the Snapshot DTO: Create frozen models defining required metrics and audit signals.
    3. Extract Pure Scoring Functions: Move status derivations into a dedicated module (e.g., health_model.py) and write comprehensive parameterized unit tests.
    4. Shadow Validation in CI: Run the pure evaluator alongside existing checks to verify parity before deprecating legacy stateful logic.
