    Reference Architecture: Pure Functional Health Evaluation

    Purpose & when to use this

    The Pure Functional Health Evaluation pattern provides deterministic, side-effect-free derivation of system health status and accompanying diagnostic rationales from immutable telemetry snapshots. By decoupling metric assessment logic from I/O operations (network, disk, or databases), it ensures reproducible scoring and human-readable diagnostic transparency across dashboards, automated release gates, and diagnostic tooling.

    When to use this

    • When diagnostic dashboards or observability consoles require unambiguous, reproducible status classifications (e.g., GREEN, YELLOW, RED) based on pre-collected metric models.
    • When automated release, promotion, or deployment pipelines need deterministic pass/fail gates that produce identical evaluation results given identical metric inputs.
    • When operational diagnostics require human-readable diagnostic explanations (get_health_reasons) bundled directly with state transitions.
    • When building health evaluation logic that must achieve high automated test coverage without complex mocking of persistence or transport layers.

    When NOT to use this

    • When health checks inherently require active, runtime probing or streaming protocols directly coupled to network transport (e.g., active socket polling or streaming ping loops) within the evaluation method itself.
    • When diagnostic decisions must depend on hidden, mutable background state or historical state machine memory maintained internally within the scoring component rather than provided via an input snapshot.
    • When evaluating complex distributed consensus across nodes where consensus resolution requires live cluster negotiation rather than discrete snapshot analysis.

    Components

    • Pure Health Evaluator (src/cas_runner/dashboard/health_model.py): Executes side-effect-free evaluation functions (calculate_health, get_health_reasons) over immutable telemetry structures to generate structured HealthStatus and diagnostic reasoning.
    • Telemetry Ingestion Collector (src/cas_runner/dashboard/): Gathers metrics, logs, and telemetry from external systems or repositories, normalizes them, and produces typed immutable snapshots for evaluation.
    • Diagnostic Dashboard UI & Consumer (src/cas_runner/dashboard/): Consumes evaluation outputs to display status badges, render diagnostic reports, or assert pipeline verification criteria.

    Technology choices

    Recommended Technologies

    • Immutable Data Modeling: Python typed dataclasses (with frozen=True) or pydantic.BaseModel (with frozen=True) to guarantee that metrics passed into the evaluator cannot be altered during execution.
    • Pure Calculation Routines: Stateless Python functions typed with explicit typing.NamedTuple or enumeration outputs (HealthStatus).
    • Declarative Reason Structuring: Explicit string formatting or structured diagnostic objects (HealthReason) mapping metric boundaries to transparent explanations.

    Alternatives Considered & Set Aside

    • Stateful Domain Models: Encapsulating evaluation logic inside long-lived OOP service instances holding internal metric caches was rejected due to risk of hidden state mutations and test pollution.
    • Integrated I/O Evaluators: Performing database queries or HTTP lookups directly inside health evaluation functions was rejected because it introduces network instability, non-determinism, and heavy mocking overhead in test suites.

    Variants

    • Synchronous Batch Evaluation: Direct invocation during dashboard compilation or web request handling where pre-fetched metric sets are evaluated in-memory within microsecond latencies.
    • Automated CI/CD Promotion Gate: Integration into build and release pipelines where compiled artifact metadata and static test results are evaluated deterministically to produce binary pass/fail deployment decisions.
    • Weighted Multi-Dimensional Evaluation: An extended variant where distinct sub-system evaluation vectors (e.g., security, test coverage, static analysis) are evaluated through independent pure functions and aggregated via weighted functional compositions.

    Non-functional characteristics

    • Reliability: High determinism guarantees identical status ratings and diagnostic reasoning for identical inputs. Enables 100% test coverage without mock dependencies.
    • Performance & Latency: Sub-millisecond execution times as all logic is in-memory and rule-based without blocking I/O calls.
    • Cost & Efficiency: Negligible compute footprint; easily executed within constrained environments like serverless functions and pre-commit hooks.
    • Operability: Transparent, human-readable reason strings accelerate incident triage and eliminate ambiguity in alert states.

    Anti-patterns & known pitfalls

    • Hidden I/O Side Effects: Infiltrating logging I/O, database queries, or external network calls into calculation routines. Remedy: Strict adherence to Functional Core, Imperative Shell patterns.
    • Wall-Clock Time Leakage: Invoking datetime.now() directly within evaluation logic, causing test flakiness. Remedy: Pass the reference evaluation timestamp inside the input snapshot.
    • Cryptic Health Scores: Outputting raw scores or booleans without diagnostic justification. Remedy: Always emit structured human-readable reasons alongside status classifications.

    Adoption guidance

    Migration Path

    1. Separate Metric Collection from Evaluation: Refactor existing stateful health monitors into two stages: an imperative metrics fetcher and a pure calculation function.
    2. Formalize Domain Models: Implement typed, frozen data structures for metrics inputs, health status enums, and diagnostic reason models.
    3. Isolate Logic in Test Suites: Transition test suites to feed synthetic metric snapshots into pure functions, validating threshold boundary cases without mocking.
