    Reference Architecture: Deterministic Context Grounding via Git-Delta Fact Ingestion

    Purpose & when to use this

    When to use this

    Use this pattern when you need to provide LLM agents with accurate, verifiable context about code changes in a CI/CD or development environment. It is particularly valuable when: - Agents must reason about recent commits, merge requests, or diffs without hallucinating details. - Raw Git diffs are too large, noisy, or unstructured for direct prompt injection. - You need a typed, queryable fact store of repository changes for later analysis or audit. - You want to ensure that any context shown to an LLM is strictly traceable to version-controlled data.

    When NOT to use this

    Do not use this pattern when: - You are working with non-repository data sources (e.g., unstructured documents, external APIs) that cannot be represented as Git deltas. - The overhead of parsing and validating every Git change is not justified for your use case (e.g., trivial scripting tasks). - Real-time, low-latency responses are required and the delay of delta ingestion is unacceptable. - Your agents must handle hypothetical or speculative scenarios where historical Git data is not the appropriate grounding mechanism.

    The flow starts with the Git repository as the source of truth. Changes are ingested, validated into PromptFacts, stored in the index, and later used to build grounded prompts for LLMs. The diagram uses standard container and store styling.

    Components

    • Git Delta Ingestor (src/cas_runner/steering/ingestors.py): Monitors Git repositories for new commits, branches, and merge requests. Extracts raw git delta information (files changed, diffs, metadata) and normalizes it into RawGitDelta structures.
    • Prompt Fact Validator (src/cas_runner/steering/validators.py): Takes RawGitDelta inputs and applies validation rules to ensure only meaningful, well-formed changes are retained. Produces PromptFact records containing typed metadata such as change type, impact summary, and relevant code paths.
    • Steering Runtime Index (src/cas_runner/steering/index.py): Persists and indexes validated PromptFact records in a queryable store. Supports time-based retrieval, deduplication, and efficient lookup of facts for a given commit, branch, or time window. Acts as the single source of truth for context grounding.
    • LLM Context Builder (src/cas_runner/steering/context_builder.py): Queries the Steering Runtime Index to gather relevant PromptFacts for a given agent task. Formats the facts into a compact, token-efficient prompt with references to the originating Git deltas, ensuring the agent receives only verified information.

    Technology choices

    Recommended technology stack: - Language: Python 3.11+ (already used in project) - Git interaction: gitpython or pygit2 for repository access and diff extraction - Data validation: Pydantic v2 for defining RawGitDelta, PromptFact, and related models - Storage: SQLite for lightweight local indexing, or PostgreSQL if distributed/scale-out required. Redis can be used as an in-memory cache for high-frequency queries. - LLM integration: LangChain or plain HTTP calls; prompt builder uses token-aware templating (e.g., tiktoken or transformers tokenizer).

    Alternatives considered and set aside: - Apache Spark / big-data processing: Overkill for typical repository sizes; adds operational complexity. - NoSQL document stores: Not needed since data is strongly relational and indexed by commit/branch. - Custom binary format: Avoided; JSON/UTF-8 keeps compatibility with LLM tokenization and debugging.

    Variants

    The pattern can be executed in several modes: - Synchronous inline ingestion: Git deltas are processed immediately when a commit is detected, and facts are stored before the agent runs. Provides the strongest consistency but increases latency in the CI pipeline. - Asynchronous background ingestion: Deltas are queued and processed by a worker pool. The agent may see slightly stale facts but achieves lower pipeline latency. - Strict validation mode: Only changes that pass all validation rules are included; any uncertain change is dropped. Guarantees high fact integrity but may omit useful context. - Fallback mode (lenient): Unvalidated deltas are included with an explicit confidence field set to low, allowing LLM to reason with caveats. Useful in exploratory scenarios. - Event-driven vs. poll-based: Git webhooks can trigger ingestion, or a cron-based poller can be used where webhooks are unavailable.

    Non-functional characteristics

    Reliability: - PromptFact records are immutable once written; updates create new versions with lineage to the Git commit. - The Steam Runtime Index is backed by a durable store with ACID transactions (SQLite/PostgreSQL). - If ingestion fails, the system retries with exponential backoff; failures are logged and alerted.

    Performance & Latency: - Typical ingestion of a single commit (few files) completes in under 200ms. - Query latency for building a prompt context is under 50ms for indexes containing up to 100k facts. - The total added latency to a CI pipeline is typically <1 second, acceptable for most workflows.

    Cost & Efficiency: - Storage footprint is proportional to number of commits; archived and pruned via retention policies (e.g., keep 30 days or last N commits). - Token usage is minimized by compact fact formatting; only relevant diffs are summarized, reducing LLM invocation costs.

    Operability: - All components are implemented as Python modules with clear interfaces, unit-testable in isolation. - Deployment can be as a standalone service (CLI/daemon) or embedded in existing CI runners. - Metrics are exported via Prometheus (ingestion rate, validation failures, index size) and logs are structured for ELK/Splunk.

    Anti-patterns & known pitfalls

    1. Dumping raw diffs into prompts: Avoid feeding entire git diff output to LLMs. This bloats context and increases hallucination risk.
    2. Remedy: Always use validated PromptFact records with concise summaries.
    3. Skipping validation: If you ingest every raw delta without checking, you may propagate file noise, binary diffs, or secrets.
    4. Remedy: Implement strict validation including file-type filtering, size limits, and secret scanning.
    5. Tight coupling to Git internals: Relying on specific Git command outputs (e.g., git log --format strings) makes the pattern brittle to Git version changes.
    6. Remedy: Use a well-tested library (GitPython) and abstract the Git interaction behind a repository interface.
    7. Over-indexing every minor change: Storing facts for every typo-fix commit can bloat the index.
    8. Remedy: Define a minimum significance level (e.g., at least one line added/modified, or file extension filter).
    9. Ignoring merge conflicts and rebases: Deltas from merged branches may be misleading.
    10. Remedy: Normalize to the final state of the commit chain; resolve conflicts before ingestion.

    Adoption guidance

    Starting point: - Begin by instrumenting the existing src/cas_runner/steering/models.py to define your own PromptFact schema (or reuse the existing one). - Implement a minimal Git Delta Ingestor using GitPython to read commits from a test repository and print raw deltas. - Once you have the data pipeline, add a simple SteeringRuntimeIndex using SQLite for persistence. - Integrate with a sample LLM call to show the value of grounded context in a toy scenario.

    Migration path: - If you already have a monolithic context builder that injects raw Git data, replace it in stages: first add the ingestion layer, then the index, and finally switch the prompt builder to use the index. - For projects using existing CI steps, add a dedicated job to run ingestion before any LLM-dependent analysis jobs.

    Governance ownership: - Domain: intelligence - Initiative: steering-projection-init - Owner: Architecture Team (architecture@ideas-to-life.example.com) - Review cadence: quarterly, aligned with ADR review cycles.
