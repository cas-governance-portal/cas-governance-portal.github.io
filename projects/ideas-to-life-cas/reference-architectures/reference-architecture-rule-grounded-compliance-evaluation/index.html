    Reference Architecture: Rule-Grounded Compliance Evaluation

    Purpose & when to use this

    This pattern enables continuous, automated evaluation of code and architectural deltas against codified organizational standards before they are merged. It transforms architectural governance from infrequent human reviews into a scalable, deterministic gate enforced within CI/CD pipelines. The pattern introduces a dedicated compliance evaluation engine that parses diffs, matches them to rule contexts, and emits structured findings that can be used to block or flag changes.

    When to use this

    • When you need to enforce architectural standards (e.g., layer boundaries, dependency rules, naming conventions, forbidden patterns) consistently across multiple teams and repositories.
    • When human architectural review is a bottleneck to deployment velocity and you want to provide fast, actionable feedback to developers.
    • When you have a machine-readable, versioned rule set that can be expressed as logical conditions against code delta metadata (file paths, language constructs, dependency graphs).
    • When compliance signals must be integrated into automated workflows (CI, pre-merge checks, audit trails).
    • When you want to capture compliance metrics over time for governance dashboards and trend analysis.

    When NOT to use this

    • For purely semantic or design-level compliance that requires human judgment and cannot be reliably encoded as deterministic rules (e.g., evaluating the elegance of a solution or the appropriateness of an architectural pattern in context).
    • When the rule set is volatile and not yet codified; investing in automation prematurely will lead to high maintenance overhead.
    • When your delta source is too coarse or unreliable (e.g., missing context for full evaluation, or when diffs are too large to map to rules without heavy preprocessing).
    • When the organizational culture is not ready for automated gates and prefers human oversight as the primary review mechanism; this pattern can be introduced gradually but requires trust in the rule engine.
    • In environments with extremely short-lived branches where full delta analysis is impractical and rule evaluation adds meaningful overhead.

    Components

    Delta Extractor

    • Path: src/cas_runner/governance/delta_extractor.py
    • Responsibility: Parses the incoming commit or pull request to isolate the changed files and relevant structural metadata (additions, modifications, deletions). Produces a normalized delta object that the Compliance Engine can consume.

    Compliance Engine

    • Path: src/cas_runner/governance/compliance_engine.py
    • Responsibility: Core evaluation component. Loads applicable rule contexts from the Rules Repository, applies them to the normalized delta, and generates a set of ComplianceFinding objects. Aggregates findings into ComplianceMetrics (e.g., total violations, severity distribution, pass/fail status).

    Rules Repository

    • Path: config/rules/
    • Responsibility: Versioned storage of codified architectural rules. Each rule context contains conditions, violation severity, and remediation guidance. Rules are expressed in a declarative, machine-readable format (e.g., YAML or JSON) and are versioned to allow evolution of standards.

    Findings Store

    • Path: data/compliance_findings/
    • Responsibility: Persists ComplianceFinding and ComplianceMetrics records for historical tracking, audit, and analytics. Enables trend analysis and enforcement of compliance gates over time.

    Report Generator

    • Path: src/cas_runner/governance/report_generator.py
    • Responsibility: Transforms raw findings into human- and machine-readable reports (e.g., Markdown summaries, SARIF, or inline comments). Provides the interface to the external PR system and dashboards.

    Technology choices

    Recommended stack is Python 3.11+ for the orchestrator and rule engine, using PyYAML for rule parsing and JSON for findings serialization. The CI integration uses GitHub Actions or GitLab CI to trigger the engine on pull_request events. For rule evaluation, a lightweight expression evaluator (e.g., a safe subset of Python or JSONPath) is used to match file paths, annotations, and dependency patterns. Alternatives considered and set aside: using ESLint or Pylint plugins proved too limiting for architectural-level rules; using a full OPA (Open Policy Agent) engine adds stronger policy capabilities but introduces a heavier operational dependency and requires a separate deployment. For persistence, SQLite or PostgreSQL is acceptable; MongoDB was considered but lacks the relational integrity needed for metrics aggregation. The findings store should be kept schema-light to facilitate integration with reporting tools.

    Variants

    The pattern can be executed in a purely advisory (non-blocking) mode where findings are reported but do not fail the build, or in a strict gate mode where any rule violation of a certain severity blocks the merge. The engine can run synchronously within the CI pipeline for immediate feedback, or asynchronously as a background job with results posted as status checks. Rule contexts can be centralized (one repository for all standards) or federated per-domain/team, with precedence merging. Another variant uses delta-level caching to only evaluate changed files against relevant rules, reducing execution time. Finally, the rule engine can support a dry-run mode for rule developers to test new rules against historical deltas before promoting them to enforcement.

    Non-functional characteristics

    • Reliability: The engine must be deterministic and idempotent; the same input delta and rule version must always produce the same outcome. It should be resilient to malformed inputs and rule execution errors, with a fail-closed policy for critical rules and fail-open for non-critical.
    • Performance: For a typical PR with hundreds of changed files, evaluation should complete in under 10 seconds. Rule evaluation is I/O-bound on rule loading and delta parsing; caching of compiled rules and deltas is essential.
    • Cost & Efficiency: Operational cost is low because the engine runs as a lightweight CI step; the major cost is rule authoring and maintenance. Infrastructure requirements are minimal if using a managed CI runner.
    • Operability: The engine should emit structured logs, export metrics (e.g., evaluation time, rule execution count), and support graceful degradation if the Rules Repository is unavailable (e.g., using a cached snapshot). It must be easy to update rules without code changes, and the report output must be traceable to the exact rule and delta.

    Anti-patterns & known pitfalls

    1. Rule over-engineering: Trying to capture every possible deviation leads to an unmaintainable rule set. Avoid this by starting with a small, high-value set and expanding based on observed failures.
    2. Misuse of delta granularity: Evaluating the entire repository rather than the delta causes slow and noisy results; always scope to changes.
    3. Ignoring rule context: Rules that operate on file paths without understanding architectural intent (e.g., module boundaries) produce many false positives. Ensure rules reference the architectural model.
    4. Making the engine a bottleneck: Synchronous evaluation on every commit can slow the pipeline; use incremental checks and consider splitting evaluation into fast and deep stages.
    5. Neglecting rule versioning: Mutating rules in place breaks historical traceability. Version rules and tie findings to the specific rule version.
    6. Security exposure: Rules may invoke unsafe expressions; sanitize all external inputs and limit rule capabilities to a safe subset.

    Adoption guidance

    Start by identifying 3-5 high-impact architectural rules that are currently violated frequently. Codify them in the Rules Repository and run the engine in advisory mode on a single repository to build a baseline. Once the rule set is stable and the noise level is acceptable, enable the gate for critical rules and then expand to all governed repositories. Establish a governance owner (domain_id: 'ideas-to-life-cas', initiative_id: 'governance-modernization') responsible for rule lifecycle and conflict resolution. Link rule adoption to the architecture decision records (ADRs) that define the standards. Provide developer onboarding by exposing rule documentation and remediation examples directly in the report output.
