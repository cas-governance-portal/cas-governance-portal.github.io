    Reference Architecture: Rule-Grounded Compliance Evaluation

    Purpose & when to use this

    This pattern provides a systematic, automated approach to evaluating code and architectural deltas against codified rule sets, generating structured compliance findings and metrics. It is designed to integrate into CI/CD pipelines to enforce organizational standards before merge.

    When to use this

    • You need to continuously verify that repository changes conform to architectural and coding standards.
    • Human architectural review is a bottleneck and slowing down deployment velocity.
    • You have a growing codebase with multiple teams and need consistent governance.
    • You require deterministic, auditable compliance checks that produce structured output for dashboards and reporting.
    • You want to capture institutional knowledge in machine-readable rules that evolve with your architecture.

    When NOT to use this

    • For purely syntactic linting that can be handled by established linters (e.g., ESLint, Pylint) without architectural context.
    • When rules are highly subjective and cannot be codified without losing nuance.
    • When the team lacks the discipline to maintain the rule repository, leading to staleness.
    • In prototypes or short-lived experiments where overhead outweighs benefits.

    The workflow starts with a code delta (e.g., from a pull request). The CI pipeline triggers the ComplianceEngine, which loads the appropriate rule contexts from the rule store. It evaluates the delta against the rules, producing structured findings and composite metrics. These results are then used to generate a report and make a pass/fail decision, feeding back into the CI pipeline.

    Components

    ComplianceEngine

    The core engine that coordinates the evaluation. It takes a diff, applies rule contexts, and returns structured results. It is implemented in src/cas_runner/governance/compliance_engine.py. Its responsibilities include: - Extracting changed files and content from the git diff. - Loading and parsing rule definitions. - Matching rules to code patterns and evaluating conditions. - Aggregating findings into metrics. - Emitting results in a structured format (e.g., JSON).

    RuleContexts

    A collection of rule definitions stored in a versioned repository (typically YAML files). Each rule specifies: - ID: Unique identifier (e.g., ARC-001). - Description: Human-readable explanation. - Applicability: Conditions under which the rule applies (e.g., file types, directories). - Severity: Error, warning, info. - Pattern: Regex or logical expression to match. - Action: How to interpret a match (e.g., prohibit, require).

    Rules are loaded dynamically by the ComplianceEngine, allowing updates without changing engine code.

    ComplianceFinding

    An individual data object representing a single non-compliance event. It is defined in src/cas_runner/governance/models.py using Pydantic. Fields include: - rule_id - file_path - line_start, line_end - message - severity - context (optional metadata)

    ComplianceMetrics

    Aggregated output summarizing the compliance status. It typically includes: - total_findings - critical_findings - pass_rate - status (pass/warn/fail) - evaluation_timestamp

    This can be serialized to JSON for dashboards and further processing.

    CI Integration

    An integration layer that plugs the engine into the CI pipeline. This is typically a GitHub Actions workflow that runs on pull requests. It orchestrates the engine, captures its output, and decides whether to pass or fail the check. It can also post comments with findings to the PR.

    Technology choices

    • Python 3.10+: Chosen for its simplicity, robust standard library, and excellent support for code analysis (e.g., ast, git subprocess).
    • Pydantic v2: Used for data models to ensure type safety and easy JSON serialization.
    • YAML: For rule definitions—human-readable, easy to review, and supports comments.
    • Git CLI: For extracting diffs, using subprocess to avoid additional dependencies.
    • GitHub Actions: As the CI orchestrator, given the project is hosted on GitHub.

    Alternatives considered: - SonarQube: Comprehensive but heavy, complex to configure, and not tailored to architectural rules. - ESLint with custom plugins: Good for JavaScript but not language-agnostic. - Open Policy Agent (OPA): Offers general policy evaluation but requires a different data model and has a steeper learning curve.

    Variants

    1. Synchronous vs Asynchronous: In CI, the pattern runs synchronously to provide immediate feedback. For large codebases, it could run asynchronously via a message queue to avoid blocking the pipeline, though this delays feedback.
    2. Strict vs Advisory: The report can be configured to fail the build (strict) or merely warn (advisory) initially, allowing gradual adoption before enforcement.
    3. Scoped vs Full: The evaluation can be scoped to only changed files or run against the entire codebase, with trade-offs between speed and completeness.
    4. Centralized vs Distributed Rules: Rules can be stored in a single governance repo or distributed across repositories, but centralization simplifies versioning and consistency.
    5. Rule Versioning: Rules may be versioned with semantic versioning to support migrations and compatibility with older codebases.

    Non-functional characteristics

    Reliability: The pattern is deterministic—given the same input and rule set, it produces identical results. It integrates with CI and provides clear pass/fail signals. However, it depends on the quality and currency of the rule set; stale rules can cause false confidence or noise. Performance & Latency: Evaluation is typically fast (milliseconds to seconds) for moderate codebases. Performance scales linearly with the number of rules and changed files. Diff analysis reduces workload compared to full scans. In CI, the overhead is acceptable compared to other build steps. Cost & Efficiency: Minimal operational cost—no additional infrastructure beyond the CI runner. Rule maintenance is the primary ongoing cost, but it can be shared across teams. The pattern reduces human review time, making it cost-efficient in the long term. Operability: The system is simple to operate: rules are in version control, results are logged and stored. It can emit metrics to monitoring systems. The main challenge is keeping rules up-to-date and managing rule proliferation.

    Anti-patterns & known pitfalls

    1. Rule Explosion: Continuously adding rules without pruning leads to a massive rule repository that is hard to manage and consumes excessive compute. Remedy: Regularly review rules, remove obsolete ones, and consolidate overlapping checks.
    2. Hardcoded Rules: Embedding rules directly in the engine code prevents dynamic updates and makes testing difficult. Remedy: Keep rules as external data files (YAML/JSON) with schema validation.
    3. Ignoring Findings: Producing findings but not acting on them diminishes trust and allows violations to persist. Remedy: Implement a clear escalation path and require sign-off for waived findings.
    4. Over-reliance on Automation: Relying solely on automated rules without human oversight for architectural intent can miss emerging design patterns or out-of-scope changes. Remedy: Combine with periodic architectural reviews and allow human override mechanism with audit trail.
    5. Rule Staleness: Rules become outdated as architecture evolves, causing false positives or missed issues. Remedy: Assign a rule owner and review them along with architecture decision records (ADRs).

    Adoption guidance

    Starting Point: Begin with a small set of high-value rules (e.g., prohibited dependencies, naming conventions, required architecture layers). Integrate the ComplianceEngine into the CI pipeline for a single repository and run in advisory mode to collect feedback. Migration Path: Once the rule set stabilizes and teams agree on outcomes, switch to strict mode. Gradually expand coverage to more rules and more repositories. Establish a governance board to own the rule repository and review changes. Governance Ownership: Assign domain_id to the architecture governance domain and initiative_id to the current project (e.g., 'ideas-to-life-cas'). The principal architect or a nominated technical lead should act as owner (contact: architect@example.com). Coordinate with ADR owners to align rules with documented decisions.
