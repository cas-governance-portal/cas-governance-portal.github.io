    Reference Architecture: Rule-Grounded Compliance Evaluation

    Purpose & when to use this

    The Rule-Grounded Compliance Evaluation pattern provides automated, deterministic, and machine-readable architectural governance for codebases by verifying pull request deltas against codified rule repositories. Traditional architectural review processes rely heavily on manual human inspection or subjective LLM-as-a-judge evaluations, leading to deployment bottlenecks and inconsistent policy enforcement. This pattern codifies organizational architecture standards and domain boundary rules into machine-enforceable definitions, parsing repository deltas to evaluate violations and yield structured compliance metrics.

    When to use this

    • Automated pull request gating: When enforcing domain boundaries, module layering, dependency constraints, or API specifications in continuous integration pipelines.
    • Verifiable audit trails: When enterprise governance mandates reproducible, machine-readable records of compliance posture across release branches.
    • Large-scale monorepos: When cross-team architectural drift occurs frequently due to decoupled development teams modifying shared boundaries.
    • Mitigating subjective LLM drift: When introducing AI-assisted evaluations where model judgments must be strictly anchored to authoritative ground-truth rules rather than generic prompt intuition.

    When NOT to use this

    • Micro-repositories with trivial domain boundaries: Where standard compiler flags or baseline linters (e.g., flake8, eslint) provide exhaustive coverage without custom architectural logic.
    • Dynamic behavioral runtime testing: When verifying system performance, latency, or integration faults under load (utilize integration test suites or synthetic transaction monitors instead).
    • Exploratory prototyping phases: When architecture is intentionally volatile and rapid experimentation precedes the crystallization of domain contracts.

    Components

    • ComplianceEngine (src/cas_runner/governance/compliance_engine.py): Ingests repository diffs (RawGitDelta), applies matching rules, and coordinates static and semantic analyzers against file changes.
    • Compliance Models (src/cas_runner/governance/models.py): Houses data definitions including ComplianceFinding (capturing violation details, file coordinates, and rule IDs) and ComplianceMetrics (composite score computation).
    • Rule Knowledge Repository (cas-knowledge/rules/): Declarative rule context definitions outlining boundary constraints, forbidden imports, and mandatory architectural patterns.
    • CI Pipeline Runner (.github/workflows/cas-build-validation.yml): Pipeline orchestration layer invoking the evaluation engine on pull request triggers and reporting gate outcomes.

    Technology choices

    • Pydantic v2: Enforces strict typing and serialization for compliance entities and findings.
    • Structured Rule Formats (YAML/JSON): Retains declarative, version-controlled architecture policies. Alternative set aside: Hardcoded code checks, which prevent centralized updates and cross-repository sharing.
    • AST Analysis Engines: Employs structural AST parsing over brittle regex-only scanning.
    • Targeted Model Contexts: Restricts LLM evaluation to localized diff snippets with explicit rule context prompts, setting aside Full-file Prompt LLM Judges to prevent high cost and hallucinations.

    Variants

    • Strict Blocking Gate: Fails CI pipelines on any critical violation, preventing merge.
    • Passive Audit & Telemetry: Scans main release branches periodically to track architectural drift trends without interrupting developer workflows.
    • Hybrid Static-Semantic Evaluation: Runs zero-cost AST checks first, deferring only ambiguous semantic cases to model-guided evaluators.

    Non-functional characteristics

    • Reliability: Eliminates subjective review variance by grounding checks in concrete rule sets.
    • Performance & Latency: Optimizes pipeline execution by restricting analysis to git diff hunks (< 5 seconds for standard PRs).
    • Cost & Efficiency: Minimizes token usage by filtering candidates statically before invoking LLMs.
    • Operability: Produces industry-standard SARIF/JSON outputs compatible with common CI/CD dashboard tools.

    Anti-patterns & known pitfalls

    • Unbounded LLM Judge: Relying on generic model prompts without concrete rule references. Remedy: Bind every evaluation to an explicit rule context file.
    • Rule Bloat & Stagnation: Accumulating dead rules that trigger false alarms. Remedy: Enforce rule versioning and deprecation reviews.
    • All-or-Nothing Merge Blocking: Blocking merges on informational style notes. Remedy: Strict tiering between error (blocking) and warning / info (advisory).

    Adoption guidance

    1. Starting Point: Identify 3-5 critical structural boundaries in the system and author them as declarative rules in cas-knowledge.
    2. Migration Path: Deploy in passive reporting mode to measure accuracy and calibrate false-positive rates before turning on blocking gates in CI.
