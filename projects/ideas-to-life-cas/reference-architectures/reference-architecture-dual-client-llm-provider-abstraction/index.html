    Reference Architecture: Dual-Client LLM Provider Abstraction

    Purpose & when to use this

    Provides a swappable, unified abstraction layer over upstream Large Language Model (LLM) providers coupled with an in-process offline mock client. This isolates core agentic orchestration logic from vendor-specific SDK quirks, minimizes execution costs, and guarantees deterministic offline CI/CD pipeline execution.

    When to use this

    • When building agentic or LLM-backed applications that require automated CI/CD validation without incurring external API costs, latency, or rate-limiting flakes.
    • When business applications require multi-model agility, such as dynamically routing between OpenAI, Anthropic, Bedrock, or self-hosted models without rewriting orchestration logic.
    • When unit and integration test suites require deterministic, reproducible LLM outputs and pre-canned responses.
    • When runtime telemetry, token-usage auditing, and fallback routing must be standardized across all upstream model providers.

    When NOT to use this

    • When building lightweight single-turn CLI utilities or throwaway prototypes that communicate with only one specific vendor API and do not require comprehensive automated testing.
    • When leveraging high-level end-to-end framework runtimes (e.g., proprietary copilot platforms) that natively enforce proprietary client adapters and do not allow client swapping.
    • When evaluating complex multi-modal or real-time streaming behaviors that cannot be effectively represented or validated via offline mock doubles.

    Components

    • LLM Base Interface / Client Factory (src/cas_runner/llm/factory.py): Defines the abstract interface (e.g., generate, astream, embed) and dynamically instantiates either the production client or mock client based on runtime configuration.
    • Production Provider Client (LiteLLMClient) (src/cas_runner/llm/litellm_client.py): Translates standard application invocation schemas into provider-specific requests via LiteLLM; handles retries, latency instrumentation, and multi-vendor credentials.
    • Offline Mock Client Double (MockLLMClient) (src/cas_runner/llm/mock_client.py): Simulates model responses using deterministic fixtures, records all invocation payloads and tokens for assertion testing, and enforces zero network dependency during local runs and CI.
    • Agent Flow Orchestrator (FlowRunner) (src/cas_runner/runner.py): Executes domain workflows and agent graphs purely against the abstracted LLM client contract without knowledge of the underlying model endpoint.

    Technology choices

    Selected Technologies

    • Unified Provider Gateway (litellm >= 1.83.14): Acts as the single dependency for routing calls to OpenAI, Anthropic, Bedrock, and Azure OpenAI using an OpenAI-compatible interface.
    • Rationale: Eliminates the need to maintain multiple vendor SDKs (e.g., openai, anthropic, boto3) and provides normalized output, error mapping, and token counting.
    • In-Memory Mock Test Double (MockLLMClient): Python-based class implementing the shared client abstract protocol with customizable canned responses and in-memory call logs.
    • Rationale: Yields sub-millisecond execution speeds for unit tests, eliminates network flakiness, and prevents accidental billable token consumption.

    Alternatives Considered

    • Direct Vendor SDKs: Direct integration with separate openai and anthropic clients.
    • Reason Set Aside: High maintenance burden, API divergence across SDK versions, and high vendor lock-in.
    • Network Replay Tooling (e.g., vcrpy, HTTP recorded tapes):
    • Reason Set Aside: Recorded HTTP tapes quickly become brittle when request serialization shifts slightly, leak API tokens if not scrubbed meticulously, and are difficult to synthesize for new negative test cases.

    Variants

    1. Offline Deterministic Variant (CI & Unit Testing)

    • The factory defaults to MockLLMClient initialized with predefined JSON response fixtures or structured schema generators.
    • Operates with strict assertions: any missing fixture triggers an explicit test failure rather than attempting network access.

    2. Multi-Provider Production Gateway Variant

    • The factory initializes LiteLLMClient with structured environment parameters.
    • Supports multi-tier model cascading and fallback routing (e.g., fallback from primary provider to secondary upon HTTP 429/500 errors).

    3. Record-and-Replay Hybrid Variant

    • LiteLLMClient wraps calls with an interceptor that can record successful production payloads to fixture files, which are subsequently loaded by MockLLMClient to refresh stale test fixtures.

    Non-functional characteristics

    Reliability

    • Fault Isolation: Agent business logic is protected from remote provider outages, network transients, and API schema shifts.
    • Deterministic Testing: Eliminates non-deterministic test failures caused by LLM hallucinations or remote provider latency variations.

    Performance & Latency

    • Test Execution Speed: Mock double reduces test execution time from seconds per call to sub-millisecond execution, enabling hundreds of workflow iterations in standard CI runs.
    • Production Overhead: LiteLLM introduces negligible CPU overhead (< 2ms) relative to model inference times.

    Cost & Resource Efficiency

    • Zero CI Spend: Completely eliminates token consumption and egress network costs in automated pull request validation.
    • Cost Observability: Standardized LiteLLM completion responses provide uniform token usage counts across heterogeneous providers for cost tracking.

    Operability & Governance

    • Unified Observability: Metrics, spans, and prompt token counts are exported through OpenTelemetry at the abstraction boundary.
    • Credential Hygiene: API keys are isolated within production environment scopes; developer workstations and CI runners require no LLM provider credentials.

    Anti-patterns & known pitfalls

    1. Mock Drift Anti-Pattern

    • Symptom: Mock clients returning schemas that are no longer aligned with updated upstream model response signatures or updated system prompts.
    • Remedy: Implement a scheduled integration smoke test that executes a minimal golden-path prompt against both LiteLLMClient and MockLLMClient to validate parity.

    2. Leaky Vendor Primitives Anti-Pattern

    • Symptom: Domain agents importing provider-specific response exceptions (e.g., openai.RateLimitError) rather than catching an abstracted LLMProviderError.
    • Remedy: Enforce strict error wrapping inside LiteLLMClient and enforce via linting rules forbidding vendor imports outside src/cas_runner/llm/.

    3. Untested Mock Paths Anti-Pattern

    • Symptom: Code branches developed exclusively against mocks without ever verifying prompt tokens or rate limits against real models until production deployment.
    • Remedy: Introduce a dedicated staging integration suite run on pre-release branches that exercises LiteLLMClient against live sandboxes.

    Adoption guidance

    Migration Path

    1. Phase 1 (Abstract Interface): Extract the common LLM call boundary from current workflow components into an abstract protocol or base class.
    2. Phase 2 (Implement Clients): Encapsulate existing live provider logic in LiteLLMClient and construct MockLLMClient with deterministic dictionary lookup responses.
    3. Phase 3 (Inject Client via Factory): Refactor agent entry points (e.g., FlowRunner) to accept the LLM client instance via dependency injection.
    4. Phase 4 (CI Isolation): Enforce USE_MOCK_LLM=true across all continuous integration pipelines and remove vendor API keys from CI environment secrets.
