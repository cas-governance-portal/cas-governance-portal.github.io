    Reference Architecture: File-Backed Knowledge Repository

    Purpose & when to use this

    The File-Backed Knowledge Repository pattern establishes a decentralized, transparent, and auditable blackboard architecture by persisting architectural, operational, and governance artifacts directly as structured files (Markdown, YAML, JSON) inside standard Git repositories.

    When to use this

    • When distributed software agents and human engineers must collaborate, peer-review, and evolve architectural designs, decisions (ADRs), and compliance policies using familiar pull-request workflows.
    • When governance, configuration, and architectural metadata need cryptographically verifiable version history, branching, and atomic commit semantics without introducing external database dependencies.
    • When bootstrapping developer tools, CLIs, or localized runtime runners that must function offline or in air-gapped CI/CD environments with zero relational database friction.
    • When artifacts must be human-readable, portable across disparate operating platforms, and immune to proprietary database vendor lock-in.

    When NOT to use this

    • When data access patterns demand high-frequency, millisecond-latency concurrent transactional updates (ACID transaction volume > 50 writes/sec), which would cause extreme Git merge conflicts and lock contention.
    • When datasets contain sensitive runtime secrets, highly dynamic telemetry streams, or high-volume ephemeral session state.
    • When deep relational graph querying, multi-table joins, or sub-millisecond full-text indexed searches across millions of entities are required without an intermediary indexing cache.

    Components

    • Knowledge Repository Store (cas-knowledge/): Root file-backed store hosting global governance policies, project configurations, ADRs, and runtime state in structured Markdown, YAML, and JSON files.
    • Workspace Bootstrapper (src/cas_runner/bootstrap.py): Provides deterministic scaffolding, template extraction, and initialization of local workspace governance files against centralized reference definitions.
    • Governance Block Merge Engine (src/cas_runner/bootstrap.py:merge_cas_governance_block): Performs idempotent updates, schema preservation, and block-level reconciliation between active workspace definitions and upstream template specifications.
    • Audit and Schema Verifier (.github/workflows/knowledge-audit.yml): Continuous integration verification layer that enforces structural schema constraints and linting on committed repository artifacts.

    Technology choices

    Adopted Technologies

    • Git Version Control: Native versioning engine providing immutability, cryptographic commit hashing, peer-review branching models, and decentralized synchronization without database infrastructure.
    • Structured Serialization (YAML, JSON, Frontmatter Markdown): Balances human readability with strict machine parsability via standard JSON Schema and Pydantic models.
    • Python (Standard Library & PyYAML): Lightweight bootstrapping and synchronization scripts without heavy external ORM or database client dependencies.

    Considered & Set Aside

    • Relational Databases (PostgreSQL): Rejected due to infrastructure deployment overhead, lack of native decentralized branching, and friction in developer PR review cycles.
    • Headless CMS / NoSQL (MongoDB, Contentful): Rejected to prevent vendor lock-in, recurring operational hosting costs, and network-boundary dependencies during local developer execution.
    • Wiki Systems (Confluence): Rejected due to weak schema validation, lack of programmatic API parity with developer IDEs, and absence of branch-merge auditability.

    Variants

    1. In-Repo Colocated Knowledge Store

    Knowledge artifacts reside directly within the application codebase (./knowledge/ or ./cas-knowledge/). Best suited for single-repository systems where code changes and architectural updates must be committed atomically in the same pull request.

    2. Centralized Multi-Repo Knowledge Hub

    A standalone Git repository acts as an enterprise-wide blackboard. Downstream application repositories mount or synchronize templates via Git subtrees, submodules, or CLI synchronization utilities (cas_runner/bootstrap.py).

    3. Read-Through Memory-Cached Repository

    Runtime services clone the Git repository into an in-memory or localized RocksDB/SQLite index at startup. Read operations bypass disk parsing while writes persist back through standard Git commit workflows.

    Non-functional characteristics

    Reliability

    • Highly resilient to data loss due to decentralized distributed replication inherent to Git.
    • Every checkout functions as a complete snapshot backup. Fault recovery involves simple commit checkouts or branch restores.

    Performance & Latency

    • Read Latency: Sub-millisecond localized disk I/O when read directly from SSD storage or cached into memory.
    • Write Latency: Higher latency (100ms - 2000ms) during Git commit, rebase, and push operations; acceptable for governance events but unsuited for high-throughput transactional logging.

    Cost & Efficiency

    • Near-zero recurring infrastructure operational costs. Relies on commodity cloud repository hosting (GitHub, GitLab) or local developer file systems.
    • Eliminates the need for managed database instances, continuous database patching, and persistent connection pool management.

    Operability & Governance

    • Native operational visibility using standard Git tools (git log, git diff, git blame).
    • Full cryptographic provenance and change ownership tracked across all governance artifacts.

    Anti-patterns & known pitfalls

    1. The High-Frequency Transaction Log Pitfall

    • Anti-pattern: Attempting to record real-time agent execution telemetry or per-event logs as separate Git commits.
    • Pitfall: Git object databases inflate rapidly, creating lock contention (index.lock) and merge collisions.
    • Remedy: Stream operational telemetry to disk-based JSON Lines files excluded by .gitignore or forward to external log aggregators; retain Git strictly for milestone state and governance declarations.

    2. Free-Form Unstructured Documentation

    • Anti-pattern: Writing arbitrary, unvalidated markdown files without consistent metadata schemas.
    • Pitfall: Downstream tools and automated agent pipelines fail to parse disparate architectural assertions.
    • Remedy: Enforce JSON schema validation over YAML frontmatter in CI gates before commits are merged.

    3. Unresolved Concurrent Merge Contention

    • Anti-pattern: Multiple distributed runners writing simultaneously to a single shared remote tracking branch without locking or automated rebasing.
    • Pitfall: Push rejections and fractured commit histories.
    • Remedy: Implement isolated working branches per agent run or use idempotent block-merging logic as provided in merge_cas_governance_block.

    Adoption guidance

    Starting Point

    1. Establish a root cas-knowledge/ directory in the repository to store architectural decisions, pattern catalogs, and team conventions.
    2. Adopt the workspace bootstrap utility (src/cas_runner/bootstrap.py) to scaffold initial configuration files and register local project templates.
    3. Integrate schema validation in pre-commit hooks or continuous integration pipelines to lint JSON/YAML frontmatter.

    Migration Path

    • Phase 1: Move scattered wiki pages and ad-hoc architecture documentation into /docs/adr and /cas-knowledge.
    • Phase 2: Introduce automated CLI utilities (cas-runner) to parse repository artifacts during local build and test execution.
    • Phase 3: Connect CI validation workflows to verify that architectural specifications align with codebase implementations.
