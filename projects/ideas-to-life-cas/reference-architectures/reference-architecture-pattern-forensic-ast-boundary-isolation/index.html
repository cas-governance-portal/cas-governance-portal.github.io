    Reference Architecture: Forensic AST Boundary Isolation

    Purpose & when to use this

    Forensic AST Boundary Isolation establishes strict architectural and execution decoupling between target codebase source files and the static analysis governance runner frameworks that evaluate them. When inspecting code for conformance, dependencies, or architectural compliance, governance tools frequently ingest abstract syntax trees (ASTs) or perform reflection. Without formal boundary isolation, runner libraries, harness dependencies, and governance runtime frameworks bleed into target AST symbols, yielding false positive policy breaches or contaminated dependency graphs.

    When to use this

    • Automated architecture governance pipelines that parse target repository codebases to extract static dependency topologies, module boundaries, or import graphs.
    • Polyglot or multi-version codebases where the analysis engine runs in a specific runtime (e.g., Node.js or Python) but must accurately evaluate external target source trees without confusing runtime environment packages with repository dependencies.
    • High-compliance forensic audits where target repository symbols and call sites must maintain cryptographic or verifiable provenance free from test runner or runner harness artifacts.

    When NOT to use this

    • Lightweight linters (e.g., standard ESLint, Flake8) executing within native runtime processes where runner isolation overhead exceeds static linting requirements.
    • Dynamic runtime profiling or agent-based instrumentation where the target application must purposefully link against telemetry or APM harnesses at runtime.
    • Monolithic codebases evaluated solely through compiler-native toolchains without custom governance extractors.

    Components

    • Runner Orchestrator (governance/runner/orchestrator): Initiates the analysis session, enforces container- or process-level isolation boundaries, and provides clean mounting of the target codebase without injecting governance dependencies into the target path.
    • Isolated AST Sandbox (governance/sandbox/ast_boundary): Executes out-of-process language parsers within an unprivileged execution context, filtering host environment variables, module resolution search paths, and synthetic wrappers.
    • Empirical Discovery Engine (governance/discovery/extractor): Extracts structural symbols, module imports, and architectural boundary markers, ensuring all detected nodes originate solely within target repository boundaries.
    • Target Repository FS (/mnt/target_repo): Read-only filesystem mount containing raw target repository source files, configuration manifests, and project-level lockfiles.
    • Forensic Graph Evidence Store (governance/storage/evidence): Immutable persistence store holding verified AST extraction evidence schemas and verified relationship records.

    Technology choices

    Selected Technology Stack: - Language-Agnostic Tree-Sitter Bindings: Chosen for AST parsing over language-native eval/reflection mechanisms (e.g., Python ast module or Babel parser run directly in runner context). Tree-sitter produces concrete syntax trees without invoking the language's native runtime loader, eliminating ambient path resolution bugs. - Ephemeral Process Sandboxing (Rootless Linux Containers / namespaces): Isolates file resolution and ensures runner libraries cannot be traversed during AST node graph building.

    Alternatives Considered and Set Aside: - Native Dynamic Module Loader / Reflection: Rejected due to frequent symbol contamination, namespace collisions with runner utility packages, and security risks associated with loading untrusted target code. - Universal Regex / Heuristic Scanning: Set aside due to high false-positive rates with complex syntax, multi-line declarations, and scoped namespace aliases.

    Variants

    • Strict Out-of-Process Sandbox: Executes Tree-sitter parsers inside isolated child processes with dedicated memory spaces and restricted filesystem views. Ideal for CI/CD runners analyzing untrusted code or complex monorepos.
    • Language Daemon IPC Boundary: Employs dedicated long-running language server daemons (LSP) across local Unix domain sockets to parse target ASTs, maximizing throughput when scanning high-churn multi-project repositories while preserving strict memory isolation.

    Non-functional characteristics

    • Reliability: Eliminates governance pipeline flakiness and false-positive policy rejections triggered by runner harness dependencies leaking into discovery scans.
    • Performance & Latency: Introduces minimal overhead (~5-15% increase compared to in-process parsing) due to IPC boundary context switches, mitigated by streaming AST chunks.
    • Cost & Efficiency: Low memory footprint; unprivileged sandbox worker pools scale down to zero when analysis phases complete.
    • Operability: Yields clean, reproducible evidence trees with source mapping hash checks, simplifying forensic debugging and audit tracking.

    Anti-patterns & known pitfalls

    • Ambient Classpath / Node Module Leaking: Allowing the runner harness's node_modules or PYTHONPATH to overlay the target repository's search path, causing the AST extractor to identify governance packages as target dependencies. Remedy: Mount target code in a scrubbed execution environment with blank module search paths.
    • In-Process Reflection: Invoking require() or importlib.import_module() on target components inside the governance runner context to introspect structure. Remedy: Parse syntax trees statically without evaluating runtime imports.
    • Single-Pass Monolithic Parser: Reusing a single parser state across disparate subprojects without purging scope caches between microservice modules in a monorepo. Remedy: Instantiate fresh sandbox worker contexts per bounded context or workspace.

    Adoption guidance

    Starting Points & Migration Path

    1. Phase 1 (Audit): Audit existing architectural governance extractors to catalog runner dependencies present in scanner lockfiles.
    2. Phase 2 (Decoupling): Refactor AST parsing calls to run via isolated CLI workers or out-of-process Tree-sitter bindings, passing file paths via explicit read-only mounts.
    3. Phase 3 (Verification): Introduce verification assertion assertions in CI to reject any extracted AST evidence containing runner-scoped packages.
