    Reference Architecture: Architecture Work Registry as Authoritative Backlog

    Purpose & when to use this

    The Architecture Work Registry pattern establishes persistent, version-controlled architecture backlog artifacts as the authoritative single source of truth for planning, technical debt tracking, and strategic milestones. It cleanly separates durable architectural planning state from volatile, automated downstream synthesis runs, treating artifacts like Architecture Evolution Maps (AEM) and alignment summaries as disposable, reproducible projections.

    When to use this

    • Automated pipelines or generative agents regularly synthesize architecture reports, debt views, and compliance summaries that risk overwriting manually recorded planning state.
    • Teams operate continuous architecture lifecycles requiring bi-directional auditability between high-level architectural proposals and implementation tasks.
    • Governance demands that architectural intent, decisions, and debt mitigation tracking persist directly in Git alongside codebase repositories.
    • Multiple downstream visualization tools (e.g., roadmaps, dashboards, alignment matrices) need consistent, structured input without becoming silos of uncommitted planning state.

    When NOT to use this

    • Small, single-developer projects or short-lived prototypes where ad-hoc issue tracking suffices without formalized architectural lifecycles.
    • Organizations where corporate planning is strictly centralized and legally bound to monolithic enterprise issue trackers that reject Git-backed flat-file synchronization.
    • Scenarios where architectural analysis is performed purely ad-hoc with zero automated generation or reporting workflows.

    Components

    • Architecture Work Registry (governance/architecture-work/): The authoritative store for all architectural backlog items, work packages, debt remediations, and strategic milestones, committed as structured, schema-validated files in Git.
    • Synthesis & Generation Pipeline (tools/synthesis-engine/): Automated engine executed during CI/CD or local analysis cycles. Ingests registry records, cross-references actual code components, and validates governance compliance.
    • Architecture Evolution Map Projection (docs/architecture/evolution-map.md): A generated, disposable visual and tabular view depicting roadmap progress, component lifecycles, and dependency states.
    • External Task Tracker Adapter (integrations/tracker-adapter/): An optional integration bridge synchronizing Git-backed work items with engineering task boards (e.g., Jira, Linear, GitHub Issues) to maintain developer alignment.

    Technology choices

    • Git Version Control: Canonical source of record. Pull request workflows provide mandatory governance reviews, cryptographically verifiable commit history, and zero-drift alignment with application code.
    • Schema-Enforced Formats (YAML/JSON Schema Draft-07): Work items must follow standardized schemas to enable machine parsing, static validation, and reliable projection synthesis.
    • Projections as Ephemeral Artifacts: Markdown and SVG projections are automatically derived; manual changes to projections are prevented or flagged via pre-commit and CI assertions.

    Alternatives Considered and Set Aside

    • Direct Jira/Issue Tracker Authoritative Backlog: Rejected because issue trackers live outside git commit history, diverge easily across branches, and suffer from manual schema drift.
    • Static Wiki/Confluence Documentation: Rejected due to chronic out-of-date documentation, lack of automated validation against code changes, and absence of pull-request gating.

    Variants

    • Colocated Monorepo: Work items live in the application repository under governance/architecture-work/. Best for cross-functional single teams owning full-stack services.
    • Federated Enterprise Registry: Work items are maintained in a dedicated architecture repository with automated sync submodules across microservice repositories.
    • Projection Guard Mode: CI pipeline runs in verification mode; if generated projections differ from checked-in projections, the pull request fails, forcing developers to regenerate artifacts from the registry.

    Non-functional characteristics

    • Reliability: Guarantees zero state loss across pipeline iterations. Automated generation processes can crash or wipe target output folders without sacrificing architectural work records.
    • Performance & Latency: Processing dozens of YAML records takes under 500ms; downstream generation runs seamlessly in standard pre-commit hooks and CI pipelines.
    • Cost & Efficiency: Eliminates redundant SaaS enterprise planning licensing fees for architectural tracking while lowering synchronization overhead.
    • Operability: Architecture changes are reviewed using standard code review tooling (e.g., GitHub PRs, GitLab MRs) with zero proprietary administrative burden.

    Anti-patterns & known pitfalls

    • Modifying Generated Projections Directly: Developers or architects edit the generated Markdown roadmap instead of updating the backing architecture work YAML item, resulting in loss of changes on subsequent builds. Remedy: Insert prominent generation warnings in generated files and validate via CI.
    • Unvalidated Work Records: Backlog records created without strict schema enforcement quickly suffer from missing fields, broken identifiers, and ambiguous statuses. Remedy: Use schema validation tools (e.g., ajv or yamale) in pre-commit hooks.
    • Decoupled Task Execution: Architecture items are maintained in Git but not mapped to sprint backlogs, leading to ignored architectural directives. Remedy: Use automated webhooks or issue adapters to bridge registry records to team sprint boards.

    Adoption guidance

    1. Establish Schema and Registry Root: Create governance/architecture-work/ and establish architecture-work.schema.json.
    2. Capture Ongoing Initiatives: Ingest current technical debt items and planned migrations (such as aw-ideas-to-life-cas-2026-05-31-001) into structured files.
    3. Integrate Generation Pipeline: Hook projection generation into local scripts and CI builds, directing outputs to generated doc directories.
    4. Governance Assignment: Assign governance oversight to platform architecture leads or designated project stewards.
