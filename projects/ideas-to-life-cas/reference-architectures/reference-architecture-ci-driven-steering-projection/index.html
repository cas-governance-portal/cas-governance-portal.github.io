    Reference Architecture: CI-Driven Steering Projection

    Purpose & when to use this

    The CI-Driven Steering Projection pattern synchronizes evolving repository facts into actionable prompt context and steering models for autonomous developer agents. By anchoring synchronization directly within continuous integration workflows, architectural facts derived from Git deltas are compiled deterministically and projected into downstream developer prompts and documentation without running continuous background daemons.

    When to use this

    • Codebases where developer agent prompts or architectural context drift rapidly from the underlying implementation.
    • Multi-contributor engineering teams requiring synchronized steering documentation without imposing manual governance overhead on every PR.
    • Environments requiring strict governance boundaries where architecture projections must be proposed via pull requests rather than destructive direct mutations.
    • Organizations seeking to optimize developer tool costs by utilizing ephemeral CI compute over 24/7 background agent services.

    When NOT to use this

    • Monolithic repositories without automated CI pipelines or with severe CI runner resource constraints.
    • Ultra-low latency interactive coding workflows where developers require instant cross-workspace feedback in sub-second intervals.
    • Unstructured or prototype codebases lacking defined module boundaries, AST stability, or architectural conventions.

    Components

    • CI Projection Runner (.github/workflows/cas-build-steering-projection.yml): Orchestrates execution triggers on repository events, provides ephemeral isolation, and manages permission scopes for projection generation.
    • Continuous Architecture Pipeline (.github/workflows/cas-continuous-architecture.yml): Triggers architectural analysis, governance validation, and boundary verification across active pull requests.
    • Steering Projection Engine (steering/models.py): Defines domain structures, validates architectural delta facts, and renders machine-readable prompt additions for local developer agents.
    • Delta Fact Extractor (steering/extractors.py): Analyzes Git diffs, AST structures, and metadata deltas between commits to extract immutable architectural facts.

    Technology choices

    • Continuous Integration Environment: GitHub Actions was selected for deep integration with repository lifecycle events, secret management, and ephemeral runtime isolation.
    • Deterministic Delta Extraction: Python standard AST libraries combined with Git plumbing commands provide fast, deterministic discovery of boundary shifts.
    • Schema-Enforced Modeling: Pydantic models in steering/models.py guarantee structural integrity before publishing prompt facts.
    • Alternatives Set Aside: Continuous indexing background daemons were rejected due to idle operational costs, high failure surface area, and branch desynchronization risks. Direct commit strategies were rejected to prevent bypass of peer review controls.

    Variants

    • Proposal Pull-Request Variant: Automatically submits a governance pull request with compiled markdown facts and steering updates whenever architectural changes exceed predefined drift metrics.
    • Ephemeral Artifact Packaging: Generates localized context bundles uploaded as CI artifacts, consumed directly by developer IDE plugins without branch pollution.
    • Pre-Merge Enforcement Variant: Operates as a required status check that validates developer additions against known steering contracts, failing the build on invariant breaches.

    Non-functional characteristics

    • Reliability: Employs deterministic parsing and pinned Git references to ensure projection generation is idempotent and reproducible across environments.
    • Performance & Latency: Focuses solely on commit deltas rather than complete repository re-indexes, completing pipeline stages in under 60 seconds.
    • Cost & Efficiency: Eliminates dedicated agent server infrastructure by executing purely on on-demand CI build allocations.
    • Operability: Emits standard GitHub status outputs, step summaries, and structured diffs accessible directly within the pull request experience.

    Anti-patterns & known pitfalls

    • Direct Branch Mutation: Allowing the CI workflow to push changes directly into trunk branches. Remedy: Enforce branch protection rules and route all projection updates through pull-request proposals.
    • Prompt Context Bloat: Over-indexing irrelevant internal implementation details into agent prompt bundles, leading to developer fatigue and agent distraction. Remedy: Restrict steering projections to structural boundaries, exported interfaces, and explicit architectural facts.
    • Stochastic Ingestion: Relying on generative models to determine baseline architectural changes. Remedy: Ground fact extraction in deterministic AST parsers and structured Git diff tools.

    Adoption guidance

    1. Baseline Ingestion: Introduce the extraction scripts into existing CI pipelines to build steering projection artifacts on push events.
    2. Review Integration: Enable the proposal pull-request mechanism with designated CODEOWNERS reviews to validate proposed architectural steering updates.
    3. Agent Consumption: Point local developer agents and prompt orchestrators to the compiled steering projections.
    4. Governance Ownership: Enterprise Architecture & Developer Experience teams.
