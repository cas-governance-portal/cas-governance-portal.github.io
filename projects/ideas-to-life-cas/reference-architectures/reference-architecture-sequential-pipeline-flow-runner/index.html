    Reference Architecture: Sequential Pipeline Flow Runner

    Purpose & when to use this

    The Sequential Pipeline Flow Runner coordinates multi-stage architectural assessment, synthesis, and verification tasks through deterministic, ordered step execution with structured context propagation.

    When to use this

    • When coordinating multi-stage workflows (e.g., assess -> plan -> specify -> implement -> verify) where each downstream phase strictly depends on the validated artifacts of preceding stages.
    • When running autonomous or semi-autonomous agentic workloads where unbounded self-looping must be prevented to avoid runaway token expenditures and non-deterministic behavior.
    • When pipeline runs must provide deterministic audit trails, step-level timing, and stage-by-stage state persistence for CI/CD or local CLI environments.

    When NOT to use this

    • When execution graphs require dynamic runtime branching, complex cycle graphs, or arbitrary iterative loops driven by open-ended agent deliberation.
    • When processing highly parallelized, high-throughput event streams that require distributed pub/sub or event-choreographed architectures.
    • When simple monolithic single-function scripts suffice and the orchestration overhead of context accumulation and step registries provides no operational advantage.

    Components

    • CLI Invoker Entrypoint (src/cas_runner/cli.py): Parses user parameters and configuration flags, initializes runtime context, and invokes FlowRunner execution pipelines.
    • FlowRunner Orchestrator (src/cas_runner/runner.py): Coordinates the ordered execution of registered workflow steps, tracks stage transitions, handles runtime exceptions, and enforces stop-on-failure contracts.
    • Step Registry (src/cas_runner/runner.py): Maintains discovered flow declarations and step bindings, resolving executable handlers and enforcing step interface compliance.
    • Execution Context Store (src/cas_runner/runner.py): Accumulates strongly typed state and metadata across steps, enabling downstream stages to access upstream deliverables deterministically.
    • Step Handlers (src/cas_runner/steps/): Executes domain-specific operations (analysis, code synthesis, schema validation, linting) taking immutable context inputs and yielding structured outputs.

    Technology choices

    The primary implementation utilizes Python 3.11+ using standard typed dataclasses/Pydantic schemas for execution context, paired with CLI entrypoints built using standard argument parsing libraries (such as Click or argparse).

    Alternatives Considered & Set Aside

    • Distributed workflow orchestrators (e.g., Temporal, Apache Airflow): Set aside as overly heavyweight for embedded CLI and direct CI/CD invocation where zero external infrastructure dependencies are required.
    • Event-driven choreography (e.g., AWS Step Functions, Kafka): Set aside due to high operational complexity and lack of immediate local developer feedback loops.
    • Graph-based autonomous agent frameworks (e.g., LangGraph, AutoGen): Set aside for the core runner backbone due to non-deterministic execution loops, high token budget variance, and lack of deterministic step gate verification.

    Variants

    • Synchronous Fail-Fast (Default): Stops execution immediately upon any step failure, raising a detailed diagnostic trace to prevent corrupted downstream side effects.
    • Checkpointed Resumable Runner: Persists context snapshots to local disk or cache after each step, permitting pipeline resumption from the last successful checkpoint.
    • Dry-Run / Plan Runner: Traverses the step registry without invoking mutations or external APIs, generating an execution plan and input/output contract verification report.

    Non-functional characteristics

    • Reliability: Guaranteed deterministic step ordering with isolated failure domains; unhandled step errors safely halt the pipeline without corrupting baseline project state.
    • Performance & Latency: Microsecond context propagation overhead between steps within a single process; pipeline latency is strictly bounded by individual step I/O or LLM response times.
    • Cost & Efficiency: Eliminates runaway agent loops and repeated prompt evaluations by establishing bounded, single-pass step transitions.
    • Operability: Structured step timing, execution status telemetry, and centralized logging provide transparent auditing across CI/CD and developer workstation environments.

    Anti-patterns & known pitfalls

    • Context Monolith Anti-Pattern: Accumulating unvalidated, untyped global state in the context dictionary without clear schema ownership between steps. Remedy: Enforce typed Pydantic or dataclass contracts for step inputs and outputs.
    • Hidden Autonomous Re-entry: Embedding unbounded recursive agent loops inside a single step handler, negating the runner's guardrails. Remedy: Bound agent retries to a strictly configured iteration ceiling with explicit failure exits.
    • Out-of-Band State Mutation: Step handlers mutating disk state or global variables without reporting outcomes back into the pipeline context. Remedy: Treat disk mutations as side effects that register their generated paths explicitly into the context.

    Adoption guidance

    Adopt this pattern by defining an explicit Step interface requiring execute(context: FlowContext) -> StepResult. Refactor sequential scripts into isolated step classes and register them in FlowRunner. - Starting Point: Review src/cas_runner/runner.py and implement discrete steps for workflow assessment and validation before generation. - Governance & Ownership: Platform Architecture Team (domain_id: platform-core, initiative_id: pipeline-orchestration). Contract changes to runner step interfaces require semantic versioning.
