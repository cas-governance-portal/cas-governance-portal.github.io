    Reference Architecture: Sequential Pipeline Flow Runner

    Purpose & when to use this

    The Sequential Pipeline Flow Runner pattern provides a deterministic, ordered execution lifecycle for multi-stage agentic workflows. It addresses the architectural need to coordinate a sequence of dependent analysis, generation, and governance steps through a central orchestrator that passes a shared execution context forward. This pattern is foundational for any system where the output of one stage is a mandatory input for the next, ensuring predictable flow, auditability, and controlled error handling.

    When to use this

    • When the workflow must execute in a fixed, well-defined order (e.g., ingestion → transformation → validation → output).
    • When each step requires data produced by its predecessor, and a shared context object is convenient for passing state.
    • When you need centralised control over error handling, retries, logging, and observability across the entire pipeline.
    • When you anticipate adding, removing, or reordering stages over time and want to do so without rewriting the orchestration logic.
    • When deterministic execution is required for compliance, governance, or reproducibility (e.g., audits, traceability).

    When NOT to use this

    • When workflow stages are fully independent and can run concurrently; consider a fan-out/fan-in or event-driven architecture instead.
    • When the order is not strictly important or when dynamic branching based on runtime data is required; a workflow engine with advanced routing (e.g., BPMN, AWS Step Functions) might be more appropriate.
    • When stages must be executed asynchronously over long time periods with human intervention mid-flight; a state machine or saga pattern would be more suitable.
    • When the pipeline is extremely simple (two steps) and the overhead of a dedicated runner is unjustified; direct function calls or a simple script may suffice.
    • When you need to support arbitrary user-defined pipelines at runtime without code changes; consider a rule engine or plugin architecture instead.

    Overview

    The Sequential Pipeline Flow Runner sits at the core of the CAS system, orchestrating a series of stages from data ingestion through generation to governance evaluation. The runner controls the lifecycle, passing a shared context object between stages. The following diagram illustrates the container-level architecture:

    The runner and stages are containerised components; the context store is a data store holding the execution state. The CLI is the entry point, but in principle any caller can invoke the runner programmatically.

    Components

    Component Path Responsibility
    FlowRunner src/cas_runner/runner.py Central orchestrator that defines the pipeline stages, manages execution order, injects shared context, and handles error propagation. It coordinates the lifecycle of each stage, ensuring proper handoff of results and capturing metrics for monitoring.
    CLI src/cas_runner/cli.py Command-line entry point that initiates the FlowRunner. Parses user arguments, configures environment, and triggers execution. It also handles early validation of inputs and formats final output or errors.
    Stage Interface src/cas_runner/stage.py Defines the contract for pipeline stages (e.g., execute(context) method). Enables pluggable implementation of stages and ensures consistent input/output handling.
    Context Store src/cas_runner/context.py Provides a thread-safe, serializable container for passing shared state between stages. Supports read/write operations and maintains separation from the external environment to avoid unintended coupling.
    Stage Implementations src/cas_runner/stages/ Concrete pipeline stages such as diff extraction, steering projection, and compliance evaluation. Each implements the Stage Interface and focuses on its single responsibility, relying on the context for inputs and outputs.

    The interfaces between components are intentionally simple: the runner holds a list of stage objects; each stage receives a context object and may mutate it. This design promotes testability and allows stages to be developed independently.

    Technology choices

    The pattern is language-agnostic but has been implemented in Python 3.11+ using standard libraries. Core choices include:

    • Python – chosen for readability, rich ecosystem, and strong typing support via typing and dataclasses. Alternatives like Node.js or Go were rejected due to existing codebase synergy and team expertise.
    • Click for CLI construction – provides declarative argument parsing, easy testing, and automatic help generation. Alternative: argparse (too low-level) or typer (accepted but Click is more established in enterprise).
    • Pydantic for context validation and schema enforcement – ensures data integrity across stages and reduces subtle bugs. Alternative: manual validation or dataclasses alone (set aside due to lack of validation error clarity).
    • Structured logging (Python logging with JSON formatter) – enables machine-parseable logs for observability. Alternative: loguru (simpler but less standard for audit trails).
    • Unit testing with pytest – chosen for robust test discovery and fixtures. Alternative: unittest (less readable).
    • Mermaid for documentation – not a runtime dependency, but used to generate consistent architecture diagrams in Markdown.

    All alternatives considered and set aside are documented in ADR-001 and ADR-004.

    Variants

    The Sequential Pipeline Flow Runner can be adapted to different operational modes:

    1. Synchronous vs. Asynchronous Execution – In synchronous mode, each stage blocks until completion; asynchronous mode uses asyncio or a task queue to allow overlapping I/O operations while preserving ordering via barriers. The choice depends on stage latency and need for resource utilization.
    2. Strict vs. Fallback Behaviour – In strict mode, a stage failure aborts the entire pipeline; in fallback mode, a stage can catch specific exceptions and substitute a default or skip to the next stage. Fallback is useful for non-critical stages but must be carefully designed to avoid cascading corruption.
    3. Single vs. Multi-Context – For pipelines that operate on multiple independent items (e.g., batch processing), the runner can either process items sequentially with one context per item, or use a shared context with per-item sections. The latter reduces overhead but requires careful concurrency control.
    4. Dynamic Stage Composition – Instead of a hardcoded list, pipelines can be defined via configuration (YAML/JSON) allowing different environments to run different stage combinations without code changes. This is a lightweight alternative to workflow engines.
    5. Checkpointing – The runner can persist context after each stage so that a failed run can be resumed from the last successful checkpoint. This variant reduces waste in long-running pipelines.

    Non-functional characteristics

    Reliability

    • Fault isolation: Each stage is sandboxed via the Stage Interface; a failure in one stage does not corrupt others if exceptions are handled appropriately.
    • Idempotency: Stages can be designed to be idempotent, allowing safe retries. The context store supports versioning to detect partial writes.
    • Graceful degradation: Fallback variants allow non-critical stages to degrade without losing the whole pipeline.
    • Recovery: Context checkpoints enable resume-from-failure, reducing the cost of transient errors.

    Performance & Latency

    • Overhead: The runner introduces minimal overhead (~1-5%) compared to direct function calls, mainly from context serialization and validation.
    • Scalability: Synchronous execution has inherently low concurrency; for high throughput, asynchronous or multi-process variants should be used. The runner can be horizontally scaled by deploying multiple instances behind a load balancer if stages are stateless.
    • Predictable latency: Since the flow is sequential, the end-to-end latency is the sum of stage latencies. This is deterministic and easier to budget than branching workflows.
    • Resource usage: Memory consumption grows with the size of the shared context; for large payloads, consider using a message broker or external store to persist context data rather than in-memory objects.

    Cost & Efficiency

    • Compute cost: Minimal overhead; the main cost is stage execution. Using efficient algorithms and avoiding unnecessary serialization reduces cost.
    • Operational cost: Simple architecture reduces monitoring complexity and maintenance overhead. No additional infrastructure beyond the runtime is required.
    • Resource optimisation: For batch processing, batching multiple items into a single context can reduce the number of invocations and thus cost.

    Operability

    • Observability: Built-in logging and metrics hooks allow easy integration with monitoring systems (e.g., Prometheus). Each stage can emit events with correlation IDs.
    • Debugging: The sequential nature simplifies tracing; logs can be correlated by a single run ID.
    • Deployment: The runner can be packaged as a CLI or as a library. CI/CD integration is trivial.
    • Governance: The explicit ordering and context handoff make it easy to audit the process for compliance. Versioned pipelines allow reproducible runs.

    Anti-patterns & known pitfalls

    1. Hardcoding stage order in business logic – Embedding the pipeline sequence in the code of stages reduces flexibility and makes changes risky. Remedy: Use a declarative pipeline definition (e.g., list of stage names) in a configuration file, or at least a constant array in the runner.

    2. Tight coupling between stages – If stages directly instantiate other stages or call their methods, the pipeline becomes brittle. Remedy: Enforce the Stage Interface and force all communication through the shared context.

    3. Ignoring context immutability – Mutating context fields arbitrarily leads to race conditions and bugs. Remedy: Use immutable context objects or provide explicit transactional update methods with validation.

    4. Swallowing exceptions – Catching too broadly and continuing can mask serious errors, leading to corrupted outputs. Remedy: Fail-fast for critical stages; only catch specific, expected exceptions in fallback variants.

    5. Over-engineering – Adding a full workflow engine (e.g., Airflow) when a simple sequential runner suffices. This adds unnecessary complexity. Remedy: Start with a lightweight runner and evolve only when requirements dictate (e.g., need for parallel branching, human tasks).

    6. Lack of telemetry – Not instrumenting stages makes it impossible to diagnose stuck or slow pipelines. Remedy: Automatically attach timing and status to each stage execution; expose metrics to a time-series database.

    7. State stored outside context – Using global variables or environment variables for shared state violates the pattern and makes testing difficult. Remedy: Always pass state via the context object; inject configuration explicitly.

    8. Not versioning pipeline definitions – When the pipeline order changes, historical runs become unreproducible. Remedy: Version the pipeline configuration and include version metadata in run logs.

    Adoption guidance

    Starting points

    • Understand the current pipeline: Review the stages in src/cas_runner/ and identify any existing manual orchestration that can be simplified.
    • Prototype a minimal FlowRunner: Implement a simple runner with just 2–3 stages to validate the context flow and error handling. Use runner.py as a reference.
    • Reuse existing stage implementations: If you have functions that perform distinct steps, wrap them as Stage objects to quickly compose a pipeline.
    • Leverage the CLI: Use the CLI to test pipelines manually before integrating with other systems.

    Migration path

    1. Identify candidate workflows – Look for any multi-step process in your application that currently executes sequentially (e.g., a bash script or a series of function calls).
    2. Refactor steps into Stage objects – Ensure each step has a clear input/output contract and is independent.
    3. Introduce the FlowRunner – Replace the orchestration logic with a runner that iterates over stage list and feeds context.
    4. Gradually adopt variants – Start with synchronous execution; add async or fallback only when needed.
    5. Instrument and monitor – Add logging and metrics early to catch issues.
