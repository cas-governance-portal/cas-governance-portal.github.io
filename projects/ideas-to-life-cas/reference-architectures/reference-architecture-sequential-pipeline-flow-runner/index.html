    Reference Architecture: Sequential Pipeline Flow Runner

    Purpose & when to use this

    The Sequential Pipeline Flow Runner coordinates multi-stage architectural assessment, generation, and verification workflows through an explicit linear execution orchestrator. By passing an immutable or explicitly updated execution context sequentially between discrete steps, it establishes deterministic stage gates and eliminates uncontrolled agentic looping.

    When to use this

    • Multi-stage agentic or verification workflows requiring strict ordering (e.g., assess -> plan -> specify -> implement -> verify).
    • Systems operating in CI/CD or automated governance pipelines where deterministic exit codes, stage timeouts, and audit traces are mandatory.
    • Complex LLM workflows where unconstrained agent autonomy or self-looping introduces token consumption runaways and non-deterministic state transitions.
    • Workflows where subsequent stages depend strictly on validated intermediate artifacts generated by prior stages.

    When NOT to use this

    • Highly dynamic, exploratory problem-solving tasks requiring non-linear backtracking or open-ended graph traversal.
    • Massively parallel data processing or independent fan-out/fan-in tasks where linear pipeline execution introduces unacceptable latency.
    • Event-driven, low-latency stream processing architectures where stages react asynchronously to independent event streams without shared sequential context.

    Components

    • CLI Entrypoint (src/cas_runner/cli.py): Parses operational parameters, configures logging and environment variables, and delegates execution directly to FlowRunner.
    • FlowRunner Orchestrator (src/cas_runner/runner.py): Manages linear workflow lifecycle, coordinates stage sequencing, enforces step timeouts, monitors failure boundaries, and handles context propagation.
    • Step Registry (src/cas_runner/steps/registry.py): Maintains discovery, registration, and dependency validation for executable pipeline step definitions.
    • Execution Context (src/cas_runner/runner.py): Thread-safe data bag accumulating step outputs, operational metadata, and telemetry across the pipeline lifespan.
    • Discrete Pipeline Steps (src/cas_runner/steps/): Encapsulates isolated units of domain or agentic logic that accept context, invoke LLMs/APIs, and return structured state updates.

    Technology choices

    • Runtime & Language: Python 3.11+ using standard type annotations and dataclasses/Pydantic for strict execution context contracts.
    • Orchestration Model: In-process lightweight sequential runner using explicit Python interfaces for low operational overhead and zero external dependencies in CI/CD runners.
    • Serialization & Context: Pydantic v2 for deterministic serialization, schema enforcement, and JSON export.

    Alternatives Considered and Set Aside: - Temporal / Cadence: Highly resilient for long-running workflows, but rejected due to heavy cluster infrastructure requirements for transient CLI and CI/CD operations. - LangGraph / AutoGen: Dynamic multi-agent routing engines set aside due to non-deterministic execution paths, debug complexity, and risk of unbounded loop execution in automated pipelines. - Apache Airflow / Prefect: Heavy distributed scheduling platforms rejected as over-engineered for synchronous CLI and single-job pipeline execution.

    Variants

    • Fail-Fast Sequential Pipeline: Pipeline execution terminates immediately upon the first step error, preserving the exact context state at failure for forensic debugging.
    • Best-Effort / Continuation Pipeline: Tolerates non-critical step failures (e.g., telemetry reporting, optional linting) by annotating context with warnings and continuing through terminal steps.
    • Checkpointed Pipeline: Persists execution context to disk or object storage between step boundaries, allowing resume capabilities after transient network or environment faults.

    Non-functional characteristics

    • Reliability: High determinism. Eliminates runaway execution loops through explicit stage order and discrete step-level timeouts. Isolated failure boundaries guarantee context capture for post-mortem analysis.
    • Performance & Latency: Minimal orchestration overhead (<5ms between steps). Latency is governed entirely by step execution and LLM inference times. Memory footprint remains small (<100MB resident memory).
    • Cost & Efficiency: Strictly caps LLM token spend by replacing free-form agent self-critique loops with predetermined, bounded invocation steps.
    • Operability: Transparent structured logging (JSON) detailing step execution duration, status codes, and input/output context snapshots, making troubleshooting in CI/CD logs straightforward.

    Anti-patterns & known pitfalls

    • Unbounded Context Accumulation: Appending unpruned raw LLM outputs or large binary files into the shared context, causing subsequent step payload limits and token exhaustion. Remedy: Enforce step contracts with explicit output schemas and store large blobs out-of-band.
    • Cross-Step State Leaks via Global Variables: Steps mutating shared process state or module-level variables instead of using the explicit Execution Context. Remedy: Enforce step execution purity where steps only interact through passed context objects.
    • Hidden Dynamic Branching in Steps: Steps attempting to rewrite the pipeline execution graph during runtime. Remedy: Keep graph definition declarative and static; use conditional step skips based on context flags instead of dynamic topological mutation.

    Adoption guidance

    Starting Points

    1. Define step interface contracts using Pydantic models for inputs and outputs.
    2. Instantiate FlowRunner within a CLI harness and register atomic steps in registry.py.
    3. Implement unit tests asserting that context evolves predictably across mock steps.
