    Reference Architecture: Sequential Pipeline Flow Runner

    Purpose & when to use this

    The Sequential Pipeline Flow Runner pattern provides a deterministic, orchestrated execution backbone for multi-stage agentic workflows where the output of each stage becomes the input for the next. It establishes a predictable lifecycle for operations such as knowledge ingestion, steering generation, and compliance evaluation, ensuring strict ordering and reliable context handoff.

    When to use this

    • When workflow steps have strict dependencies and must execute in a fixed order (e.g., diff extraction → steering projection → governance check).
    • When auditability and deterministic execution are more important than maximum parallelism or dynamic branching.
    • When you need a single, central control mechanism to track progress, handle errors, and provide observability across the pipeline.
    • When building systems that require consistent, reproducible execution across different runs or environments.

    When NOT to use this

    • When steps are independent and could be executed in parallel to reduce latency or improve throughput.
    • When the workflow must adapt dynamically to runtime conditions, requiring flexible branching or conditional execution.
    • When the number of steps is small and a simple script or direct method calls would suffice without the added complexity of a runner abstraction.
    • When the system demands high scalability and the central runner becomes a bottleneck; consider event-driven or choreographed designs instead.

    Overview

    The FlowRunner orchestrates the execution by reading from and writing to the shared context after each stage. The CLI provides the entry point and returns the final result to the user.

    Components

    The following components constitute the pattern:

    • FlowRunner (src/cas_runner/runner.py): Core orchestrator that iterates through a list of stages, invokes them in order, and manages the shared context. It handles errors, logging, and optionally retries.
    • CLI (src/cas_runner/cli.py): Command-line interface that accepts user arguments, creates the initial context, invokes the FlowRunner, and displays the outcome.
    • Diff Extraction (src/cas_runner/stages/diff_extractor.py): The first stage; extracts changes from the input source (e.g., Git diff) and stores them in the context.
    • Steering Generation (src/cas_runner/stages/steering_generator.py): Uses the diff data to generate steering options or recommendations, writing results back to the context.
    • Governance Check (src/cas_runner/stages/governance_checker.py): Final stage; validates the steering output against governance policies and marks the run as compliant or not.
    • Execution Context (src/cas_runner/context.py): A data container (dictionary or JSON store) that holds all intermediate artifacts and metadata. It provides a consistent interface for stages to read/write data.

    Technology choices

    The pattern is implemented in Python, leveraging its simplicity and broad ecosystem. Specific choices:

    • Language: Python 3.9+ for modern typing and dataclasses.
    • CLI Framework: argparse (standard) or Typer (for a more ergonomic CLI). Typer is recommended for better UX and automatic help generation.
    • Context Store: In-memory dict for simplicity; can be extended to use json files or a lightweight DB (e.g., SQLite) for persistence.
    • Logging: Standard logging module to ensure structured, queryable logs.
    • Testing: pytest for unit and integration tests, allowing stage mocking.

    Alternatives considered and set aside: - Apache Airflow / Prefect: Heavyweight, require external services, and introduce network latency; unsuitable for single-machine execution. - Celery with message queues: Overkill for a simple sequential flow; adds complexity and potential ordering issues. - Event-driven microservices: Not needed unless stages are independently deployable and elastic scaling is required; contradicts the strict sequential dependency.

    Variants

    • Synchronous vs Asynchronous: The default is synchronous. An asynchronous variant could be built using asyncio to overlap I/O-bound stages, but careful locking is needed to maintain order.
    • Strict vs Fallback: In strict mode, any failure aborts. Fallback mode could allow skipping non-critical stages but should log and flag governance gaps.
    • Persistence: The context may be persisted to disk after each stage to support recovery and audit. This is invaluable for compliance-heavy workflows.
    • Dynamic Stage Registration: Instead of a hardcoded list, stages can be discovered via a plugin interface (e.g., entry points) to allow third-party extensions.

    Non-functional characteristics

    • Reliability: High — the deterministic order and centralized error handling make failures predictable. Retry logic can be added per stage. The shared context prevents partial state corruption.
    • Performance & Latency: Total latency equals the sum of all stage durations plus minimal overhead. For latency-sensitive applications, parallelize independent stages or consider a streaming model, but this violates the fixed-order requirement. The context in-memory access is fast; persistence adds I/O.
    • Cost & Efficiency: Low operational cost — no additional infrastructure. Compute cost is linearly proportional to the number of stages and their individual resource footprints. Ideal for serverless if stages are independent, but then ordering requires external orchestration.
    • Operability: Excellent — logs from each stage can be correlated with a run ID. The runner can expose metrics (e.g., stage duration, success/failure) to a monitoring system. Deployment is a single container or script; easy to debug by replaying with the same context.

    Anti-patterns & known pitfalls

    • Over-centralization: Avoid making FlowRunner the only way to execute tasks. This can lead to a monolith and a single point of failure. Mitigation: allow stages to be invoked individually for debugging or ad-hoc use.
    • Duplicated orchestration: Teams may create similar runners for different pipelines. Mitigation: extract a common runner library and register stages via configuration.
    • Hardcoded stage order: Changing the order requires code modification. Mitigation: move pipeline definitions to declarative YAML/JSON files that the runner reads.
    • Ignoring errors: Catching and swallowing exceptions can produce incorrect results without indication. Mitigation: propagate errors upward; offer a dry-run mode to preview failures.
    • Context bloat: Storing large datasets in memory can cause performance issues. Mitigation: keep only essential fields in context, and store large artifacts externally with references.

    Adoption guidance

    To adopt this pattern:

    1. Identify your workflow steps: Break down processes into a linear sequence with clear dependencies.
    2. Start small: Implement a minimal runner that executes a list of functions and passes a dict. Use it for a new feature or a refactor of an existing script.
    3. Define stage interfaces: Each stage should accept a context and return a status/result. This makes swapping or adding stages straightforward.
    4. Gradually migrate: Convert existing ad-hoc sequences into stage functions, wrapping them with appropriate error handling and logging.
    5. Configure and extend: Create a pipeline configuration file to specify the order and parameters, allowing non-developers to adjust the flow.
    6. Establish governance: Assign an owner within the domain (as per domain_id and initiative_id). The owner ensures the pattern is followed, reviews stage designs, and maintains the runner core.
    7. Educate the team: Document the pattern in the architecture wiki and conduct a workshop to demonstrate how to add a new stage.

    Migration path: Start with a new, non-critical pipeline. Then incrementally refactor existing flows to use the runner. The pattern is designed to be low-risk and reversible — you can always revert to direct function calls if needed.
