    Reference Architecture: Sequential Pipeline Flow Runner

    Purpose & when to use this

    The Sequential Pipeline Flow Runner coordinates multi-stage agentic analysis, transformation, and generation tasks through an orchestrated linear runner passing a shared execution context. It guarantees deterministic ordering and explicit state propagation, preventing non-deterministic runaway loops.

    When to use this

    • Multi-stage agentic pipelines with strict data dependencies (e.g., repository diff extraction followed by steering projection followed by governance evaluation).
    • Continuous Integration (CI) and build workflows requiring deterministic, reproducible step execution and predictable exit codes.
    • Scenarios where debuggability, low operational complexity, and direct observability outweigh autonomous re-planning.

    When NOT to use this

    • Autonomous goal-directed agents that require dynamic self-directed plan adjustment or non-linear graph traversal.
    • Highly concurrent, asynchronous map-reduce or fan-out workloads where tasks have no sequential dependencies.
    • Interactive conversational agents requiring unpredictable multi-turn conversational branching.

    Components

    • FlowRunner Engine (src/cas_runner/runner.py): Coordinates ordered lifecycle execution, manages shared context propagation, handles step-level exceptions, and aggregates telemetry metrics.
    • CLI Entrypoint (src/cas_runner/cli.py): Parses runtime options, loads pipeline manifests, configures environment context, and triggers the FlowRunner instance.
    • Execution Context (src/cas_runner/runner.py): Maintains intermediate immutable or versioned artifacts, configuration flags, and telemetry metrics shared across sequential steps.
    • Pipeline Step Handlers (src/cas_runner/steps/): Encapsulates modular transformation units (e.g. diff ingestion, prompt synthesis, policy verification) adhering to standard step interfaces.

    Technology choices

    Recommended Technologies

    • In-process Python Control Loop: Uses a lightweight, declarative Python pipeline runner (FlowRunner) to avoid external orchestrator daemon overhead inside short-lived CI containers.
    • Pydantic / TypedDict Shared Context: Provides strong type validation across stage outputs and enforces contracts between pipeline steps.
    • Structured Telemetry (Logging / OpenTelemetry): Captures step execution duration, token expenditure, and error states uniformly.

    Alternatives Considered

    • Autonomous Dynamic Agent Loops (e.g., LangGraph / CrewAI Dynamic Agents): Set aside due to non-deterministic execution paths, higher risk of runaway token consumption, and difficulty reproducing failures in automated verification pipelines.
    • Heavyweight Orchestrators (e.g., Temporal / Apache Airflow): Set aside due to infrastructure overhead and complexity unsuitable for self-contained command-line execution and lightweight CI/CD runner environments.

    Variants

    Fail-Fast Sequential Runner

    Execution terminates immediately upon encountering the first failed step, returning a non-zero exit code. Best suited for gatekeeping operations such as architectural linting or pull request validation.

    Resilient Accumulator Runner

    Execution executes all declared non-dependent diagnostic steps even if a prior non-critical step logs warnings or non-blocking failures. It aggregates all diagnostics in the shared context before emitting a unified report.

    Non-functional characteristics

    Reliability

    • Deterministic step sequence eliminates race conditions and infinite recursive agent execution.
    • Step boundaries provide isolated blast radiuses and clear stack traces upon failure.

    Performance & Latency

    • Minimal orchestration overhead (sub-millisecond handoff between steps in memory).
    • Total runtime is strictly bounded by the sum of individual step durations.

    Cost & Efficiency

    • Deterministic invocations prevent unexpected recursive LLM token consumption.
    • Operates in transient containers without persistent daemon infrastructure costs.

    Operability

    • Predictable CLI exit codes integrate directly with standard CI/CD runners.
    • Standardized context serialization allows local reproduction of CI-encountered failures by reloading context snapshots.

    Anti-patterns & known pitfalls

    The God Context Antipattern

    • Pitfall: Storing all global variables, unchecked payloads, and raw step states inside a single untyped dictionary.
    • Remedy: Enforce strongly typed step inputs and outputs with isolated namespace keys or Pydantic models.

    Hidden Step Branching

    • Pitfall: Steps secretly triggering out-of-band external sub-pipelines or looping internally without notifying the orchestrator.
    • Remedy: Keep steps purely functional; require any control flow branching or repeated execution to be explicitly managed by declared runner policies.

    Silent Failure Suppression

    • Pitfall: Steps catching critical runtime exceptions internally and continuing execution with incomplete context data.
    • Remedy: Step contracts must explicitly return standardized status payloads (SUCCESS, WARNING, FAILED) to let the runner decide fail-fast actions.

    Adoption guidance

    Starting Point

    1. Define your pipeline stages as callable units implementing a common signature: execute(context: ExecutionContext) -> StepResult.
    2. Instantiate FlowRunner in src/cas_runner/runner.py with an explicit list of steps.
    3. Wire the pipeline into a single entrypoint CLI in src/cas_runner/cli.py.

    Migration Path

    • For legacy shell scripts or multi-step action files, wrap each shell script or sub-routine into an isolated step class.
    • Migrate hardcoded outputs into context variables to permit clean testing with mock contexts.
