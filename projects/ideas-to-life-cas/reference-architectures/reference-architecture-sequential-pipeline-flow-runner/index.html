    Reference Architecture: Sequential Pipeline Flow Runner

    Purpose & when to use this

    When to use this

    Use the Sequential Pipeline Flow Runner when you need to coordinate a defined set of multi-stage agentic analysis and generation tasks where the output of each stage is required as input for the next. This pattern is ideal for workflows with predictable step ordering and strong dependencies, such as knowledge ingestion, diff extraction, steering generation, and governance compliance checks. It provides a consistent execution lifecycle, reliable context handoff, and observability across all stages.

    When NOT to use this

    Do not use this pattern when steps are independent and can run in parallel, or when the execution order must be dynamically determined based on real-time conditions. For workflows that require complex branching, event-driven orchestration, or need to scale horizontally per stage, a more flexible workflow engine (e.g., temporal, airflow) or a message-driven architecture is preferable. Also avoid this pattern if you need to support long-running interactive steps or human-in-the-loop decisions that interrupt the deterministic flow.

    Overview

    This pattern provides a structured way to execute a sequence of agentic stages that produce and consume a shared execution context. The FlowRunner is the central coordinator, responsible for instantiating the context, invoking stages in a fixed order, and ensuring data continuity. Each stage is a self-contained unit of work that reads from the context, performs its task (possibly interacting with external systems), and updates the context with its results. The pattern enforces a linear flow, making the pipeline predictable, testable, and easy to reason about.

    Components

    FlowRunner

    Path: src/cas_runner/runner.py Responsibility: Core orchestrator that defines the sequence of stages, manages the shared execution context, and invokes each stage in order. It owns the execution lifecycle and ensures correct handoff of data between stages.

    CLI

    Path: src/cas_runner/cli.py Responsibility: Command-line entry point that accepts user input, configuration, and flags, then instantiates and executes the FlowRunner with the appropriate parameters.

    Shared Context

    Path: src/cas_runner/context.py Responsibility: A mutable container holding all intermediate state, results, and metadata produced and consumed by stages. It is passed to every stage and ensures consistency across the pipeline.

    Diff Extraction Stage

    Path: src/cas_runner/stages/diff_extractor.py Responsibility: Queries the external code repository to extract a diff or change set, validates its structure, and populates the shared context with relevant information.

    Steering Projection Stage

    Path: src/cas_runner/stages/steering_generator.py Responsibility: Reads the diff from shared context, generates a steering or guidance projection using agentic models, and updates the context with the projected outcome.

    Governance Evaluation Stage

    Path: src/cas_runner/stages/governance_checker.py Responsibility: Evaluates the generated steering against governance policies, calls an external governance service if needed, and writes the final results to the state store.

    Technology choices

    Primary language: Python 3.11+ (matches existing codebase). CLI: Typer or Click for robust argument parsing. Configuration: Pydantic for typed settings and context validation. State persistence: JSON lines or SQLite for simple, durable local state. Execution: Plain synchronous Python; no external workflow engine to keep overhead low. Alternatives considered: Apache Airflow (too heavy for single-process execution), Celery (unnecessary distributed complexity), event-driven microservices (overkill for deterministic sequential tasks).

    Variants

    • Synchronous vs. asynchronous: The base pattern runs sequentially in a single thread. For I/O-bound stages, an async variant using asyncio can be used, but the stage order remains strictly sequential.
    • Retry and fallback modes: Each stage can be wrapped with retry logic (e.g., exponential backoff) and a fallback handler to skip or substitute results if a stage fails.
    • Configurable stage chain: The sequence of stages can be defined via a configuration file (e.g., YAML) instead of hardcoded, enabling reuse across different workflows.
    • Checkpointing: A variant persists the shared context after each stage to allow resumption from a failed stage, increasing robustness for long-running pipelines.

    Non-functional characteristics

    Reliability: The deterministic ordering and explicit context handoff minimize hidden dependencies and make failures reproducible. Error handling is centralized in the FlowRunner, allowing consistent recovery strategies.

    Performance & Latency: Sequential execution inherently adds latency proportional to the number of stages. For typical multi-stage analysis (e.g., diff extraction, generation, compliance), total latency is acceptable (seconds to minutes). Overhead of context serialization is minimal if kept in-memory.

    Cost & Efficiency: Low operational cost because there is no need for additional infrastructure or distributed systems. The pattern runs in a single process, using minimal resources. Compute is only used when stages are active.

    Operability: Excellent observability because each stage can log its inputs/outputs. The FlowRunner can expose structured logs and metrics (e.g., stage duration, context size). Simple to trace and debug due to linear execution.

    Anti-patterns & known pitfalls

    • God object runner: Trying to embed all business logic in the FlowRunner rather than delegating to stages. Remedy: Keep FlowRunner generic and delegate all domain-specific processing to stage implementations.
    • Implicit shared state: Using global mutable state instead of passing the shared context explicitly. Remedy: Always pass the context as a parameter to each stage and never use global variables.
    • Skipping validation between stages: Assuming the output of one stage is always well-formed for the next. Remedy: Validate the shared context after each stage (e.g., with Pydantic) and fail fast.
    • Hard‑coded stages: Embedding stage list in code, making it difficult to reconfigure. Remedy: Use a configuration‑driven stage registry.
    • Mixing concerns: Letting stages access external systems directly instead of through interfaces. Remedy: Define a clear stage contract and wrap external calls with adapters.

    Adoption guidance

    Start by refactoring an existing monolithic script that already performs sequential steps into this pattern. Identify the natural stages and define a shared context interface. Use the existing FlowRunner and CLI as a skeleton. Add new stages incrementally, ensuring each stage is unit‑tested and validates context. For migration, begin with a simple two‑stage pipeline and expand. Ownership: The pattern should be owned by the platform architecture group (domain_id: platform, initiative_id: agentic-core). Primary contact: architecture-team@example.com. Governance linkage: Align with ADR-001 (Agent Execution Pipeline).
