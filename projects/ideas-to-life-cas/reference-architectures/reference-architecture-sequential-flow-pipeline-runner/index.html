    Reference Architecture: Sequential Flow Pipeline Runner

    Purpose & when to use this

    When to use this

    Use this pattern when you need to orchestrate a deterministic, multi-step workflow where each phase must complete successfully before the next begins, and where shared state across steps is required for consistency. Ideal for CI/CD pipelines, data extraction and reporting workflows, and any automation that requires a strict sequence of operations with early abort on failure.

    When NOT to use this

    Do not use this pattern when: - Phases are independent and can be parallelized for performance; a linear pipeline would unnecessarily lengthen execution time. - The workflow requires dynamic routing, retries with branching, or event-driven reactions to intermediate results (use an orchestration engine like Temporal or a DAG-based workflow). - The execution environment is highly distributed and needs stateful coordination across separate services; a simple sequential runner will become a bottleneck or single point of failure. - The order of operations is not critical or can be altered without affecting the final outcome.

    Components

    • CLI Entrypoint (src/cas_runner/cli.py): Parses user commands and arguments, loads configuration, and delegates to the FlowRunner for execution.
    • FlowRunner (src/cas_runner/runner.py): Central orchestrator that manages the sequential execution of phases, holds shared state, and enforces the order of operations with early abort on failure.
    • Setup Phase (src/cas_runner/phases/setup.py): Initializes environment variables, validates prerequisites, and prepares the shared context that subsequent phases will consume.
    • Extraction Phase (src/cas_runner/phases/extract.py): Extracts relevant data from external sources (e.g., git diff, metadata) and persists it to the shared context store.
    • Evaluation Phase (src/cas_runner/phases/evaluate.py): Applies the core logic, such as compliance checks or LLM-based analysis, using the extracted data and writes results back to the context store.
    • Reporting Phase (src/cas_runner/phases/report.py): Generates final outputs (dashboards, summaries, artifacts) from the evaluated results and returns them to the caller.
    • Shared Context Store (src/cas_runner/context.py): In-memory or persisted data structure that carries state between phases, ensuring consistency and traceability.

    Technology choices

    Recommended Stack: - Language: Python 3.11+ – chosen for readability, rich ecosystem (CLI, LLM, data processing), and team familiarity. - CLI Framework: typer (or click) – declarative command definitions, easy argument validation, and automatic help generation. - Process/State Management: dataclasses or pydantic for schema-validated shared context; pathlib for file operations. - External API Clients: httpx (async-compatible) or requests for LLM calls; gitpython for git operations. - Testing: pytest with responses/respx for mocking external calls. - CI/CD Integration: Native GitHub Actions or GitLab CI for execution; artifacts uploaded as build outputs.

    Alternatives Considered and Set Aside: - Airflow / Prefect – overkill for simple linear workflows; adds infrastructure complexity. - Docker/Kubernetes – not needed when running as a CLI or CI job; introduces overhead for single-process execution. - Node.js – rejected due to existing codebase and team expertise in Python.

    Variants

    Synchronous vs Asynchronous: The primary implementation is synchronous, blocking each phase until completion. For long-running evaluation steps, an asynchronous variant could use asyncio or background threads, but careful state management is required to avoid race conditions.

    Strict vs Fallback: In strict mode, any phase failure aborts the entire pipeline. A fallback variant can catch errors in non-critical phases (e.g., reporting) and produce partial results, while preserving the integrity of earlier phases.

    In-Memory vs Persisted Context: For local execution, context is stored in memory. For multi-run or distributed execution, the context can be serialized to disk or a lightweight database (e.g., SQLite) to enable inspection and recovery.

    Parallelizable Independent Steps: If some extraction or evaluation steps are independent, they could be executed in parallel using concurrent.futures, but this changes the sequential nature and should only be considered when ordering is not strictly mandatory.

    Non-functional characteristics

    Reliability: - Early-abort mechanism prevents cascading failures and avoids unnecessary API calls when prerequisites fail. - Shared context store ensures consistent state; if a phase crashes, the pipeline can be resumed from a known checkpoint (with persisted context). - Deterministic ordering eliminates heisenbugs related to race conditions.

    Performance & Latency: - Sequential execution is simple and predictable; latency is the sum of phase durations. - Bottlenecks occur in slow external calls (e.g., LLM APIs); caching and timeouts are essential. - Minimal overhead – no scheduler or queueing system; ideal for sub-minute pipelines.

    Cost & Efficiency: - Low infrastructure footprint (single process, no extra services). - Cost is dominated by external API usage; early abort reduces spend by preventing unnecessary calls. - Efficient for small to medium pipelines; scaling horizontally does not apply without redesign.

    Operability: - Excellent observability – each phase can log clear progress, and shared context can be dumped for debugging. - Easy to test – phases are units with clear inputs/outputs; mocks can replace external systems. - Deployment is straightforward (e.g., CLI tool, CI job); no special runtimes required.

    Anti-patterns & known pitfalls

    Overcentralization: Putting too much logic in the FlowRunner makes it a god object, reducing maintainability. Remedy: Keep the runner thin and delegate logic to phase-specific modules.

    Silent Failure of Phases: Swallowing exceptions without aborting leads to inconsistent outcomes. Remedy: Enforce strict error propagation and fail fast by default.

    Data Leakage Between Phases: Passing unvalidated data through shared context can break downstream steps. Remedy: Validate context schemas at each boundary.

    Ignoring Timeouts on External Calls: Hanging LLM or git calls freeze the pipeline. Remedy: Always set timeouts and retry policies.

    Premature Optimization: Introducing parallelism or async without measured need complicates the design. Remedy: Measure actual bottlenecks and only refactor when necessary.

    Hard-Coded Configuration: Embedding environment-specific values in phases degrades portability. Remedy: Use configuration files and environment variables.
