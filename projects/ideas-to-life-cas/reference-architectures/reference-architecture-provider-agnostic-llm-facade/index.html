    Reference Architecture: Provider-Agnostic LLM Facade

    Purpose & when to use this

    When to use this

    Apply the Provider-Agnostic LLM Facade pattern when your system requires interaction with multiple Large Language Model (LLM) providers (e.g., OpenAI, Anthropic, Ollama, Azure OpenAI) and you need to decouple core business logic from provider-specific APIs, request formats, and error semantics. This pattern is ideal when: - You anticipate switching or adding LLM providers without altering downstream components. - You need uniform invocation semantics for chat completions, structured output, or streaming across all agent tasks and modules. - You want to centralize cross-cutting concerns like retries, timeouts, rate limiting, and cost tracking in a single place. - You are building a multi-agent system where different agents may use different models but share the same call interface. - You require consistent observability and logging of all LLM interactions.

    When NOT to use this

    Avoid this pattern in the following scenarios: - You are building a simple, single-provider prototype with no explicit portability requirement; direct SDK usage is simpler and reduces initial overhead. - You need to use highly provider-specific features (e.g., custom tooling, advanced parameter tuning) that cannot be abstracted cleanly; forcing a generic interface would hide essential capabilities. - Your team has insufficient capacity to maintain a shared abstraction layer; premature abstraction can lead to over-engineering. - You are in a short-lived proof-of-concept where speed trumps maintainability. - You have strict performance requirements that are highly sensitive to extra indirection; a thin wrapper may add negligible but nonzero overhead, though this is rarely a real concern.

    Agents or governance modules issue requests to the facade. The facade normalizes the request, consults the cache, and delegates to the underlying provider SDK. Responses are normalized back into a canonical form before returning to the caller.

    Components

    Component Path Responsibility
    LLMFacade (Interface) src/cas_runner/llm/base_client.py (proposed) Defines the contract for LLM interactions: generate(), stream(), parse_structured(). Abstracts providers and standardizes request/response objects, error types, and retry semantics.
    LiteLLMClient src/cas_runner/llm/litellm_client.py Concrete implementation using LiteLLM library. Delegates to the appropriate provider backend while applying common configuration (model, temperature, max tokens, API keys) and mapping LiteLLM responses to the facade contract.
    MockClient src/cas_runner/llm/mock_client.py Provides deterministic mock responses for testing and development. Supports scripted responses or rule-based generation, enabling integration tests without external dependencies.
    ResponseNormalizer src/cas_runner/llm/normalizer.py (proposed) Transforms provider-specific outputs (including tool calls, thinking blocks, and structured JSON) into a canonical format. Handles error mapping to uniform exception types.
    ProviderRegistry src/cas_runner/llm/registry.py (proposed) Maps logical model names (e.g., gpt-4o, claude-sonnet-4, ollama/mistral) to concrete client implementations and their configurations. Enables dynamic selection at runtime.

    Technology choices

    Primary implementation uses LiteLLM as the underlying gateway because it already provides a unified interface to 100+ LLM providers and handles authentication, retries, and timeout management. This reduces custom code while meeting the facade goal. Alternative considered: writing custom adapters for each provider directly would have increased maintenance burden and reduced flexibility; rejected. For caching and structured output, we integrate with project’s existing Redis cache and Pydantic for schema validation. In the broader ecosystem, OpenAI SDK, anthropic SDK, and ollama-python are used indirectly via LiteLLM. The facade interface itself is intentionally framework-agnostic (plain Python Protocol) to avoid vendor lock-in.

    Variants

    1. Streaming Facade: Extends the interface to support token streaming, crucial for real-time interactive agents. Uses async generators and standardized SSE/stream formats.
    2. Structured Output Variant: Specializes in returning Pydantic models or JSON schemas, leveraging provider-specific functions (e.g., OpenAI's function calling) under the hood while normalizing the interface.
    3. Fallback Variant: Adds multi-provider failover logic, automatically retrying with a secondary model on primary failure. Implemented as a wrapper around the facade.
    4. Local/Remote Variant: Supports both remote APIs and local models (e.g., Ollama) through the same interface, with configuration determining endpoint and model parameters.
    5. Caching Variant: Integrates a response cache layer to reduce cost and latency for repeated prompts. Can be optional at runtime via a decorator.

    Non-functional characteristics

    • Reliability: The facade centralizes retry, timeout, and error handling. It uses exponential backoff and circuit breakers to handle provider outages. Mock client ensures deterministic testing. Failure modes are isolated to the facade, preventing propagation to business logic.
    • Performance & Latency: Direct provider invocation adds a thin overhead layer. Caching reduces repeated calls. Streaming support minimizes time-to-first-token. Batching can be leveraged for multiple prompts, though not yet implemented.
    • Cost & Efficiency: By abstracting providers, teams can switch to cheaper models without code changes. Unified logging enables cost per request tracking. Caching reduces spend. The pattern avoids vendor-specific cost optimization fragmentation.
    • Operability: All LLM calls pass through a single point, enabling structured logging, metrics (latency, token usage, error rate), and tracing. Configurations are externalized (e.g., via env vars) allowing deployment-specific tuning. The facade promotes observability and easy rollback when changing providers.

    Anti-patterns & known pitfalls

    • God Class Facade: Trying to solve all LLM concerns inside one monolithic class. Remedy: Split into focused clients (e.g., ChatClient, EmbeddingClient, StreamingClient) that share a base contract.
    • Leaking Provider-Specific Types: Exposing provider-specific request/response objects in the interface. Remedy: Define canonical types (dataclasses, Pydantic models) and normalize at boundaries.
    • Premature Abstraction: Creating the facade without real multi-provider requirement. Remedy: Start with one provider and extract the interface when second provider is needed; adhere to YAGNI.
    • Ignoring Error Semantics: Handling provider errors only as generic exceptions leads to loss of context. Remedy: Map to structured error types (e.g., RateLimitError, AuthenticationError, ContentPolicyError) and include request metadata.
    • Overly Complex Configuration: Trying to support every provider parameter in the facade leads to unwieldy configuration. Remedy: Use a simplified configuration that covers 90% of needs and allow raw pass-through for advanced cases.

    Adoption guidance

    Starting Points: - Begin by extracting an interface (LLMClient Protocol) from existing LiteLLMClient and MockClient. - Introduce the ResponseNormalizer to standardize outputs and error handling. - Define canonical model names in a configuration file and wire into ProviderRegistry. - Add integration tests that verify facade behavior using mock and real providers.

    Migration Path: - For existing components that directly use LiteLLM, refactor them to depend on the facade interface. - Gradually introduce caching and fallback wrappers as needed. - Ensure all client code references the facade, not the concrete implementation, to enable future provider swaps.

    Governance Ownership: - domain_id: agent-platform or intelligence-core (set by governance context) - initiative_id: llm-abstraction-initiative - Owner Contact: platform-architecture@example.com - Review Board: Architecture Guild (bi-weekly) with focus on interface evolution and provider integration standards.
