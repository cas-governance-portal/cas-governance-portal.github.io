    Reference Architecture: Provider-Agnostic LLM Facade

    Purpose & when to use this

    The Provider-Agnostic LLM Facade encapsulates large language model invocations behind a cohesive interface. It insulates agent execution logic from proprietary vendor APIs, diverse error formats, and distinct prompt-formatting rules.

    When to use this

    • When agentic runners execute across disparate environments (local development, offline CI/CD, production multi-cloud).
    • When switching between foundational model providers (e.g., OpenAI, Anthropic, self-hosted Ollama) without modifying business logic.
    • When centralized token budgeting, distributed tracing, structured schema extraction, and fallback retry mechanisms are required.

    When NOT to use this

    • Single-model proofs-of-concept requiring proprietary features (e.g., provider-specific assistant sandboxes or multimodal streaming hooks) not supported across common interfaces.
    • Lightweight, ad-hoc automation scripts where abstraction layers add unnecessary complexity.

    Components

    • LLM Client Facade Interface (src/cas_runner/llm/base.py): Formal interface defining uniform execution methods, schema parsing, and token usage accounting contracts.
    • LiteLLM Client Adapter (src/cas_runner/llm/litellm_client.py): Concrete adapter wrapping LiteLLM, standardizing requests across OpenAI, Anthropic, and local endpoints.
    • Mock LLM Client Adapter (src/cas_runner/llm/mock_client.py): Zero-egress adapter serving pre-recorded fixtures and deterministic synthetic output for tests.
    • Prompt / Response Cache (src/cas_runner/llm/cache.py): Key-value store avoiding redundant remote calls for idempotent prompt evaluations.

    Technology choices

    • Base Abstraction: Python typing.Protocol / abc.ABC to guarantee zero-overhead polymorphic dispatch.
    • Vendor Translation: LiteLLM for dynamic multi-provider routing and standardized schema transformation.
    • Output Validation: Pydantic v2 for rigid response schema validation and type parsing.
    • Alternatives set aside: Direct provider SDKs (increased vendor coupling) and heavy agent frameworks like LangChain/LlamaIndex (uncontrolled dependencies, rapid deprecations).

    Variants

    • Synchronous Direct Invocation: Standard request-response mode for deterministic batch pipeline operations.
    • Streaming Event Adapter: Asynchronous token streaming for responsive conversational and interactive user flows.
    • Multi-Provider Fallback: Dynamic failover automatically routing around vendor outages or rate limits to alternative configured models.
    • Hermetic Mock Runner: Offline test execution using static fixtures, enforcing contract stability without consuming API tokens.

    Non-functional characteristics

    • Reliability: Centralized retry with exponential backoff and jitter; graceful fallbacks on rate-limit exhaustion.
    • Performance & Latency: Sub-millisecond adapter overhead; reuse of persistent HTTP connection pools.
    • Cost & Efficiency: Per-step token accounting; prevention of duplicate calls via caching; ability to route simple tasks to lower-cost models.
    • Operability: Standardized spans for OpenTelemetry with uniform tagging of prompt tokens, completion tokens, latency, and model IDs.

    Anti-patterns & known pitfalls

    • Leaky Vendor Invocations: Passing provider-specific parameter dicts directly through the interface, breaking abstraction.
    • Model-Specific Prompt Engineering: Hardcoding prompts dependent on model-specific tags (e.g., <thinking>) inside common agent code.
    • Test Mock Drift: Failing to update mock adapters when provider contracts or response schemas change.

    Adoption guidance

    1. Define and inject the base LLMClient protocol across all agent and runner classes.
    2. Standardize model selection through configuration flags rather than inline model declarations.
    3. Implement MockLLMClient in standard test fixtures to decouple test execution from network access and API keys.
    4. Governance: Maintained under ideas-to-life-cas platform intelligence engineering. Architectural reviews required before introducing direct external SDK dependencies.
