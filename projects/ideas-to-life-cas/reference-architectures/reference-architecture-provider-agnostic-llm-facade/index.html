    Reference Architecture: Provider-Agnostic LLM Facade

    Purpose & when to use this

    The Provider-Agnostic LLM Facade abstracts upstream Large Language Model (LLM) APIs behind a unified internal client interface. It establishes a consistent invocation contract, standardized error handling, and deterministic test double implementations across all application workflows.

    When to use this

    • When services or autonomous agents interact with multiple LLM providers (e.g., OpenAI, Anthropic, Ollama, Bedrock) and need to switch or fallback dynamically.
    • When automated unit and integration test suites require deterministic, offline simulation of LLM responses without flakiness or network costs.
    • When application business logic must remain decoupled from evolving upstream vendor SDKs and payload schemas.
    • When centralized token accounting, prompt telemetry, retry strategies, and rate limiting must be consistently enforced across all agent steps.

    When NOT to use this

    • Single-model exploratory scripts, throwaway prototypes, or trivial utilities where the overhead of abstraction outweighs vendor portability.
    • Use cases fundamentally dependent on hyper-specific proprietary features (such as provider-native stateful Assistants API threads) that resist meaningful abstraction.
    • Direct client-side edge applications where a lightweight SDK direct call is strictly required due to extreme binary size constraints.

    Components

    • LLMClientInterface (src/cas_runner/llm/base.py): Defines the abstract interface and canonical request/response contracts for text completion, structured output extraction, and streaming.
    • LiteLLMClient (src/cas_runner/llm/litellm_client.py): Implements the production facade using LiteLLM to normalize multi-provider routing, credential injection, retry handling, and schema mapping.
    • MockLLMClient (src/cas_runner/llm/mock_client.py): Provides a high-fidelity, deterministic in-memory test double matching LLMClientInterface for hermetic CI/CD test execution.
    • AgentRunner (src/cas_runner/runner.py): Consumes the facade interface across agent execution phases without binding to underlying model vendors.

    Technology choices

    Selected Standards & Technologies

    • LiteLLM: Selected as the internal proxy engine due to broad multi-provider coverage (100+ model targets), automatic token counting, and uniform OpenAI-compatible payload schemas.
    • Pydantic: Standardized for request/response serialization and schema enforcement on structured outputs.
    • Abstract Base Classes (Python abc): Used to enforce the contract interface, ensuring zero vendor lock-in in consumer code.

    Alternatives Considered & Rejected

    • Direct Provider SDKs (openai, anthropic): Rejected due to high vendor lock-in, divergent error structures, and brittle agent business logic across model switches.
    • LangChain / LlamaIndex: Considered for high-level abstractions, but rejected in core infrastructure to avoid heavy transitive dependencies, frequent breaking changes, and opaque debugging paths.
    • Custom Internal Translation Layer: Rejected due to high ongoing maintenance burden tracking third-party API changes, which LiteLLM solves collaboratively.

    Variants

    Synchronous vs Asynchronous Dispatch

    • Async Non-Blocking (Primary): Standard for multi-agent runners executing concurrent subtasks or tool evaluations via asyncio.
    • Synchronous Blocking: Available for batch command-line utilities and single-threaded CLI processes.

    Local vs Remote Provider Routing

    • Cloud Gateway: Routes requests through remote model providers (OpenAI, Anthropic, Bedrock) with API key and secret rotation.
    • Local Inference: Seamlessly redirects the same client contract to self-hosted engines (e.g., Ollama, vLLM) for offline, privacy-critical, or cost-constrained workloads.

    Dynamic Fallback Variant

    • Configurable failover chains where a primary provider rate-limit (HTTP 429) or outage instantly redirects calls to a secondary provider model with identical structural contracts.

    Non-functional characteristics

    Reliability

    • Standardized retry policies with exponential backoff and jitter on transient HTTP 429 and 5xx errors.
    • Automated failover routing across designated backup model endpoints without caller intervention.

    Performance & Latency

    • Negligible serialization overhead (<2ms per call added by facade abstraction layer).
    • Connection pooling and keep-alive sessions enabled by default to minimize TCP/TLS negotiation overhead.

    Cost & Resource Efficiency

    • Centralized token tracking and usage telemetry emitted for every invocation.
    • Zero cloud spend during test suite execution via symmetrical mock clients.

    Operability & Observability

    • Standardized structured logging emitting model name, latency, prompt tokens, completion tokens, and provider trace IDs.
    • Decoupled configuration allowing runtime model swaps via environment variables without code deployments.

    Anti-patterns & known pitfalls

    Leaky Abstraction Pitfall

    • Anti-Pattern: Passing provider-specific proprietary parameters (such as extended_thinking_tokens or custom headers) directly through general agent code into the facade.
    • Remedy: Encapsulate advanced capabilities into explicit facade capability flags or typed metadata dicts with graceful degradation fallback.

    Vendor Exception Propagation

    • Anti-Pattern: Letting native vendor exceptions (e.g., openai.RateLimitError) bubble up into application domains.
    • Remedy: Translate all vendor-specific exceptions into unified domain exceptions (e.g., LLMRateLimitException, LLMAuthenticationException).

    Live Model Testing in CI

    • Anti-Pattern: Invoking live LLM endpoints in automated CI/CD unit or smoke tests, causing non-deterministic failures, latency, and uncontrolled billing.
    • Remedy: Enforce MockLLMClient or recorded VCR/fixture replays for all regression testing pipelines.

    Adoption guidance

    Starting Point

    1. Introduce LLMClientInterface as the single dependency for any LLM-powered agent step.
    2. Instantiate LiteLLMClient in production factory setups and inject MockLLMClient in all unit and integration test fixtures.
    3. Migrate existing direct provider SDK calls by rewriting caller expectations to the unified response object.
