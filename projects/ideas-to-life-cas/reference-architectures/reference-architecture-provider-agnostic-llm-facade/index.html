    Reference Architecture: Provider-Agnostic LLM Facade

    Purpose & when to use this

    The Provider-Agnostic LLM Facade pattern encapsulates all LLM interactions behind a unified client interface, decoupling agent and pipeline business logic from any specific model provider (OpenAI, Anthropic, Ollama, etc.). It standardizes call semantics, error handling, and response parsing while preserving the ability to switch providers without affecting downstream components.

    When to use this

    • When multiple LLM providers are or may be required (e.g., for resilience, cost optimization, or geographic data sovereignty).
    • When a consistent invocation contract is needed across many agent steps, runner components, or governance modules.
    • When structured output extraction and retry/fallback logic must be centralized rather than scattered across the codebase.
    • When testing requires deterministic, mockable LLM behavior without hitting real APIs.
    • When the project expects to evolve provider capabilities or pricing without rewriting core logic.

    When NOT to use this

    • When only one provider is used and is firmly locked (no foreseeable need for portability) – a direct SDK call is simpler.
    • When the application requires deep provider-specific features (e.g., custom token-level streaming controls, provider-unique embeddings) that are not exposed through the facade.
    • When the team is small and the abstraction overhead outweighs the benefit; a thin wrapper may suffice.
    • When performance is ultra-critical and the extra indirection of a facade adds unacceptable latency – though this is rare given modern proxies.
    • When the full feature set of every provider must be accessible – a facade often restricts to a common subset.

    Components

    LLM Facade (LiteLLMClient)

    Path: src/cas_runner/llm/litellm_client.py

    Responsibility: Provides a unified invocation interface over LiteLLM, handling provider selection, retry/timeout policies, structured output parsing (via response_format or tool calls), and consistent error mapping. Exposes methods like complete() and complete_structured() to all agent steps.

    MockLLMClient

    Path: tests/llm/mock_llm_client.py

    Responsibility: Implements the same interface as LiteLLMClient but returns deterministic canned responses for unit and integration tests, enabling fast, offline validation of agent workflows.

    LLMResponse

    Path: src/cas_runner/llm/types.py

    Responsibility: Canonical data class representing a completed LLM call: content, tool calls, finish reason, usage metadata. Parsed uniformly from provider-specific responses to normalize downstream handling.

    Agent / Workflow Step

    Path: src/cas_runner/steps/

    Responsibility: Any runner step or governance module that requires LLM generation. It depends solely on the facade interface, never directly on a specific provider SDK, ensuring portability and testability.

    Provider Adapters

    Path: via LiteLLM configuration

    Responsibility: Translates the unified facade request to each provider's native API schema (OpenAI, Anthropic, Ollama, etc.). These adapters are implicit in LiteLLM and configured through environment variables or config files.

    Technology choices

    Recommended technology: - LiteLLM (Python library) as the underlying provider abstraction – supports 100+ LLM providers, consistent API, automatic fallback/retry, and cost tracking. - Pydantic for structured output validation and schema definition – used by the facade to parse provider responses into typed LLMResponse objects. - pytest with MockLLMClient for test scenarios.

    Alternatives considered and set aside: - Direct provider SDKs (OpenAI, Anthropic): Couples code to each vendor, violates portability, and duplicates error/retry logic. Only viable for a single-provider spike, not production. - LangChain (as a facade): Heavyweight, introduced versioning churn, and over-complicates the call path. Lacks the fine-grained control we needed for structured outputs and cost management. - Custom hand-rolled wrapper: Would require maintaining provider-specific adapters, error mapping, and rate-limit handling – high maintenance cost for no benefit over LiteLLM.

    Variants

    1. Synchronous vs Asynchronous: The facade exposes both complete (sync) and acomplete (async) methods. Sync is used for simple runner steps; async is preferred for concurrent agentic workflows.
    2. Strict vs Fallback: In strict mode, any provider failure aborts the step; in fallback mode, the facade retries with alternative providers (e.g., OpenAI → Anthropic) based on configured priority list.
    3. Streaming vs Non‑streaming: For long-form generation, streaming mode returns a token iterator; non‑streaming returns the complete response at once. Both share the same facade interface.
    4. Structured vs Unstructured Output: When a Pydantic schema is provided, the facade uses tool calling or response_format to force structured JSON; otherwise it returns raw text.
    5. Caching Variant: An optional response cache (in‑memory or Redis) can be enabled to deduplicate identical requests, reducing cost and latency for repeated queries.

    Non-functional characteristics

    Reliability - The facade centralizes retry with exponential backoff and jitter, automatically handles transient provider errors (rate limits, 5xx, timeouts), and can cascade to fallback providers. - Timeout values are configurable per call type, preventing hung agents. - MockLLMClient allows deterministic failure injection for resilience testing.

    Performance & Latency - The facade adds negligible overhead (low‑single‑digit microseconds) beyond direct SDK calls. - Async support enables concurrent LLM calls, improving throughput for parallel agent steps. - Response caching reduces average latency for repeated prompts. - Streaming capability reduces time‑to‑first‑token for user‑facing generation.

    Cost & Efficiency - Provider portability enables switching to cheaper models without code changes. - The facade enforces token‑usage tracking, enabling per‑step cost analytics. - Caching reduces redundant calls, lowering overall spend. - Model selection can be configured per step (e.g., small model for classification, large for generation) without impacting code.

    Operability - All provider credentials and settings are managed via environment variables or config files, not code – simplifying CI/CD and secret rotation. - Structured logging includes request/response metadata (provider, model, tokens) for observability. - The interface is stable, so swapping providers is a metadata change, no code change. - Standardized error codes (e.g., RateLimitError, AuthenticationError) propagate across the system, easing monitoring.

    Anti-patterns & known pitfalls

    1. Over‑abstraction – Adding unnecessary methods or provider‑specific parameters to the facade for every possible feature. Remedy: Keep the facade minimal; expose advanced provider‑specific features via a separate escape‑hatch (e.g., raw_request() method) for rare cases.
    2. Leaky abstraction – Letting provider‑specific types (e.g., OpenAI message objects) leak into agent code. Remedy: Always map responses to the canonical LLMResponse type; reject any attempt to return raw provider objects.
    3. Ignoring provider differences – Assuming all providers behave identically (e.g., token limits, tool‑calling support). Remedy: Document and test provider variants; use feature detection at runtime where needed.
    4. Mixing facade layers – Using the facade for non‑LLM operations (e.g., vector store calls). Remedy: Keep the facade focused solely on model invocation; other services have their own clients.
    5. Mocking the facade incorrectly – Overriding the facade in tests but not exercising real error paths. Remedy: Use MockLLMClient for happy paths and integration tests against real providers (or a local Ollama) for edge cases.
    6. Configuration sprawl – Storing provider API keys in code. Remedy: Use environment variables or a secret manager; verify no secrets are committed to VCS.

    Adoption guidance

    Starting Point - Replace existing direct LLM calls in runner steps and governance modules with the existing LiteLLMClient facade. Look for any place that imports openai or anthropic directly. - Integrate MockLLMClient into the test suite for deterministic unit tests. - Standardize on the LLMResponse type across codebase.

    Migration Path 1. Phase 1 (Week 1–2): Audit all LLM usage; convert to facade calls. Add unit tests with MockLLMClient. 2. Phase 2 (Week 3–4): Introduce structured output support and caching; benchmark and tune timeout/retry settings. 3. Phase 3 (Month 2+): Expand to multi‑provider fallback; enable request analytics and cost dashboards.
