    Reference Architecture: Provider-Agnostic LLM Facade

    Purpose & when to use this

    The Provider-Agnostic LLM Facade encapsulates large language model invocations behind a unified, standardized interface. It decouples high-level agent reasoning, step execution, and workflow orchestration from proprietary vendor APIs, enabling runtime model swapping, unified telemetry, and resilient multi-provider routing.

    When to use this

    • When application workflows or autonomous agent runners must support multiple model providers (e.g., OpenAI, Anthropic, Mistral, Ollama) without modifying business logic.
    • When business requirements demand dynamic failover or cost-based model tiering (e.g., attempting a lightweight or self-hosted model before escalating to an expensive frontier model).
    • When centralized cross-cutting concerns—such as token tracking, rate limiting, retries, and structured schema enforcement—must be managed consistently across disparate providers.
    • When testing or local development requires stubbing model calls or redirecting them to local endpoints (such as Ollama or vLLM) without reconfiguring step logic.

    When NOT to use this

    • Single-model, prototype-stage scripts where vendor portability introduces unwarranted indirection and operational overhead.
    • Highly specialized solutions relying heavily on vendor-exclusive primitives (e.g., vendor-specific fine-tuning endpoints, proprietary assistant state engines) that cannot be cleanly abstracted without loss of functionality.
    • Real-time ultra-low-latency edge streaming where even fractional gateway or wrapper overhead cannot be tolerated.

    Components

    • LiteLLMClient (src/cas_runner/llm/litellm_client.py): Provides a consistent invocation wrapper and execution facade across disparate model providers, mapping domain-level prompt objects and parameters into normalized underlying LiteLLM completions.
    • Model Configuration & Credentials Store (config/settings.py): Manages model definitions, provider endpoint URIs, token thresholds, rate limits, and secure API credential lookups.
    • Agent Orchestrator / Runner Steps (src/cas_runner/steps/): Executes domain workflows and prompt generation logic, consuming the facade interface without dependency on vendor-specific SDKs.

    Technology choices

    Recommended Choices

    • LiteLLM (litellm>=1.83.14): Adopted as the core mediation engine for wrapping 100+ LLM APIs behind an OpenAI-compatible interface. It standardizes request formatting, error classification, and response streaming while preserving Python async/await paradigms.
    • Pydantic V2: Standardized for structured output schema definitions and runtime validation, ensuring type safety regardless of the underlying model's JSON adherence.

    Alternatives Considered & Set Aside

    • Direct Vendor SDKs (openai, anthropic, google-generativeai): Set aside due to high maintenance coupling, divergent retry/exception structures, and the necessity of writing bespoke adapter layers for each provider.
    • LangChain / LlamaIndex Abstractions: Set aside to avoid heavyweight framework bloat, complex dependency graphs, and leaky abstractions that hinder granular control over prompt formatting and raw token handling.

    Variants

    Synchronous vs Asynchronous Invocation

    • Asynchronous Non-Blocking: Default production mode for agent workflows and batch pipeline executions, permitting concurrent generation and non-blocking streaming.
    • Synchronous Blocking: Constrained execution mode used in CLI diagnostics, linear setup phases, and deterministic single-step integration tests.

    Fallback & Cascading Routing

    • Strict Target Variant: Binds a specific task to a designated provider and model family (e.g., code generation pinned to Claude 3.5 Sonnet).
    • Resilient Fallback Cascade: Tries a primary provider (e.g., Anthropic Claude), catches transient 429/503 network or quota exceptions, and transparently routes the request to a secondary fallback (e.g., OpenAI GPT-4o) with standardized output mapping.

    Non-functional characteristics

    Reliability

    • Normalizes vendor-specific error responses into unified domain exception types (e.g., AuthenticationError, RateLimitExceeded, ContextLengthExceeded).
    • Integrates exponential backoff and transparent retry budgets for transient provider-side failures.

    Performance & Latency

    • Adds sub-millisecond local wrapping overhead over direct HTTP calls.
    • Enables zero-copy response streaming to minimize time-to-first-token (TTFT) for user-facing and real-time agent processes.

    Cost & Efficiency

    • Centralizes token usage extraction (prompt_tokens, completion_tokens) to ensure accurate cost attribution per workflow step.
    • Simplifies dynamic task routing to lower-cost frontier or local models (e.g., running summarization on Llama 3 instead of GPT-4o).

    Operability

    • Standardizes logging and OpenTelemetry-compliant trace generation across all LLM calls from a single interception layer.

    Anti-patterns & known pitfalls

    Anti-Pattern 1: Leaking Provider-Specific SDK Exceptions

    • Pitfall: Allowing raw vendor errors (such as openai.RateLimitError or anthropic.APIStatusError) to escape into calling agent steps.
    • Remedy: Catch and wrap all external provider exceptions within standardized domain exceptions defined in the facade.

    Anti-Pattern 2: Vendor-Specific Prompt Formatting in Domain Logic

    • Pitfall: Hardcoding proprietary role tags or formatting hacks (e.g., custom XML wrappers or proprietary image payload blocks) directly inside business logic.
    • Remedy: Keep messages in standard OpenAI-compatible role schemas (system, user, assistant, tool) and allow the facade adapter to translate parameters into vendor-specific dialect requirements.

    Adoption guidance

    Starting Points

    1. Replace direct imports of vendor SDKs across runner steps with imports of LiteLLMClient.
    2. Configure API keys and default routing aliases (primary_model, fallback_model) via environment variables and project configuration files.
    3. Validate agent execution through standardized unit and integration tests using mocked provider responses.
