    Reference Architecture: Provider-Agnostic LLM Facade

    Purpose & when to use this

    When to use this

    Use the Provider-Agnostic LLM Facade whenever an application integrates multiple LLM providers (e.g., OpenAI, Anthropic, Ollama) or anticipates future provider changes. It is essential when you need consistent invocation semantics, unified error handling, and the ability to swap model providers without altering business logic. This pattern is particularly valuable in agentic pipelines, tool-calling runners, and any system requiring deterministic mock behavior for testing or CI.

    When NOT to use this

    Do not use this pattern for applications that are permanently bound to a single provider with no prospect of migration and that do not require strict testing isolation. Over-abstracting LLM calls in simple, one-off scripts or prototypes adds unnecessary complexity. Also avoid if the abstraction layer cannot maintain parity with underlying provider-specific features (e.g., streaming, vision, structured outputs) or if the team lacks the capacity to evolve the facade to match provider updates.

    Components

    Agent Step

    • Path: src/cas_runner/runner
    • Responsibility: Orchestrates a single step in the agent pipeline, invoking the facade to generate or parse completion outputs without knowledge of the underlying provider.

    Provider-Agnostic Facade (LiteLLMClient)

    • Path: src/cas_runner/llm/litellm_client.py
    • Responsibility: Provides a unified interface for LLM calling, wrapping LiteLLM to normalize provider APIs, handle retries, and expose a consistent response format. It also supports structured output parsing and deterministic settings for reproducibility.

    MockLLMClient

    • Path: src/cas_runner/llm/mock_llm_client.py
    • Responsibility: Implements the same interface with deterministic mock responses for testing, CI pipelines, and offline development. Ensures parity with real client behavior to avoid test drift.

    Provider Clients (OpenAI, Anthropic, Ollama)

    • Path: external
    • Responsibility: External model providers offering distinct API schemas, rate limits, and error patterns. The facade shields the rest of the system from these differences.

    Technology choices

    Recommended Stack: Python 3.11+, LiteLLM as the core provider abstraction layer, Pydantic for structured output validation, pytest for testing with mock clients.

    Alternative: Direct SDK wrappers per provider (e.g., openai, anthropic, boto3 for Bedrock) but this increases boilerplate and reduces portability.

    Considered and set aside: - LangChain: Overly high-level and heavy for the need. - Custom HTTP client: High maintenance burden. - Provider SDK directly without facade: Causes vendor coupling and inconsistent error handling.

    For deterministic testing, MockLLMClient is recommended over monkey-patching external SDKs.

    Variants

    • Synchronous vs. Asynchronous Facade: The facade can expose async call methods to integrate with asyncio-based runners.
    • Strict vs. Fallback: A strict variant raises provider errors immediately; a fallback variant tries real provider first, then falls back to mock on failure.
    • Caching Variant: Adding a response cache at the facade level to reduce cost and latency for repeated prompts.
    • Multi-Model Routed Variant: The facade can route based on task type (e.g., small model for classification, large model for generation) using a configurable policy.

    Non-functional characteristics

    Reliability

    • The facade handles provider outages by retry policies and may degrade to mock fallback for non-critical operations. It should track error rates and timeouts per provider.
    • Idempotency for generation calls is not guaranteed by LLMs; design workflows to tolerate partial failures via retries or checkpoints.

    Performance & Latency

    • Adds minimal overhead (~5-10 ms) over raw SDK calls when using LiteLLM's wrapper.
    • MockLLMClient eliminates round-trip latency for tests, making CI faster and deterministic.
    • For streaming, the facade must support incremental token delivery to preserve user-facing latency.

    Cost & Efficiency

    • Provider-agnostic design allows dynamic selection of cheapest provider for given task, reducing cost.
    • Mock fallback avoids burning tokens during development.
    • Caching variants can significantly lower expense for repetitive calls.

    Operability

    • Centralized logging and metrics collection at the facade layer improves observability across all provider interactions.
    • Configuration via environment variables or config files supports different deployments (e.g., local mock, staging real, production real).
    • Requires clear ownership and versioning of the facade package to keep parity with provider API changes.

    Anti-patterns & known pitfalls

    Over-Abstraction

    • Problem: Creating a facade that tries to support every possible provider feature leads to bloated interface and high maintenance.
    • Remedy: Keep the interface minimal; expose advanced provider-specific features via optional method or parameter when needed.

    Mock Parity Drift

    • Problem: MockLLMClient responses become stale and no longer reflect real provider behavior, misleading tests.
    • Remedy: Implement contract tests that run both clients against the same fixture set and require periodic manual review of generated outputs.

    Leaking Provider Types

    • Problem: Returning raw provider models (e.g., OpenAI-specific response object) couples consumers to a vendor.
    • Remedy: Always return a normalized, Pydantic-validated response object.

    Error Swallowing

    • Problem: Facade catches errors and silently returns mock fallback in production, hiding provider outages.
    • Remedy: Only use mock fallback in explicit fallback mode; otherwise, log errors with severity and alert operators.

    Adoption guidance

    Starting Points

    • Begin by introducing the facade behind a single existing LLM call site. Replace raw SDK calls with a facade method and add unit tests using MockLLMClient.
    • Use the LiteLLMClient for production and MockLLMClient for CI to ensure deterministic builds.
    • Gradually migrate all LLM calls across the codebase, keeping a uniform interface.

    Migration Path

    • Phase 1: Add facade classes and unit tests; no production impact.
    • Phase 2: Refactor existing agent steps to use the facade, keeping the same provider and configuration.
    • Phase 3: Enable provider switching via configuration (e.g., environment variables) and run comparison tests.
    • Phase 4: Monitor performance and reliability; tune retry and fallback policies.
