    Reference Architecture: Sequential Pipeline Orchestration

    Purpose & when to use this

    When to use this

    Use Sequential Pipeline Orchestration when you need deterministic, ordered execution of a multi-step process where each step depends on the outcome of the previous one, and where strict termination on failure is critical. This pattern is ideal for:

    • CI/CD pipelines that must produce deterministic exit codes and structured stage results.
    • Agentic workflows requiring bounded autonomy with explicit checkpoints and guarded transitions.
    • Analytical or synthesis pipelines that must enforce a fixed sequence of transformations (e.g., architectural analysis, generation, evaluation, and reporting).
    • Compliance‑sensitive environments where a failure in an early step must halt the entire process to avoid cascading errors or state corruption.

    When NOT to use this

    Avoid this pattern when:

    • Steps are independent and can run in parallel without shared state or ordering constraints—use a fan‑out/fan‑in or event‑driven model instead.
    • The pipeline requires dynamic branching or condition‑based retries that cannot be expressed as a linear sequence—consider a state machine or workflow engine with richer semantics.
    • Steps can be long‑running and require asynchronous execution with human interaction—a distributed workflow engine (e.g., Temporal, Argo) might be more suitable.
    • A single failure should not interrupt the entire pipeline (e.g., best‑effort data enrichment)—use a resilient orchestration approach with compensation or fault tolerance.

    Components

    Component Path Responsibility
    FlowRunner src/cas_runner/runner.py Central deterministic orchestrator that executes a sequence of steps according to a defined order. It manages context propagation, enforces step boundaries, and terminates immediately on critical compliance failures.
    Step Definitions src/cas_runner/steps/ Encapsulate individual pipeline steps as modular units. Each step defines its input contract, execution semantics, and output to be written back to the shared context.
    Shared Context Store src/cas_runner/context.py Mutable, process‑scoped data structure that carries state and artifacts from one step to the next. Provides versioning and immutability for critical compliance checks.
    Checkpoint Store src/cas_runner/checkpointing.py Persists the execution progress and intermediate results to support resumability and auditability. Enables recovery from partial execution without restarting the entire pipeline.
    Compliance Evaluator src/cas_runner/evaluators/ Executes deterministic checks against the workflow output and compliance rules. If a critical violation is detected, it signals the FlowRunner to halt execution immediately.
    Agent Runner src/cas_runner/agents/ Wraps automated agentic steps (e.g., LLM‑based analysis) with bounded execution time, retry policies, and structured output validation. This container isolates external dependencies.
    CLI/API Adapter src/cas_runner/cli.py Exposes the pipeline to external invokers (CLI, GitHub Actions) and translates command‑line arguments into step parameters. It enforces exit‑code mapping and result reporting.

    Technology choices

    Core implementation: Python 3.11+ for its rich standard library and type‑hinting support. Orchestration backbone: A custom micro‑framework built around a FlowRunner class that reads a declarative step declaration (YAML or dataclass) to avoid lock‑in to heavyweight workflow engines. Context store: In‑memory dataclass/TypedDict for the active run, with optional JSONL (or SQLite) for durable checkpoints. Agent integration: LangChain or direct AsyncOpenAI calls for LLM steps, isolated in the AgentRunner for testability. Deterministic evaluation: Pure Python functions with pydantic for validation and a rule engine (e.g., jsonpath‑ng or simple predicate functions) for compliance checks. Alternatives set aside: Apache Airflow (too heavy for single‑process deterministic pipelines), Temporal (over‑engineered for linear orchestrations and requires external infrastructure), and custom state machines (adds complexity without tangible benefit for a fixed sequence).

    Variants

    Strict vs. lenient failure handling: The baseline FlowRunner halts on the first critical error. A variant allows non‑critical warnings to be collected and reported, while critical violations still abort immediately. Checkpointed vs. ephemeral: For long‑running pipelines, a variant persists checkpoints to disk after each step, enabling resumption from the last completed step. For short CI jobs, checkpoints may be kept only in memory. Deterministic vs. agent‑augmented steps: Some steps may be fully deterministic (e.g., formatting, aggregation); others may invoke agents. A variant treats agent steps as black boxes that must return structured output, while deterministic steps are pure functions. Parallel fan‑out within a step: Although the outer orchestration is linear, a single step may internally parallelize sub‑tasks (e.g., evaluating multiple candidate solutions concurrently) and aggregate results before returning to the FlowRunner.

    Non-functional characteristics

    Reliability: The pattern ensures deterministic termination on critical failures, preventing cascading state corruption. Checkpointing provides crash recovery without rerunning earlier steps. Performance & Latency: Sequential execution introduces linear latency proportional to the number of steps. Each step's internal parallelism can mitigate latency, but overall it is suitable for pipelines with moderate step counts (typically <20). Cost & Efficiency: Minimal runtime overhead because the orchestrator is lightweight and in‑process. Agent steps can be expensive; the variant with checkpointing reduces rerun cost. Operability: The pipeline exposes structured JSON logs, exit codes, and checkpoint artifacts, enabling straightforward integration with CI/CD. The declarative step list is human‑readable and version‑controllable. Safety: The strict failure mode and compliance evaluator enforce architectural guardrails, making the pattern suitable for governance‑sensitive environments.

    Anti-patterns & known pitfalls

    Monolithic step definitions: Creating steps that are too large or have side effects make the pipeline hard to test and maintain. Remedy: Decompose steps into single‑responsibility units with clear input/output contracts. Unbounded context growth: Propagating large or mutable data between steps leaks memory and makes checkpointing expensive. Remedy: Store only necessary artifacts; use references to external storage for heavy payloads. Bypassing the FlowRunner: Direct invocation of steps from external modules breaks ordering guarantees and defeats checkpointing. Remedy: Enforce that all execution goes through the FlowRunner. Ignoring non‑critical errors: Silently swallowing warnings can hide compliance drift. Remedy: Define a policy for warnings and surface them in the structured output. Over‑parallelization inside a step: Parallelizing every internal task without limits can cause resource exhaustion and non‑deterministic outputs. Remedy: Use controlled concurrency (e.g., thread pool with a fixed size) and aggregate deterministically.

    Adoption guidance

    Starting point: Identify a linear workflow with 3–5 sequential steps that currently run ad hoc or in separate scripts. Define the step boundaries and context schema. Migration path: Introduce the FlowRunner as a thin orchestrator around existing step functions. Add checkpointing and compliance checks incrementally. Governance ownership: Pattern owned by platform engineering team responsible for the CAS workflow. Initial adoption is in ideas-to-life-cas project. Stakeholder links: Architecture review board, DevOps engineering, and agent framework teams. Success criteria: Reduced pipeline execution time, clear audit trails, and deterministic failure behavior. Recommended rollout: Pilot on a non‑critical workflow, measure observability and recovery benefits, then expand to compliance‑sensitive pipelines.
