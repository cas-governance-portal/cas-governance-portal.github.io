    Reference Architecture: Sequential Pipeline Orchestration

    Purpose & when to use this

    Purpose

    Coordinates multi-step agentic analysis, deterministic policy evaluation, and artifact synthesis tasks through a centralised, linear execution runner with shared context propagation. The pattern ensures deterministic exit codes, unified state tracking, and immediate circuit-breaking on critical compliance failures.

    When to use this

    • Multi-stage pipelines where downstream phases strictly depend on successful, verified execution of preceding stages.
    • CI/CD and automation environments requiring deterministic process exit codes, structured execution logs, and predictable resource consumption.
    • Governance and compliance enforcement workflows where policy violations must halt execution immediately to prevent runaway agent costs or invalid artifact generation.
    • Workflows involving autonomous LLM agents that require strict outer-loop boundaries, state inspection checkpoints, and deterministic fallback routines.

    When NOT to use this

    • High-throughput parallel data processing where stages are independent and can be modeled as a fully asynchronous Directed Acyclic Graph (DAG).
    • Event-driven reactive choreographies where decoupled microservices trigger off independent message queues or bus events without central coordination.
    • Simple single-action tasks or trivial utility scripts where a central orchestrator introduces unnecessary abstraction overhead.
    • Ultra-low latency request/response cycles requiring concurrent non-blocking sub-task execution.

    Components

    • FlowRunner Core (src/cas_runner/runner.py): Directs linear phase transitions, registers execution hooks, tracks timing metrics, and halts execution immediately on stage failure.
    • Shared Pipeline Context (src/cas_runner/context.py): Maintains immutable configuration inputs, accumulated phase outputs, token consumption counters, and intermediate domain models.
    • Phase Evaluator Interface (src/cas_runner/phases/base.py): Provides standard execute and validate contract for deterministic policy checks, agent calls, and synthesis operations.
    • State Checkpointer (src/cas_runner/checkpoint.py): Persists stage transitions and error state dumps to disk or remote storage for auditing and replay capabilities.

    Technology choices

    Selected Technologies

    • Python Standard Library & Pydantic: Context schema enforcement, static type validation, and structural validation across phases without heavy framework lock-in.
    • File-based & Memory Checkpointing: Fast local checkpointing for CLI/CI runs, supporting JSON and serialized state artifacts.
    • Structured JSON Logging: Standardized log emission across all pipeline phases for ingestion into CI/CD telemetry systems.

    Alternatives Considered

    • Temporal / Cadence: Set aside due to operational complexity, external server dependency requirements, and overkill for self-contained CI/CD CLI tools.
    • Apache Airflow / Prefect: Set aside due to heavy infrastructure footprint and runtime friction when embedding directly into developer workstations and lightweight CLI runners.
    • Decoupled Event Choreography (Kafka/RabbitMQ): Set aside because linear governance validation requires strict deterministic control and immediate fail-stop semantics without distributed queue management.

    Variants

    Variant A: Strict Fail-Fast (Default)

    Any assertion error, policy validation failure, or unhandled agent error in any stage immediately triggers an execution abort, writes diagnostic state to the checkpointer, and exits with a non-zero code.

    Variant B: Soft-Gate Diagnostics

    Failures in non-critical evaluation phases (e.g., style recommendations or advisory checks) record warnings into the shared context without terminating execution, allowing synthesis phases to proceed while reporting degradation.

    Non-functional characteristics

    Reliability

    • Deterministic step transitions guarantee reproducible outcomes given identical inputs.
    • Checkpoints capture error traces and execution states before process exit, minimizing troubleshooting time.

    Performance & Latency

    • Minimal orchestration overhead (sub-millisecond handoff between phases).
    • Sequenced execution trades maximum potential concurrency for predictability and strict gate validation; complex DAG branch validation may exhibit linear cumulative latency.

    Cost & Efficiency

    • Strict phase boundaries prevent autonomous agent looping and unintended API token burn.
    • Early termination on governance failures prevents expensive downstream LLM synthesis invocations.

    Operability

    • Standard UNIX exit codes indicate stage-specific failures.
    • Structured logs and step metadata provide transparent telemetry for CI/CD pipelines and developer environments.

    Anti-patterns & known pitfalls

    Unbounded Agent Loops

    • Anti-Pattern: Allowing an autonomous LLM agent within a phase to recursively self-prompt indefinitely without strict iteration limits.
    • Remedy: FlowRunner enforces a maximum execution timeout and turn count per phase, forcibly failing the step upon threshold exhaustion.

    Side-Channel Mutation

    • Anti-Pattern: Pipeline stages mutating global environment state or bypassing the shared context object to communicate with downstream stages.
    • Remedy: Enforce pure functional phase inputs/outputs where each phase receives a read-only context slice and yields explicit result models.

    Monolithic Pipeline Phasing

    • Anti-Pattern: Merging analysis, governance, and artifact synthesis into a single opaque script, obscuring failure points.
    • Remedy: Separate distinct responsibilities into granular, individually testable phase modules managed through the central orchestrator.

    Adoption guidance

    Starting Point

    1. Define concrete input and output schemas using Pydantic for each phase.
    2. Wrap individual workflow actions into implementations of the Phase Evaluator interface.
    3. Configure FlowRunner with an explicit list of phases and configure fail-fast criteria.

    Migration Path

    • Stage 1: Wrap existing standalone scripts as isolated FlowRunner phases.
    • Stage 2: Standardize pipeline context sharing, removing ad-hoc file passing.
    • Stage 3: Integrate checkpointing and link to CI/CD exit code policies.
