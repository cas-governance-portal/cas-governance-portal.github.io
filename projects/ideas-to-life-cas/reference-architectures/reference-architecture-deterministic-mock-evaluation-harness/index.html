    Reference Architecture: Deterministic Mock Evaluation Harness

    Purpose & when to use this

    This pattern provides a drop-in mock LLM client that enables deterministic, offline execution of agentic workflows and governance decision flows. It is designed to replace live LLM calls with a scripted, predictable response engine, ensuring that pipelines can be validated end-to-end without network flakiness, model nondeterminism, or associated costs.

    When to use this

    • Use when you need to run agent pipelines in CI/CD environments where live LLM calls are unreliable, slow, or costly.
    • Use when end-to-end testing of state transitions, schema validation, and orchestration logic is required, independent of external model behavior.
    • Use when you need to reproduce specific LLM outputs (e.g., edge cases, error responses) to test error handling and fallback paths.
    • Use for unit and integration tests that must be fast, deterministic, and runnable in parallel.
    • Use when you want to establish a baseline for performance or behavior before switching to live models.

    When NOT to use this

    • Do not use as a substitute for integration testing with real LLMs, as mock responses may not reflect actual model output quality or latency.
    • Do not use when testing model-specific features (e.g., token limits, streaming, or fine-tuned responses) that cannot be accurately simulated.
    • Do not use in production paths where you need genuine LLM reasoning; this pattern is strictly for testing and development.
    • Avoid using if your pipeline relies on non-deterministic LLM side effects (e.g., random sampling) that are essential to the business logic.

    Components

    • MockLLMClient (path: src/cas_runner/llm/mock_client.py): Implements the LLM client interface with deterministic, scripted responses. It reads from a mock configuration store and returns pre-defined outputs, optionally simulating delays or errors.
    • Production LLM Client (path: src/cas_runner/llm/client.py): Provides live LLM integration for production and non-test environments. It adheres to the same interface, enabling drop-in replacement.
    • Agent Pipeline Orchestrator (path: src/cas_runner/pipeline/): Coordinates end-to-end execution of agentic workflows, including sequential or parallel steps, state transitions, and schema validation. It consumes either client based on runtime configuration.
    • Mock Configuration Store (path: tests/fixtures/mock_responses.json): Holds structured test scenarios, including response sequences, error payloads, and timing parameters. This store drives the MockLLMClient's behavior.
    • CI/CD Integration Layer (path: .github/workflows/): Automates test execution using the MockLLMClient, ensuring deterministic validation of the entire pipeline in isolation from external services.

    Technology choices

    Recommended technologies: - Python 3.11+ for implementation and test frameworks (pytest, unittest). - JSON or YAML for mock response fixtures, leveraging schema validation (e.g., pydantic). - Environment variable LLM_MOCK (or similar) to toggle between mock and real clients. - Dependency injection for client swapping.

    Alternatives considered and set aside: - Third-party HTTP mocking libraries (e.g., responses, moto): set aside because they over-couple tests to the HTTP layer and do not abstract the LLM interface cleanly. - Live LLM with retry logic: set aside due to cost, latency, and nondeterminism. - Service virtualization tools (e.g., Mountebank): set aside as they introduce heavyweight infrastructure unnecessary for this use case.

    Variants

    • Synchronous vs. asynchronous: Support both sync and async interfaces to accommodate pipelines that use concurrent LLM calls.
    • Scripted vs. generative mocks: Scripted responses for deterministic tests; generative mocks (e.g., using templates or rule-based generation) for load testing or fuzzing.
    • Delay simulation: Configure mock responses to introduce artificial latency, testing timeout and retry behavior.
    • Error injection: Define sequences that return errors or malformed responses to test error handling and fallback mechanisms.
    • Schema enforcement: Strict mode validates every mock response against the expected schema; permissive mode allows partial responses for exploratory testing.

    Non-functional characteristics

    • Reliability: High reliability in test environments due to predictable responses, eliminating flaky network calls. However, it does not validate real-world LLM behavior; periodic integration tests with live models are necessary.
    • Performance & Latency: Mock responses are near-instant, enabling fast feedback loops. Simulated latency can be used to test timeout behavior.
    • Cost & Efficiency: Zero cost for mock execution, saving significant LLM API expenses during development and CI. Negligible operational overhead.
    • Operability: Simple to deploy and maintain; requires periodic review of mock fixtures to ensure they remain aligned with evolving LLM APIs.

    Anti-patterns & known pitfalls

    • Over-reliance on mocks: Teams may rely solely on mocks and miss issues that appear only with real LLMs. Remedy: Schedule regular integration tests with live models in staging environments.
    • Mock drift: Mock responses become outdated when the real API changes. Remedy: Automate schema checks that compare mock fixtures against live API response schemas.
    • Accidental use in production: Misconfiguration could route production traffic to mocks. Remedy: Use environment-specific configuration and fail-safe checks to prevent mock clients from being used outside test profiles.
    • Overcomplicating mock scenarios: Excessively complex mock configurations become hard to maintain. Remedy: Keep scenarios modular and well-documented, and reuse common fixtures.
    • Ignoring error scenarios: Neglecting to mock error responses leads to untested failure paths. Remedy: Include error injection as a mandatory part of test planning.

    Adoption guidance

    Starting point: Identify the LLM client interface in your codebase and implement a mock implementation analogous to MockLLMClient. Use it in your existing test suite to replace live calls.

    Migration path: 1. Implement the mock client behind the same interface. 2. Configure test environment to use the mock client via dependency injection or environment variable. 3. Create initial mock fixtures for the most common happy-path scenarios. 4. Expand coverage with error and edge-case scenarios. 5. Integrate with CI/CD pipeline and enforce that all tests run with mocks. 6. Periodically run a subset of tests against live LLM to validate compatibility.
