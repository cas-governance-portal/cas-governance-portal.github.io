    Reference Architecture: Continuous Architecture Governance Runtime

    Purpose & when to use this

    The Continuous Architecture Governance Runtime operationalises continuous architecture steering by implementing an automated closed-loop lifecycle (Detect -> Analyse -> Plan -> Execute -> Publish -> Observe) within CI/CD delivery pipelines. It prevents and remediates architectural drift without manual intervention for non-breaking changes, replacing slow, manual review boards with deterministic policy evaluation.

    When to use this

    • When architectural drift between design models and deployed codebases causes recurring delivery blockers or production incidents.
    • In high-velocity multi-repo or monorepo environments where manual Architecture Review Boards (ARBs) create a throughput bottleneck (e.g., 15:1 developer-to-architect ratio).
    • When architectural decisions (ADRs) can be codified into computable fitness functions, schema assertions, or static policy rules.
    • In engineering organisations targeting continuous compliance, regulatory traceability, or autonomous refactoring for non-breaking architectural updates.

    When NOT to use this

    • In early-stage exploratory prototypes or disposable greenfield proof-of-concepts where architecture undergoes radical daily pivots and schemas are intentionally unstable.
    • In teams lacking automated CI/CD pipelines, automated testing, or source-controlled architecture definitions.
    • For subjective or high-ambiguity domain modelling decisions that inherently require cross-functional consensus and stakeholder negotiation rather than rule-based automated verification.

    Components

    • Drift Detector Agent (src/governance/drift-detector): Inspects commit deltas, AST structures, infrastructure-as-code manifests, and service dependency graphs to detect divergence against recorded architecture state.
    • Fitness Policy Engine (src/governance/policy-engine): Executes declarative architecture fitness functions and compliance rules against detected drift to evaluate impact severity and identify policy violations.
    • Plan & Execution Controller (src/governance/execution-controller): Orchestrates automated remediation workflows, synthesizes Architecture Work Items, and generates safe automated pull requests or blocking signals.
    • Architecture State Store (docs/architecture/state): Maintains authoritative machine-readable current architecture state snapshots, architecture decision records (ADRs), and pattern catalogues.

    Technology choices

    Recommended Technologies

    • Policy Enforcement Engine: Open Policy Agent (OPA) / Rego or TypeScript-based structural linters (e.g., ArchUnit for JVM, ts-arch for TypeScript). Rationale: Declarative policy as code enables version-controlled, auditable governance assertions inside standard CI runners.
    • State Storage: Git-backed Markdown/JSON Schema repository (Architecture-as-Code). Rationale: Eliminates synchronization drift between documentation and code; benefits from Git history, PR reviews, and cryptographic commit signing.
    • Orchestration: GitHub Actions / GitLab CI custom actions running in containerized runtimes. Rationale: Integrates natively into developer pull request workflows without requiring external orchestration servers.

    Alternatives Considered & Set Aside

    • Centralized CMDB / Governance Web Portal: Rejected due to high operational latency, disjointed developer experience, stale manual synchronization, and inability to gate pull requests directly.
    • Fully Autonomous LLM Fixer without Deterministic Gates: Rejected due to nondeterministic hallucination risks on structural dependencies and lack of formal safety guarantees.

    Variants

    Variant A: Observability & Soft Governance (Advisory Mode)

    Operates asynchronously on merged branches or daily schedules. Evaluates policies and publishes warnings, architecture health scores, and Jira/Linear work items without blocking CI pipelines. Recommended for initial onboarding and legacy systems.

    Variant B: Deterministic Pull-Request Gate (Enforcing Mode)

    Runs synchronously inside pull-request checks. Fails build checks if critical architectural invariants (e.g., cyclic boundary violations, unauthorized data access layers) are broken, while auto-committing non-breaking remediations (e.g., manifest schema alignment).

    Non-functional characteristics

    Reliability

    • Idempotent execution: Multiple runs on the same commit hash produce identical evaluation states.
    • Graceful degradation: CI builds can be configured with safe fallback modes during governance engine transient failures to avoid blocking critical hotfixes.

    Performance & Latency

    • Pipeline Execution Overhead: Must complete evaluation within <= 45 seconds for incremental PR checks to preserve developer feedback velocity.
    • Caching: Employs distributed AST and dependency graph caching between runs to prevent repeated full-repository scanning.

    Cost & Efficiency

    • Serverless / Ephemeral Execution: Runs within existing CI runner allocations without requiring permanent dedicated infrastructure instances.

    Operability & Auditability

    • Cryptographic Audit Trail: Every architectural evaluation, pass/fail result, and drift remediation is recorded directly in Git history and pipeline logs, meeting enterprise compliance standards.

    Anti-patterns & known pitfalls

    Anti-Pattern 1: The 'All-Blocking Day One' Gate

    • Pitfall: Imposing strict blocking enforcement across dozens of newly codified rules on day one, stalling all team deliveries and causing developers to bypass checks.
    • Remedy: Start in Variant A (Advisory Mode) to build baseline drift metrics, tuning false positives before enabling synchronous gating for high-severity invariants only.

    Anti-Pattern 2: Unversioned External Governance Authority

    • Pitfall: Pointing CI runners to a dynamically updated remote policy endpoint without pinned semantic versions, causing unexpected build failures on untouched legacy repositories.
    • Remedy: Pin architecture governance engines and rule definitions to immutable semantic versions in the repository manifest.

    Anti-Pattern 3: Opaque Rule Failures

    • Pitfall: Failing a developer's build with generic errors such as 'Architecture policy violated' without contextual guidance.
    • Remedy: Provide actionable error annotations pointing directly to the violated ADR, the line of code, and a deterministic remediation guide.

    Adoption guidance

    Starting Points & Migration Path

    1. Phase 1 (Baseline Capture): Extract current architecture boundaries and declare them in machine-readable format (architecture-state.json).
    2. Phase 2 (Advisory CI Integration): Deploy the Drift Detector Agent into CI in reporting-only mode to measure baseline drift frequency and calibrate rules.
    3. Phase 3 (Selective Enforcement): Transition critical perimeter rules (e.g., public API contracts, modular boundary leaks) to blocking gates.
    4. Phase 4 (Autonomous Closed-Loop): Enable automated PR generation for routine updates (e.g., schema refactors, catalog updates).
