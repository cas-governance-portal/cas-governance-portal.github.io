    Reference Architecture: Deterministic Governance Action State Machine

    Purpose & when to use this

    This pattern restricts agent modifications to governance state through an explicit TransitionRegistry finite state machine (FSM). It ensures that autonomous agents cannot bypass approval gates, skip compliance checks, or trigger arbitrary state mutations. The engine validates every proposed transition against a declarative registry of legal transitions before executing any governance action, providing deterministic proof of valid state changes.

    When to use this

    • Use when autonomous agents or automated workflows must mutate governance state such as promotion decisions, rule exceptions, or architecture approvals, and those mutations must be auditable and verifiable.
    • Use when hallucinated or illegal state transitions pose a risk to system integrity, compliance, or policy enforcement.
    • Use when you need a reusable, centralized governance mechanism that can be applied across multiple lifecycle operations (promotion, approval, exception handling).
    • Use when auditability requires deterministic proof that a transition was legal, traceable to a specific actor and timestamp.
    • Use when the set of possible states and transitions is finite, enumerable, and stable enough to be captured in a registry.

    When NOT to use this

    • Do not use when the state space is open-ended or dynamically generated (e.g., free-form workflows where transitions cannot be enumerated upfront).
    • Do not use for simple CRUD operations that do not require governance gates or compliance checks.
    • Do not use when low-latency, high-throughput state mutations are required and the overhead of transition validation is unacceptable.
    • Do not use when teams lack the discipline to maintain the transition registry; a stale registry can become a bottleneck or cause false rejections.
    • Do not use when governance requirements are still evolving rapidly and the fixed transition set would cause frequent churn and rigidity.

    Components

    GovernanceActionEngine

    • Path: src/cas_runner/governance/governance_action_engine.py
    • Responsibility: Orchestrates the validation-then-execution pipeline for governance actions. It intercepts every proposed state mutation, builds a GovernanceAction from the request, and invokes the TransitionRegistry to verify that the transition from the current state to the target state is legal. Only after validation succeeds does it execute the action and record the outcome in the state store.

    TransitionRegistry

    • Path: src/cas_runner/governance/governance_action_engine.py
    • Responsibility: Declaratively defines the complete set of legal state transitions (source state, target state, required approval gates, and any preconditions). It exposes a lookup/validation method that the GovernanceActionEngine calls to determine whether a proposed transition is permitted. Acts as the single source of truth for governance rules.

    GovernanceAction

    • Path: src/cas_runner/governance/models.py
    • Responsibility: Typed model that represents a governance action with fields for source state, target state, action type, actor, timestamp, and metadata. Ensures that all actions conform to a strict schema, preventing malformed or ambiguous requests from reaching the engine.

    GovernanceException

    • Path: src/cas_runner/governance/models.py
    • Responsibility: Structured exception type raised when a transition is deemed illegal or a precondition fails. Provides consistent error reporting and enables deterministic failure handling by the caller, including logging and alerting.

    Governance State Store

    • Path: src/cas_runner/governance/
    • Responsibility: Persists the current governance state for each entity (e.g., proposal, exception, approval) and retains an append-only audit log of all executed transitions. The store is the authoritative source for 'current state' queries and post-hoc audit verification.

    Technology choices

    Recommended: Python 3.11+ with dataclasses or Pydantic v2 for typed GovernanceAction models; built-in enum or a simple class hierarchy for state representation; SQLite for lightweight local deployments or PostgreSQL for multi-writer production environments; file-based or in-memory TransitionRegistry for small-scale deployments.

    Alternatives considered and set aside: - BPMN/process engines (e.g., Camunda): powerful but heavyweight, introducing external infrastructure that complicates auditability and deployment. - Ad-hoc if/else validation embedded in each governance method: rejected because it duplicates logic, scatters rules, and makes auditing impossible. - Event sourcing frameworks: set aside as the current need is a simple FSM with audit trail, not a full event-sourced system. - Rule engines (Drools): overkill for enumerable transitions, and their DSL adds a learning curve.

    The chosen stack minimizes dependencies, keeps validation logic declarative and centralized, and is compatible with the existing cas_runner module structure.

    Variants

    1. Strict FSM vs. Hierarchical State Machine: In the strict variant, every transition must be explicitly registered; the hierarchical variant allows grouping states into super-states with inherited transition rules, useful when governance states naturally form a hierarchy (e.g., Draft -> Review -> Approved).
    2. Synchronous vs. Asynchronous Validation: The default is synchronous validation inside the engine; an asynchronous variant (event-based) can be used when the validation involves external checks or human-in-the-loop approvals, leveraging a queue to decouple the engine from external dependencies.
    3. Single Global Registry vs. Domain-Scoped Registries: For multi-domain systems, each domain can own a TransitionRegistry scoped to its state machines, reducing coupling; the global variant centralizes all transitions but may become a bottleneck.
    4. Enforcing vs. Advisory Mode: In enforcing mode, illegal transitions are rejected (default); in advisory mode, the engine logs warnings but allows the transition to proceed, useful for backward compatibility during migration.

    Non-functional characteristics

    Reliability

    The FSM ensures deterministic behavior - every action either succeeds as a legal transition or fails with a GovernanceException. The append-only audit log provides a trustworthy trail for compliance and post-incident analysis. Atomic validation-before-execution prevents partial state mutations.

    Performance & Latency

    Transition validation is an O(1) hash lookup in the TransitionRegistry, adding negligible latency (microseconds) compared to the actual governance action (e.g., promotion decision processing). In synchronous mode, the engine blocks on any external approval checks, which can increase latency proportionally; asynchronous mode mitigates this.

    Cost & Efficiency

    No additional infrastructure beyond the existing application runtime and a lightweight persistence layer (SQLite/PostgreSQL). Operational cost is minimal since the pattern is implemented as in-process code with no extra services.

    Operability

    The pattern is observable via structured GovernanceException logs and the audit trail; operators can trace any state change back to its initiating action and actor. The TransitionRegistry can be updated via configuration or code, and changes are straightforward to review. However, a stale or over-restrictive registry may require operational intervention to unlock legitimate workflows.

    Anti-patterns & known pitfalls

    1. Direct State Store Mutation: Circumventing the GovernanceActionEngine and writing to the state store directly breaks all invariants and auditability. Remedy: Encapsulate the state store behind a repository interface and ensure it is only accessible via the engine; enforce code reviews and static analysis to prevent bypass.
    2. Overly Restrictive Transitions: Defining too few transitions causes legitimate workflows to be rejected, leading to user frustration and workarounds. Remedy: Start with a permissive registry covering all real use cases, then tighten over time; involve domain experts when enumerating transitions.
    3. Duplicated Validation Logic: Copying transition-check logic into other services or scripts creates drift and inconsistency. Remedy: Always route through the GovernanceActionEngine; treat the registry as the single source of truth.
    4. Registry as God Object: Putting all transitions for the entire system into one registry leads to coupling and merge conflicts. Remedy: Use domain-scoped registries with clear ownership boundaries.
    5. Silent Failures: Catching GovernanceException and ignoring it hides illegal attempts, eroding trust in auditability. Remedy: Always log exceptions and alert when illegal transitions are attempted, as they may indicate a compromised or confused agent.

    Adoption guidance

    Starting point: Begin by auditing existing governance state mutations (promotion decisions, rule exceptions, architecture approvals) in the ideas-to-life-cas project, and enumerate all legal transitions into an initial TransitionRegistry.

    Migration path: 1. Introduce the GovernanceActionEngine and TransitionRegistry alongside the current code, with enforcement in advisory mode to collect illegal-attempt telemetry. 2. Switch to enforcing mode once the registry is validated against real workflows. 3. Replace all direct state mutations with calls to the engine, removing legacy paths. 4. Implement the audit log for all executed transitions.

    Governance ownership: Associate this pattern with the project domain_id for ideas-to-life-cas and the relevant initiative_id (to be assigned by the architect board). Owner contact: The governance architecture team responsible for cas_runner; day-to-day stewardship belongs to the platform engineering group maintaining the governance module.

    Related stakeholder links: Connect with the ADR for governance action engine, the global pattern catalogue entry, and the source files listed above.
