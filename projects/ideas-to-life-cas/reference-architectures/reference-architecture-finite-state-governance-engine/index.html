    Reference Architecture: Deterministic Governance Action State Machine

    Purpose & when to use this

    The Deterministic Governance Action State Machine establishes an authoritative, deterministic verification layer between autonomous reasoning agents and operational state mutations. By enforcing an explicit, codified transition registry, this pattern guarantees that autonomous agents, automated workflows, and human actors cannot bypass compliance gates, skip validation steps, or mutate lifecycle artifacts into unauthorized states.

    When to use this

    • When autonomous or semi-autonomous AI agents are empowered to propose or trigger lifecycle mutations (e.g., candidate promotion, policy deprecation, architectural ratification).
    • When governance, compliance, or regulatory standards demand zero-tolerance guarantees against illegal, out-of-order, or hallucinated state transitions.
    • When decoupling agentic planning and reasoning from state mutation authority is necessary to maintain an auditable system of record.
    • When lifecycle states follow discrete, deterministic workflows with explicit preconditions and invariants.

    When NOT to use this

    • In open-ended conversational or exploratory agents where operations do not mutate formal, managed lifecycle states.
    • In simple CRUD applications where basic static role-based access control (RBAC) without multi-step lifecycle progression is sufficient.
    • In experimental or early prototyping phases where lifecycle models are shifting continuously and formal transition tables impose unwanted development friction.

    Components

    • TransitionRegistry (src/cas_runner/governance/governance_action_engine.py): Maintains an immutable specification of valid (current_state, proposed_action) -> target_state transitions and executes precondition assertions prior to state mutations.
    • GovernanceActionEngine (src/cas_runner/governance/governance_action_engine.py): Orchestrates execution of requested governance operations, enforcing transition validation, triggering domain event notifications, and raising typed exceptions on policy violations.
    • GovernanceAction Models (src/cas_runner/governance/models.py): Provides strongly-typed schemas (GovernanceAction, GovernanceException) defining action types, actor identities, payloads, and structural error contracts.
    • Governance State Store (src/cas_runner/governance/storage.py): Persists verified artifact lifecycle states, ensuring transactional consistency and atomic updates during state transitions.
    • Audit Ledger Store (src/cas_runner/governance/audit.py): Appends tamper-evident audit records capturing allowed and rejected state transition attempts, actor metadata, and runtime timestamps.

    Technology choices

    Selected Technologies

    • In-Memory Pure State Registry: Implemented via Python native data structures, dataclasses, and strict Enum classes. This provides deterministic O(1) transition lookup with zero external network overhead.
    • Pydantic / Strict Typed Models: Standardizes action payloads (GovernanceAction) and transition contracts, enforcing schema correctness before passing commands to the engine.
    • Transactional Persistence (ACID Store): Relational or transactional document store (e.g., PostgreSQL or SQLite for embedded execution) guaranteeing serialized, isolated updates to lifecycle entities.

    Alternatives Considered and Set Aside

    • LLM-Based Guardrail Validation: Evaluated having a secondary LLM validate whether an action is allowed. Set aside due to non-deterministic failure modes, prompt injection risks, and unnecessary inference cost and latency.
    • Distributed Orchestration Engines (Temporal / Camunda): Considered for long-running workflows. Set aside for core state transition enforcement to avoid operational complexity and heavy external dependencies when in-process deterministic FSM validation is sufficient.
    • Unstructured Ad-Hoc Procedural Checks: Conditional if/else checks scattered across service boundaries were rejected due to maintenance drift, lack of exhaustiveness, and failure to provide a central audit trail.

    Variants

    1. Strict Synchronous In-Process Gate (Default)

    The engine evaluates the transition synchronously in the request execution path. Any disallowed transition immediately raises a GovernanceException, aborting the operation before any side effects or storage writes occur.

    2. Two-Phase Ratification Gate (Human-in-the-Loop)

    High-risk transitions (such as moving from PROPOSED to RATIFIED) enter an intermediary PENDING_APPROVAL state. The FSM prevents automated agent finalization until an authorized human operator or multi-signature consensus event transitions the entity to ACTIVE.

    3. Shadow / Advisory Mode

    Used during pattern rollout: transitions are evaluated against the registry, but illegal transitions are logged as telemetry anomalies rather than throwing exceptions, allowing teams to test lifecycle definitions without breaking workflows.

    Non-functional characteristics

    Reliability

    • Guarantees 100% deterministic state transitions; eliminates illegal edge states caused by agent hallucinations or non-linear reasoning paths.
    • Transactional isolation ensures transitions succeed completely or roll back without leaving artifacts in half-mutated states.

    Performance & Latency

    • Transition validation executes in sub-millisecond time (<1ms) via memory-mapped lookup tables.
    • Negligible latency impact relative to agent inference or network storage latency.

    Cost & Efficiency

    • Operates entirely within standard CPU runtimes with zero third-party API or LLM token costs.
    • Minimal memory footprint, allowing embedded deployment in lightweight edge and serverless runtime environments.

    Operability & Observability

    • Emits structured events for every transition attempt with full contextual metadata (actor_id, source_state, action, outcome).
    • Explicit error taxonomies (GovernanceException) allow automated recovery, self-correcting agent loops, and immediate triage for platform operators.

    Anti-patterns & known pitfalls

    1. The Dual-Truth Anti-Pattern

    • Problem: Maintaining state inside an agent's memory or context window while also persisting it in the registry, resulting in desynchronization.
    • Remedy: Treat the Governance State Store as the absolute single source of truth; agent context must be refreshed from storage prior to proposing transitions.

    2. The Over-Monolithic Transition Table

    • Problem: Hardcoding business domain validation rules (e.g., budget limits, text syntax) directly into the FSM transition table, leading to an unmaintainable state explosion.
    • Remedy: Keep the FSM focused strictly on lifecycle states; delegate contextual business logic validation to pluggable precondition guards.

    3. Silent Fallbacks / Implicit Coercion

    • Problem: Silently re-routing an invalid transition into a 'safe' default state without notifying the caller.
    • Remedy: Fail fast by raising explicit GovernanceException errors to ensure the invoking agent or engineer recognizes and addresses the invalid transition.

    Adoption guidance

    Migration Path

    1. State Discovery: Map existing lifecycle stages and catalog all valid operational actions and target states across the domain.
    2. Registry Codification: Instantiate the TransitionRegistry mapping origin states to allowable actions and target states, along with required precondition predicates.
    3. Shadow Deployment: Deploy the engine in Advisory Mode alongside existing services to log transition violations without terminating active pipelines.
    4. Enforcement Activation: Switch to Strict Synchronous Mode, ensuring all candidate promotion and state-mutation endpoints route through GovernanceActionEngine.
