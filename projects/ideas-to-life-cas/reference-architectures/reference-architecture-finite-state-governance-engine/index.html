    Reference Architecture: Deterministic Governance Action State Machine

    Purpose & when to use this

    Enforces provable, deterministic state transitions for all governance mutations initiated by autonomous agents or automated workflows. Autonomous agents can hallucinate or attempt invalid workflow bypasses; this pattern restricts state updates exclusively to formally registered transitions evaluated through a Finite State Machine (FSM).

    When to use this

    • Autonomous agents or automated pipelines are executing mutations against architectural, compliance, or lifecycle governance records (e.g., pattern promotion, rule exceptions, gate approvals).
    • Strict regulatory compliance and security posture require an immutable, auditable log proving that each state change followed valid preconditions and verified transition rules.
    • Multi-step governance workflows where skipping intermediate verification or approval stages introduces critical risk.

    When NOT to use this

    • Unstructured, open-ended conversational agent interactions with no formal lifecycle states or persistence.
    • Trivial CRUD models where transitions carry no compliance risk, policy dependencies, or branching constraints.
    • High-frequency ephemeral data streaming (e.g., telemetry metrics collection) where transactional transition verification induces unnecessary latency.

    Components

    • GovernanceActionService (src/cas_runner/governance/governance_action_service.py): Exposes the public governance API boundary, authenticates agent caller identities, parses incoming mutation payloads, and coordinates request orchestration with the engine.
    • GovernanceActionEngine (src/cas_runner/governance/governance_action_engine.py): Executes domain governance actions, enforces pre/post-conditions, triggers side effects, and records audit trails upon successful state transitions.
    • TransitionRegistry (src/cas_runner/governance/governance_action_engine.py): Houses the deterministic finite state machine graph, evaluating whether a requested state transition from state S(n) to S(n+1) under action A is permitted.
    • Governance Models & Contracts (src/cas_runner/governance/models.py): Defines typed immutable data structures (GovernanceAction, GovernanceException, TransitionContext) ensuring strictly typed boundaries and schema enforcement.

    Technology choices

    Recommended Choices

    • Implementation Language: Python 3.11+ using Pydantic v2 for typed model validation and static type guarantees.
    • State Engine Core: In-memory declarative TransitionRegistry with deterministic directed-acyclic/cyclic state validation tables, avoiding external heavyweight runtime dependencies.
    • Persistence & Audit: Relational database with transactional ACID guarantees (e.g., PostgreSQL) or append-only event ledgers for state transitions.

    Alternatives Considered & Set Aside

    • Ad-hoc Procedural Conditionals: Rejected due to high risk of gate bypassing, lack of visibility into state transition coverage, and high defect rates under agent hallucination.
    • Distributed BPMN Workflow Engines (e.g., Camunda, Temporal): Set aside as initial runtime dependency due to operational complexity; lightweight Python FSM contracts provide sufficient isolation with lower operational overhead.

    Variants

    • Synchronous Interactive Mode: Real-time blocking evaluation where agent requests are validated, committed, and responded to within a single synchronous request-response boundary.
    • Asynchronous Gatekeeper Mode: State mutations are recorded in a pending transition state, requiring asynchronous quorum, human-in-the-loop (HITL) sign-off, or multi-agent consensus before entering terminal state.
    • Dry-Run / Policy Simulation Mode: Evaluates state transition validity without committing mutations or executing side-effects, allowing agents to pre-flight actions.

    Non-functional characteristics

    • Reliability: Deterministic state gating guarantees zero illegal state transitions even under erroneous agent input; exceptions are strongly typed and bubble up with machine-readable remediation codes.
    • Performance & Latency: In-memory transition table lookup incurs sub-millisecond overhead (< 2ms) during the validation phase; database commit boundaries bound total execution time to standard write latency.
    • Cost & Efficiency: Zero external service licensing overhead; runs co-located with service runners, minimizing infrastructure cost.
    • Operability: Transitions emit structured OpenTelemetry traces and audit events detailing caller identity, previous state, target state, applied action, and timestamp.

    Anti-patterns & known pitfalls

    • Engine Bypass via Direct Database Updates: Modifying entity state directly in the database without passing through GovernanceActionEngine, corrupting state consistency. Remedy: Restrict data tier permissions so that only the service account utilized by GovernanceActionEngine possesses write privileges.
    • Domain Logic Smear into Registry: Injecting business mutation logic directly into TransitionRegistry definitions. Remedy: Keep TransitionRegistry strictly focused on topology (allowed transitions and guard checks); keep execution logic inside GovernanceActionEngine.
    • Permissive Dynamic Transitions: Creating catch-all wildcard transitions (e.g., * -> Approved). Remedy: Require explicit source-target mapping for every transition.

    Adoption guidance

    Migration Path

    1. Inventory existing governance entity states and map out all valid transitions on an explicit state chart.
    2. Encode valid states and transitions in TransitionRegistry within src/cas_runner/governance/governance_action_engine.py.
    3. Wrap all mutation endpoints with GovernanceActionService to ensure no agent can mutate entity state directly.
    4. Introduce negative regression tests verifying that unauthorized transitions raise GovernanceException.
