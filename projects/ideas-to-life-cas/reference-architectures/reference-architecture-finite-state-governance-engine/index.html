    Reference Architecture: Deterministic Governance Action State Machine

    Purpose & when to use this

    The Deterministic Governance Action State Machine pattern provides an authoritative boundary that validates, orchestrates, and records lifecycle transitions for governed software, architecture, and deployment artifacts. In environments driven by autonomous multi-agent systems or automated pipelines, non-deterministic agents may attempt invalid state skips, bypass required reviews, or corrupt artifact metadata. This pattern imposes a strict, fail-closed finite state machine (FSM) enforcing transition prerequisites and deterministic state mutations.

    When to use this

    • When autonomous AI agents or automated pipelines have permissions to mutate artifact lifecycle states (e.g., candidate promotion, architecture deprecation, production certification).
    • In regulated or high-assurance systems where auditability demands verifiable, tamper-evident lineage of who or what initiated each transition.
    • When business or architectural rules mandate strict sequential gates (e.g., code cannot transition to 'promoted' without meeting quality and verification criteria).
    • To centralize scattered transition validation logic into a unified, versioned transition registry.

    When NOT to use this

    • In simple CRUD applications where lifecycle progression is linear, single-user, and without multi-step safety invariants.
    • For fluid, exploratory workflows where artifact states are ad-hoc, unstructured, or intentionally non-linear without governance implications.
    • In ultra-low latency data plane processing where state check overhead cannot be tolerated and consistency is eventual.

    Components

    • TransitionRegistry (src/cas_runner/governance/governance_action_engine.py): Encapsulates valid lifecycle states and permissible directed transitions between them. Evaluates pre-conditions, required approvals, and invariant assertions before permitting any state mutation.
    • GovernanceActionEngine (src/cas_runner/governance/governance_action_engine.py): Orchestrates governance action requests. Accepts strongly-typed GovernanceAction payloads, queries the TransitionRegistry for validity, executes transactional state modifications, and guarantees fail-closed error handling.
    • Governance Action & Domain Models (src/cas_runner/governance/models.py): Provides immutable schemas for GovernanceAction, State transitions, and the typed GovernanceException hierarchy representing transition violations.
    • Governance State & Audit Store (src/cas_runner/governance/storage.py): Persists current artifact lifecycle states along with immutable, append-only logs capturing actor identities, timestamps, input parameters, and transition rationales.

    Technology choices

    Recommended Technologies

    • In-Memory Deterministic FSM Registry (Python / Pydantic / TypedDicts): Enforces compile-time and runtime validation with minimal overhead, natively supporting type validation in src/cas_runner/governance/models.py.
    • Transactional Persistence (PostgreSQL or ACID-compliant Document Store): Guarantees linearizable transition commit and concurrent lock handling to prevent race conditions during parallel state changes.
    • Append-Only Audit Journal (Structured JSON Logs or Event Store): Emits structured telemetry for every transition attempt (both approved and rejected) for compliance auditing.

    Alternatives Considered & Set Aside

    • Decentralized Boolean Flags on Entities: Rejected due to state drift, lack of centralized gatekeeping, and vulnerability to agents directly mutating individual attributes without checking preconditions.
    • Heavyweight External BPMN / Workflow Engines (e.g., Camunda, Temporal): Set aside for local governance operations to avoid external network hops and excessive operational footprint, though appropriate as an outer-loop orchestrator.

    Variants

    1. Synchronous Guarded Execution (Default)

    The calling process invokes the GovernanceActionEngine synchronously. The engine checks the TransitionRegistry, writes to storage, and returns an updated state or raises a GovernanceException. Ideal for CLI tools and deterministic pipeline steps.

    2. Asynchronous Event-Driven FSM

    State transition intents are published to an event bus. The governance engine acts as an event consumer, validating transitions, writing to an outbox, and broadcasting transition completed/failed events.

    3. Dry-Run / Policy Simulation Mode

    The engine evaluates whether a hypothetical state transition would succeed under current registry rules without persisting mutations, enabling autonomous agents to plan multi-step actions safely.

    Non-functional characteristics

    Reliability

    • Fail-Closed Guarantees: Any unmapped transition or unmet condition raises a deterministic GovernanceException, preventing unverified state advancement.
    • Concurrency Control: Optimistic locking via version fields or explicit row-level locks ensures parallel agent actions do not cause race conditions.

    Performance & Latency

    • O(1) In-Memory Lookup: State validation operates as a constant-time table lookup within TransitionRegistry, keeping overhead below 2 milliseconds.

    Cost & Efficiency

    • Low Compute Overhead: Eliminates complex distributed rollbacks and remediation compute costs by preventing invalid operations upfront.

    Operability & Observability

    • Structured Diagnostic Codes: Distinct error codes and structured transition metadata enable real-time alerting on agent hallucination rates or broken pipeline attempts.
    • Complete Audit Trail: Every executed or rejected transition records actor provenance, timestamp, and target state.

    Anti-patterns & known pitfalls

    1. The 'Bypass Force Flag'

    • Anti-pattern: Adding parameters like force=True or skip_validation=True to the action engine to expedite emergency releases.
    • Remedy: Model emergency states as formal transitions in the registry requiring designated break-glass credentials and explicit post-incident audits.

    2. Direct State Mutation (Backdoor Updates)

    • Anti-pattern: Allowing repository or data access layers to update status fields directly in the database without passing through GovernanceActionEngine.
    • Remedy: Restrict write access to artifact state tables exclusively to the engine service account or encapsulate updates behind an authoritative repository interface.

    3. Static Matrix Rot

    • Anti-pattern: Hardcoding states without versioning the transition matrix, leading to deadlocks when emerging operational states are introduced.
    • Remedy: Maintain the transition matrix as declarative versioned configuration, validated by automated FSM reachability test suites.

    Adoption guidance

    Starting Points & Migration Path

    1. State Discovery: Map all existing implicit artifact lifecycle states and assemble them into a formal directed state diagram.
    2. Codify Transition Matrix: Instantiate the TransitionRegistry mapping current states to permissible next states, attaching precondition callables.
    3. Intercept Mutation Paths: Refactor all agent action handlers to route through GovernanceActionEngine.execute_transition(action).
    4. Enable Audit Assertion: Introduce integration tests simulating both valid journeys and illegal transition attempts (e.g., skipping review steps) to verify fail-closed behavior.
